# パンくずリスト UI コンポーネント — 調査結果まとめ

<!-- 過去の社内フレームワーク調査（beeworks-framework の breadcrumbs.astro）の観点を統合済み -->

## 1. コンポーネントの概要（What & Why）

### 定義・解決する問題

パンくずリストは、現在のページから上位階層（親ページ）へのリンクを階層順に並べたナビゲーション。「サイトの中で自分がどこにいるか」を示し、上位階層へワンクリックで戻れるようにする。

- **パンくずリストの設置自体が、達成基準 2.4.8 現在位置（レベル AAA）の代表的な達成方法（G65）**。他章の UI が「作ると要件を背負う」のに対し、パンくずは「置くこと自体が達成基準への貢献」という珍しい立ち位置（過去の社内フレームワーク調査でもこの観点が筆頭だった）
- 検索エンジンからの直接流入では、ユーザーはサイト構造を知らないまま深い階層に着地する。パンくずはその文脈を補う

### そもそも使うべきかの判断

- 使う価値が高いのは**階層が 2 段以上あるサイト**。フラットな構造（トップ + 数ページ）では、グローバルナビゲーションと重複するだけで不要
- パンくずは**主要ナビゲーションの補助**であって代替ではない（NN/g）。パンくずがあることを理由にナビゲーションを削らない
- 種類の整理（NN/g の分類）:
  - **階層型（location-based）**: サイト構造上の位置を示す。基本形でこれを使う
  - **履歴型（path-based）**: ユーザーが辿った経路を示す。**ブラウザの戻ると重複し、同じページでも表示が変わって混乱を招くため非推奨**（→ 層 3「不採用」）
  - 属性型（EC の絞り込み条件表示など）: フィルター章の領域と重なる
- コストが低い（リンクの列だけ・場所も取らない）ため、「使うべきか」より「正しく作れているか」が主題になるコンポーネント

### ネイティブ HTML 要素の有無

- 専用要素はないが、**`nav` + `ol` + `a` の素の HTML で完結する**。JS 不要・ARIA も `aria-label` と `aria-current` の 2 つだけ。ページネーション章と同じ「HTML だけで正しく作れる」側
- APG にも Breadcrumb の公式サンプルがあり、構成はほぼ確定している（→ 参考記事 #1）

### 類似コンポーネントとの使い分け

| 観点 | パンくずリスト | グローバルナビゲーション | ページタイトル（h1） |
|------|-----------------|---------------------------|-----------------------|
| **伝えるもの** | 階層上の現在位置と経路 | サイトの主要セクション | このページが何か |
| **移動できる先** | 祖先ページ | 全セクション | （移動しない） |
| **省略可否** | 補助（なくても致命傷ではない） | 必須級 | 必須 |
| **2.4.8 への寄与** | 達成方法そのもの | 部分的 | 部分的 |

## 2. アクセシブルであるためには（要件・規範）

### WCAG 2.2 該当基準の洗い出し

<!-- △ = 該当するか微妙だが念のため入れておく。詳細な要件・確認方法はチェック項目案側 -->

- **達成基準 2.4.8 現在位置（レベル AAA）** — パンくず設置自体が達成方法（G65）。「要件」ではなく「効能」として書く
- **達成基準 1.3.1 情報及び関係性（レベル A）** — `nav` によるナビゲーションの明示、`ol` による順序付きリスト構造
- **達成基準 4.1.2 名前・役割・値（レベル A）** — `nav` の `aria-label`（他のナビゲーションとの区別）、`aria-current` による現在位置
- **達成基準 2.4.4 リンクの目的（コンテキスト内）（レベル A）** — 各リンクがどの階層へのリンクか分かる（通常はページ名で自然に満たせる）
- **達成基準 2.1.1 キーボード（レベル A）** — 標準リンクなら自動で満たせる
- **達成基準 1.4.1 色の使用（レベル A）** — リンクと現在ページ（非リンク）の区別が色だけになっていない
- **達成基準 1.4.4 文字サイズの変更 ／ 1.4.10 リフロー（レベル AA）** — 長い階層・長いページ名でも読める（過去調査の「デザイン上の考慮事項」に対応）
- △ **達成基準 2.5.8 ターゲットのサイズ（最低限）（レベル AA）** — リンクが小さい文字で並ぶ
- △ **達成基準 2.4.7 フォーカスの可視化（レベル AA）** — リンクのフォーカスリング
- △ **達成基準 3.2.3 一貫したナビゲーション（レベル AA）** — 全ページで同じ位置・形式

### キーボード操作仕様

APG も「Not applicable（標準のリンク操作のみ）」と明記。`Tab` で順に移動し `Enter` で遷移する以外の仕様はない。専用のキーボード実装が不要であること自体が、このコンポーネントの美点として書ける。

### ARIA ロールと属性（APG）

| 属性・要素 | 付与先 | 値・説明 |
|------------|--------|----------|
| `nav` 要素 | 全体のコンテナ | ナビゲーションランドマークにする |
| `aria-label` | `nav` | 「パンくずリスト」等。ページ内の他の `nav` と区別する |
| `ol` 要素 | リンクのリスト | 階層の順序を表すため順序付きリスト |
| `aria-current="page"` | 最後の項目（現在ページ） | 現在ページをリンクにする場合は**必須**、リンクにしない（`span` 等）場合は任意（APG） |

補足:

- **セパレータ（「>」「/」等）はコンテンツにしない**。`li` 内のテキストとして書くとスクリーンリーダーが「大なり」等と読み上げる。CSS の `::before` / `::after` で生成するか、装飾画像・`aria-hidden="true"` の要素にする
- `aria-current` の値は現在**ページ**なら `page`。ナビゲーション内で「現在ページの祖先カテゴリ」を示す場合は `aria-current="true"` を使う、という APG タスクフォースの見解がある（→ 参考記事 #9。パンくずでは通常最後の項目＝ページ本体なので `page` でよい）
- 構造化データ（schema.org の `BreadcrumbList`）は SEO 目的の別レイヤー。アクセシビリティ要件ではないが、実務では併記されることが多いので記事で一言触れる価値あり（→ 参考記事 #8）

### WCAG 外のユーザビリティ要件

- **長いテキストの扱い**（過去調査の観点）: ページ名が長い・階層が深い場合の表示を必ず確認する。過去のサンプルは「1 行で省略（ellipsis）」だったが、**あくまで一例であり、省略すると現在地の情報自体が読めなくなる**トレードオフがある。折り返して全文表示する選択肢も併記する
- **モバイルでの縮約**: 中間階層を「…」ボタンで畳む（GOV.UK の collapse オプション等）。畳む場合は展開手段をキーボード・SR からも使えるようにする（ディスクロージャーの要件が乗ってくる）
- **現在ページを載せるか**: 載せる（最後の項目・非リンクまたは `aria-current` 付きリンク）のが主流。載せないと「どこまでが経路で、いまどこか」が完結しない
- **タップ領域**: 小さな文字リンクの列になりがち。行間・パディングで領域を確保する

### チェック項目案（記事の単位に束ね直す）

#### パンくずリストだと識別でき、他のナビゲーションと区別できるようにする【他章共通】

- 流用元: ページネーション章「ページネーションだと識別できるようにする」項（`nav` + `aria-label` の同型パターン）
- 該当基準: 1.3.1 情報及び関係性、4.1.2 名前・役割・値
- 要件: `nav` + `aria-label="パンくずリスト"`、`ol` によるリスト構造
- 確認方法: スクリーンリーダーのランドマーク一覧で「パンくずリスト ナビゲーション」として識別できるか

#### 現在のページが視覚でもスクリーンリーダーでもわかるようにする【本章固有】

- 該当基準: 4.1.2、1.4.1 色の使用
- 要件: 最後の項目に `aria-current="page"`。リンクと現在ページ（非リンク）の見た目の区別を色だけにしない（下線の有無・太さ等を併用）
- 確認方法: スクリーンリーダーで最後の項目が「現在のページ」と読まれるか。グレースケールでリンクと現在地を区別できるか

#### 区切り文字が読み上げの邪魔をしないようにする【本章固有】

- 該当基準: 1.3.1（構造と表示の分離）
- 要件: セパレータは CSS 生成コンテンツで描く。HTML に書く場合は `aria-hidden="true"`
- 確認方法: スクリーンリーダーで「トップ、大なり、一覧ページ」のようにセパレータが読まれないか

#### 長いページ名・深い階層でも読めるようにする【他章共通】

- 流用元: アコーディオン章「文字の拡大・行間の変更・画面幅の縮小でも〜」項
- 該当基準: 1.4.4 文字サイズの変更、1.4.10 リフロー
- 要件: 長いテキストで確認する（過去調査のサンプルは長文テストケースを持っていた）。1 行省略にする場合は「読めなくなる情報」とのトレードオフを認識して選ぶ。折り返し許容が無難
- 確認方法: 長いページ名 + ズーム 200% + 画面幅 320px で、リンクが操作でき現在地が読めるか

#### キーボードで操作でき、フォーカスが見えるようにする【他章共通】

- 流用元: ページネーション章の同名項
- 該当基準: 2.1.1 キーボード、2.4.7 フォーカスの可視化
- 確認方法: `Tab` で各リンクに到達でき、フォーカスリングが見えるか

#### 見送り（チェック項目にしない基準）

- **2.4.8 現在位置（AAA）** — チェック項目ではなく「パンくずを置くこと自体がこの基準の達成方法」として冒頭（〜とは）で扱う
- **2.5.8 ターゲットのサイズ** — ユーザビリティ節のタップ領域の話に吸収（主役はページネーション章）
- **3.2.3 一貫したナビゲーション** — サイト全体の話。扱わない（ページネーション章と同じ判断）
- **2.4.4 リンクの目的** — ページ名がそのままリンクテキストになる構造上、通常は自然に満たされる。特筆しない

## 3. 具体事例（Evidence）

### 実装事例（デザインシステム）

| 項目 | W3C APG | GOV.UK | Scott O'Hara の実装解説 | 過去の社内フレームワーク |
|------|---------|--------|--------------------------|---------------------------|
| **コンテナ** | `nav` + `aria-label="Breadcrumb"` | `nav` + ラベル | `nav` + `aria-label` | `nav` + `aria-label="パンくずリスト"` |
| **リスト** | `ol` | `ol` | `ol` | `ol` |
| **現在ページ** | リンク + `aria-current="page"` | 現在ページを省略するパターンもあり | リンク or 非リンク両論 | `span` + `aria-current="page"` |
| **セパレータ** | CSS 生成 | CSS | CSS 生成（コンテンツに入れない） | CSS |
| **モバイル** | — | 中間階層の collapse | — | 1 行省略（ellipsis） |

#### 設計判断ポイント（実装が割れている論点）

- **現在ページを載せるか・リンクにするか** — 3 択（載せない／`span` で載せる／リンク + `aria-current` で載せる）。載せる場合、`span` に `aria-current="page"` を付ける形（過去の社内実装と同じ）が「無意味な自己リンクを作らない」点で扱いやすい。ページネーション章の同論点とセットで解説できる
- **1 行省略 vs 折り返し** — 省略はレイアウトが安定するが情報が欠ける。折り返しは崩れにくさの確認が必要。「どちらでもよいが、確認すべきことが違う」という書き方ができる（過去調査も「一例でありこれに限らない」と明記していた）
- **モバイルでの縮約方式** — 全表示／中間を「…」で畳む（要ディスクロージャー実装）／「1 つ上の階層へ戻る」リンクだけにする（GOV.UK が採用例）。3 案目は実装が最も単純で壊れにくい
- **構造化データの併記** — `BreadcrumbList`（JSON-LD）は SEO 上の慣習。ARIA とは独立していることを明確にする（構造化データを書いても支援技術には何も伝わらない）

### 失敗事例（ありがちな NG 例）

<!-- 候補ベース。執筆前にコード例化と裏取りをする -->

- **NG: セパレータ「>」をテキストとして書いている**
  - 対応する要件: 1.3.1
  - 何が起きるか: スクリーンリーダーが「トップ 大なり 一覧ページ 大なり…」と読み、経路が聞き取りにくくなる
- **NG: `nav` にラベルがなく、他のナビゲーションと区別できない**
  - 対応する要件: 4.1.2
  - 何が起きるか: ランドマーク一覧に「ナビゲーション」が複数並び、どれがパンくずか分からない
- **NG: `div` の羅列（リスト構造がない）**
  - 対応する要件: 1.3.1
  - 何が起きるか: 「3 項目のリスト」という構造情報が失われ、経路の全体量が把握できない
- **NG: 現在ページとリンクの区別が色だけ**
  - 対応する要件: 1.4.1
  - 何が起きるか: どこまでがリンク（押せる）でどれが現在地か、色覚特性によっては判別できない
- **NG: 長いページ名が 1 行省略で「…」になり、現在地が読めない**
  - 対応する要件: 1.4.4 / 1.4.10（実害としては現在地情報の喪失）
  - 何が起きるか: パンくずの存在意義（現在位置の把握）が失われる。拡大表示ではさらに悪化する
- **NG: 構造化データ（JSON-LD）だけ書いて、画面上のパンくずのマークアップは `div` のまま**
  - 対応する要件: 1.3.1、4.1.2
  - 何が起きるか: 検索結果には階層が出るのに、当のページでは支援技術に何も伝わらない

### 新しいブラウザ機能

該当なし（素の HTML で完結する。ページネーション章と同じ「新機能に頼らない」見本側）。

### フォールバック・不採用案

#### フォールバック: 「1 つ上の階層へ戻る」リンク

- 深い階層や狭い画面でパンくず全体を出せない場合、「← ○○（親ページ名）へ戻る」リンク 1 本に縮退させる（GOV.UK の採用例）。経路全体は失うが、最重要の「1 つ戻る」は保てる

#### 不採用: 履歴型（path-based）パンくず

**最大の問題: ブラウザの戻る機能と重複し、同じページなのに来訪経路によって表示が変わるため、現在位置の理解をむしろ妨げる（NN/g）。**

**その他の問題:**

- 実装も状態管理（セッション）が必要になり、素の HTML で完結する階層型の利点を失う
- 2.4.8 の達成方法として想定されているのも階層型（サイト構造上の位置）
