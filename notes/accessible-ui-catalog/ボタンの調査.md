## 1. コンポーネントの概要（What & Why）

### 定義・解決する問題

ボタンは、ユーザーの操作（クリック・タップ・キー押下）でページ内の動作を実行するコントロール。本書で扱うほぼすべてのコンポーネント（ダイアログを開く・タブを切り替える・アコーディオンを開閉する…）のトリガーがボタンであり、**ここが壊れていると全部が壊れる**土台のコンポーネント。

この章の本質的な問い: **「それはボタンか、リンクか」**

- **リンク（`a`）**: 別の場所（URL）へ移動する。右クリックで新しいタブに開ける・URL をコピーできる・履歴に残る
- **ボタン（`button`）**: その場で動作を実行する（送信・開閉・切り替え・削除）

見た目は自由（ボタンの見た目のリンクは問題ない）だが、**実体（要素）は挙動で選ぶ**。スクリーンリーダーのユーザーは「リンク」「ボタン」という読み上げから挙動を予測して操作している（→ 参考記事 #5）。

### そもそも使うべきかの判断

- ボタン自体は「使うべきか」を迷う対象ではない。迷うべきは**実体の選択**（上記）と、**その操作が本当に必要か**（ボタンが多い UI は選択肢が多すぎる UI）
- 「見た目がテキストリンクの `button`」「見た目がボタンの `a`」はどちらも正当。**見た目とセマンティクスは独立に決める**という原則を最初に示す章にできる

### ネイティブ HTML 要素の有無

- **`button` 要素がある**。フォーカス可能・`Enter` / `Space` で発火・`role="button"` 暗黙付与・フォーム統合まで全部入り。この章は「ネイティブを使えばほぼ終わり」のショーケース
- 過去調査からの重要な実務知見: **`button` には基本的に `type="button"` を明示する**。`type` のデフォルトは `submit` なので、フォーム内に置いた「開閉ボタン」などが意図せずフォームを送信する事故が定番（過去の社内フレームワークでは全コンポーネント共通の注意事項として繰り返し明記されていた）
- `div` / `span` + クリックイベントで作る「なんちゃってボタン」は、フォーカス・キーボード発火・ロール・状態のすべてを自前再実装することになる（→ 層 3「不採用」）

### 類似要素との使い分け

| 観点 | `button` | `a`（リンク） | `input type="submit"` |
|------|-----------|---------------|------------------------|
| **用途** | その場の動作 | URL への移動 | フォーム送信（`button type="submit"` と同等） |
| **キーボード発火** | `Enter` と `Space` | `Enter` のみ（`Space` はスクロール） | `Enter` と `Space` |
| **右クリック・新規タブ** | 不可 | 可能（奪ってはいけない） | 不可 |
| **`disabled`** | あり | なし（概念自体がない） | あり |
| **中に置ける内容** | フレージングコンテンツ | ほぼ何でも（インタラクティブ要素以外） | テキストのみ（`value`） |

- `a` に `href` がない場合はフォーカス不能になる。「`href` のない `a` + JS」はボタンの劣化版でしかない

## 2. アクセシブルであるためには（要件・規範）

### WCAG 2.2 該当基準の洗い出し

<!-- △ = 該当するか微妙だが念のため入れておく。詳細な要件・確認方法はチェック項目案側 -->

- **達成基準 4.1.2 名前・役割・値（レベル A）** — ボタンに名前がある（特にアイコンのみのボタン）。役割が「ボタン」として伝わる
- **達成基準 2.1.1 キーボード（レベル A）** — `Enter` / `Space` で発火する（`button` 要素なら自動）
- **達成基準 1.1.1 非テキストコンテンツ（レベル A）** — アイコンボタンのアイコンに代替（名前）がある
- **達成基準 2.4.7 フォーカスの可視化（レベル AA）** — フォーカスリングが見える（`overflow: hidden` で欠ける事故への注意は過去調査の定番指摘）
- **達成基準 2.5.8 ターゲットのサイズ（最低限）（レベル AA）** ※WCAG 2.2 新規 — 24×24 CSS ピクセル以上
- **達成基準 1.4.3 コントラスト（最低限）（レベル AA）** — ラベル文字と背景のコントラスト 4.5:1。**無効状態のボタンは適用除外**（フォーム章と同じ但し書き）
- **達成基準 2.5.3 ラベルを含む名前（レベル A）** — 視覚ラベルと `aria-label` がずれない（音声操作で「保存 をクリック」と言えるか）
- **達成基準 2.5.2 ポインタのキャンセル（レベル A）** — 押下（down）ではなく解放（up）で発火する。ネイティブの `click` イベントを使っていれば自動で満たせる（`mousedown` / `touchstart` で発火させる独自実装が違反する）
- △ **達成基準 1.4.11 非テキストのコントラスト（レベル AA）** — ボタンの枠線・背景。厳密には「ヒット領域の理解に視覚的な境界が必要な場合」だけが対象で、テキストだけでボタンと分かるなら枠のコントラストは必須でない（誤解の多い基準として正確に書く価値あり）
- △ **達成基準 1.4.1 色の使用（レベル A）** — 状態（押下・選択）を色だけで示す場合
- △ **達成基準 3.2.5 要求による変化（レベル AAA）** — ボタンの動作が予測どおりであること（一般論）

### キーボード操作仕様

| キー | 動作 |
|------|------|
| `Enter` | 発火（keydown 時） |
| `Space` | 発火（keyup 時。押しっぱなしでキャンセル可能） |

- `button` 要素ならブラウザが提供する。**`a` + `role="button"` で自作すると `Space` 対応と `Enter` の抑制を JS で書く羽目になる**（役割を偽装したら挙動も偽装し切る責任が生じる、という教材例）
- `Space` が keyup 発火なのは 2.5.2（ポインタのキャンセル）のキーボード版に相当する挙動で、豆知識として面白い

### ARIA ロールと属性

ネイティブ `button` を使う限り、必要な ARIA はほぼない。状態を持つボタンにだけ追加する:

| 属性 | 用途 | 説明 |
|------|------|------|
| `aria-label` / 視覚的に隠すテキスト | アイコンのみのボタンの名前 | ツールチップ章「トリガー自体に名前」項と同一の論点 |
| `aria-expanded` | 開閉トリガー | アコーディオン・ヘッダーのサブメニュー等 |
| `aria-pressed` | トグルボタン | 押下状態が残るボタン（タブ章のフォールバックでも登場） |
| `aria-disabled="true"` | 「無効だが説明したい」状態 | `disabled` との使い分けは設計判断ポイント（→ 層 3） |
| `aria-busy` / ライブリージョン | 処理中状態 | 送信中の「保存中…」等。ラベル変更 + `role="status"` 併用が実際的 |

### WCAG 外のユーザビリティ要件

- **長いテキスト・狭い画面での表示確認**（過去調査のデザイン考慮事項）: ラベルが長い場合に折り返すか・はみ出さないか。`white-space: nowrap` で組むと翻訳・拡大で破綻する（ツールチップ章と同じ構図）
- **多重送信の防止**: 送信ボタン連打への対策は `disabled` 化だけでなく、処理中表示 + 冪等化。`disabled` にするならフォーカスを失わせない工夫（`aria-disabled` 方式）を検討
- **ラベルの文言**: 「はい／いいえ」より「保存する／保存しない」のように動作を書く（ダイアログ章の確認ボタンと共通）

### チェック項目案（記事の単位に束ね直す）

#### 移動なら `a`、動作なら `button` を使うようにする【本章固有】

- 該当基準: 4.1.2 名前・役割・値（役割の正しさ）
- 要件: URL が変わる操作は `a href`、その場の動作は `button type="button"`（送信は `type="submit"`）。`div` / `span` + クリックイベントにしない
- 確認方法: スクリーンリーダーで「リンク」「ボタン」が挙動どおりに読み分けられるか。リンクを右クリックして「新しいタブで開く」が使えるか
- 補足: `type` 未指定の `button` がフォーム内で誤送信する事故（過去調査の定番注意）はここで扱う

#### アイコンのみのボタンにも名前があるようにする【他章共通】

- 流用元: ツールチップ章「トリガー自体にアクセシブルな名前がある」項
- 該当基準: 4.1.2、1.1.1
- 要件: 視覚的に隠したテキストまたは `aria-label`。視覚ラベルがある場合は `aria-label` で上書きしない（2.5.3）
- 確認方法: スクリーンリーダーで「○○ ボタン」と読まれるか

#### フォーカスインジケータが見えるようにする【他章共通】

- 流用元: アコーディオン章「フォーカスインジケータが見える」項
- 該当基準: 2.4.7
- 要件: `outline: none` で消さない。消すなら `:focus-visible` で代替スタイルを用意。`overflow: hidden` の親でリングが欠けないか（過去調査の指摘）
- 確認方法: `Tab` でフォーカスしてリングが四辺とも見えるか

#### 押しやすい大きさにする【他章共通】

- 流用元: ページネーション章「番号リンクを押しやすい大きさにする」項
- 該当基準: 2.5.8 ターゲットのサイズ（最低限）
- 確認方法: 最小のボタン（アイコンボタン）の操作領域が 24×24 CSS ピクセル以上か

#### 無効状態のボタンの伝え方を決める【本章固有】

- 該当基準: 4.1.2（状態の伝達）、1.4.3 の適用除外の理解
- 要件: `disabled` はフォーカス不能＝存在に気づけない。「なぜ押せないか」を伝えたいなら `aria-disabled="true"`（フォーカス可能・説明を読める）+ クリック無視、または最初から押させてエラーを説明する（フォーム章参照）
- 確認方法: キーボード操作だけで、無効なボタンの存在と理由に気づけるか

#### 見送り（チェック項目にしない基準）

- **2.5.2 ポインタのキャンセル** — ネイティブの `click` を使う限り自動で満たせる。独自ジェスチャ実装の注意として実装例の補足で触れる
- **1.4.11 非テキストのコントラスト** — 「ボタンの枠線は必須ではない」という誤解されがちな正確な話をコラム候補にする（チェック項目にすると過剰要求になる）
- **長いテキスト・狭幅** — アコーディオン章の拡大系項目と同じ話。ビジュアルデザイン節で扱う

## 3. 具体事例（Evidence）

### 実装事例・設計判断ポイント

ボタン単体はデザインシステム間の差が小さいため、比較表よりも**割れている論点**を中心に据える:

- **`disabled` vs `aria-disabled` vs 押させてエラー** — 3 派に割れる代表的論点
  | | `disabled` | `aria-disabled="true"` | 押させてエラー表示 |
  |---|---|---|---|
  | フォーカス | 不可（存在に気づけない） | 可能 | 可能 |
  | 理由の説明 | 困難 | `aria-describedby` で可能 | エラーメッセージで確実 |
  | 実装 | 属性 1 つ | クリック無視の JS が必要 | バリデーション実装 |
  | 向く場面 | 一時的・自明な無効化 | 無効の理由を伝えたい場面 | フォーム送信（フォーム章の推奨） |
- **処理中（ローディング）状態** — ラベルを「保存中…」に変える + `role="status"` で通知 + 再押下を無視、が堅実。スピナーだけ（テキストなし）は伝わらない
- **「ボタンの見た目のリンク」の可否** — 見た目は自由、実体は挙動で。CTA がリンクなら `a` のまま装飾する（Bootstrap の `.btn` を `a` に付ける形は正当）

### 失敗事例（ありがちな NG 例）

<!-- 候補ベース。執筆前にコード例化と裏取りをする -->

- **NG: `div` / `span` + クリックイベントの「なんちゃってボタン」**
  - 対応する要件: 2.1.1、4.1.2
  - 何が起きるか: フォーカス不能・キーボード発火なし・「ボタン」と読まれない。修復には `tabindex` / `role` / keydown 処理の 3 点セットが必要で、`button` に書き換えるほうが早い
- **NG: `a href="#"` + `onclick` でその場の動作をさせる**
  - 対応する要件: 4.1.2（役割の嘘）
  - 何が起きるか: 「リンク」と読まれるのに移動しない。`#` により URL が汚れ、ページ先頭にスクロールする副作用も
- **NG: フォーム内の開閉ボタンに `type` を書かず、押すと送信される**
  - 対応する要件: 3.2.5 の精神（予測しない動作）
  - 何が起きるか: アコーディオンを開こうとしたら入力途中のフォームが送信される。過去調査が全章で繰り返し警告していた事故
- **NG: アイコンだけで名前のないボタン**
  - 対応する要件: 4.1.2、1.1.1
  - 何が起きるか: 「ボタン」としか読まれない。ページ内に「ボタン、ボタン、ボタン」が並ぶ
- **NG: `outline: none` でフォーカスリングを消す**
  - 対応する要件: 2.4.7
  - 何が起きるか: キーボードユーザーが現在位置を見失う。アコーディオン章の失敗例と共通
- **NG: 視覚ラベル「検索」に `aria-label="送信"` を付ける**
  - 対応する要件: 2.5.3 ラベルを含む名前
  - 何が起きるか: 音声操作で「検索をクリック」と言っても反応しない

### 新しいブラウザ機能

- **`command` / `commandfor` 属性**（Baseline Newly available、2025 年 12 月）: ボタンにダイアログ・popover の制御を宣言的に持たせる Invoker Commands。詳細はダイアログ章に記載。「ボタンがプラットフォーム機能のリモコンになっていく」方向性として本章でも一言触れる価値あり

### フォールバック・不採用案

#### フォールバック: とにかく `button` / `a` に寄せる

- ボタンには実装上の難所がそもそもない。「フォールバックを考える状況＝ネイティブ要素を使っていない状況」なので、修正方針は常に「実体を `button` / `a` に置き換える」

#### 不採用: `a role="button"` や `div role="button"` での自作

**最大の問題: `Space` キー発火・`Enter` の挙動・フォーカス可能性を JS で再実装する必要があり、どれか 1 つは必ず漏れる。**

**その他の問題:**

- フォーム統合（`type="submit"`・暗黙の送信）も失われる
- 見た目の都合は CSS（`appearance: none` + 任意のスタイル）で完全に解決できるため、自作の動機自体が存在しない
