# カルーセル（スライダー）UI コンポーネント — 調査結果まとめ

## 1. コンポーネントの概要（What & Why）

### 定義・解決する問題

カルーセルは、複数のコンテンツ（スライド）を同じ領域内で順に切り替えて表示する UI パターン。限られた領域（特にファーストビュー）に複数の訴求を詰め込みたいときに使われる。

APG の定義する構成要素（→ 参考記事 #1）:

- **スライド**: コンテンツを保持する単位
- **前へ／次へボタン**: スライドの切り替え
- **回転コントロール（rotation control）**: 自動回転の開始・停止（自動回転がある場合は必須）
- **スライドピッカー**: 特定のスライドへ直接移動するコントロール（ドット型が典型）

### そもそも使うべきかの判断

カルーセルは本書で扱うコンポーネントの中でも**「そもそも使うべきか」の証拠がもっとも豊富に揃っている** UI。使用判断の材料を厚めに書ける。

- **クリック率の統計（Erik Runyon、Notre Dame 大学のトラッキング調査。→ 参考記事 #20）**:
  - 手動カルーセルをクリックした訪問者は約 1%。そのうち **89% が 1 枚目のスライド**のクリック
  - 自動回転ありのサイトでは約 8.8% と多少ましだが、それでも 1 枚目 40% → 最後 11% と急減する
  - つまり「2 枚目以降にも訴求を置ける」というカルーセルの建前は、データ上ほぼ機能していない
- **自動回転の問題**:
  - 読み終わる前にスライドが変わる（読む速度は人によって大きく違う。ロービジョン・認知障害・非母語話者には特に深刻）
  - 操作しようとした瞬間に切り替わり、誤クリックを誘発する（バナー誤タップ問題）
  - 前庭障害のあるユーザーには、停止ボタンを探している間にも動き続けるアニメーション自体が害になる（Heydon Pickering。→ 参考記事 #6）
- Heydon Pickering の立場: **「複数コンテンツを順に見せる」という概念自体は悪くない。問題は自動回転と、非表示コンテンツの扱いという実装特性にある**（→ 参考記事 #6）
- 代替案: 静的ヒーロー（1 枚に絞る）、コンテンツグリッド（全部並べて自分で選ばせる）、ネイティブ横スクロールのリスト
- カルーセルが向くケース: 画像ギャラリーなど、**ユーザー自身が「順に見たい」動機を持つ並列コンテンツ**。ビジネス都合で情報を押し込む用途には向かない

### ネイティブ HTML 要素の有無

- **カルーセルに相当するネイティブ HTML 要素はない** → ARIA + JS が本筋
- ただし「スクロール型」カルーセルは `overflow-x` + CSS scroll snap でネイティブのスクロール機構に乗せられる。スワイプ・キーボードスクロール・慣性がブラウザ標準で手に入るため、**JS の役割をボタンと通知だけに減らせる**
- さらに CSS Overflow 5 の **CSS Carousels**（`::scroll-button()` / `::scroll-marker`）が Chrome 135 で出荷され、ボタン・ドットも CSS だけで生成できるようになりつつある。ただしアクセシビリティ上の未解決問題がある（→ 層 3「新しいブラウザ機能」）

### 類似コンポーネントとの使い分け

| 観点 | カルーセル | タブ | 横スクロールリスト |
|------|------------|------|---------------------|
| **コンテンツの性質** | 並列（順に見る動機がある） | 並列（明確なグループ分け） | 並列（一覧から選ぶ） |
| **非表示部分の存在** | 伝わりにくい（チラ見せ・ドットで補う） | タブラベルで常に見える | スクロールバー・見切れで伝わる |
| **自動切り替え** | ありがち（＝問題の温床） | なし | なし |
| **ネイティブ実装** | なし | なし | `overflow-x` + scroll snap でほぼ完結 |
| **ARIA** | `aria-roledescription="carousel"` | `tablist` / `tab` / `tabpanel` | 不要（リスト＋スクロール） |

- **ドット型ピッカーをタブとして実装するバリエーション**（APG の tabbed carousel）があり、その場合の要件はタブ章とほぼ同じになる（→ 層 3「設計判断ポイント」）
- 迷ったら横スクロールリストに落とすのが安全（ネイティブ機構に乗る分、壊しにくい）

## 2. アクセシブルであるためには（要件・規範）

### WCAG 2.2 該当基準の洗い出し

<!-- △ = 該当するか微妙だが念のため入れておく。詳細な要件・確認方法はチェック項目案側 -->

- **達成基準 2.2.2 一時停止、停止、非表示（レベル A）** — カルーセルの中核基準。自動的に切り替わり 5 秒以上続くコンテンツには、一時停止・停止・非表示の手段が必要
- **達成基準 2.1.1 キーボード（レベル A）** — 前後ボタン・ピッカーの操作、全スライドへの到達がキーボードで可能
- **達成基準 4.1.2 名前・役割・値（レベル A）** — スライドの名前（「3 / 10」等）、前後ボタン・ドットのアクセシブルな名前
- **達成基準 1.3.1 情報及び関係性（レベル A）** — カルーセルという構造（`aria-roledescription`）とスライドのグループ関係
- **達成基準 2.4.3 フォーカス順序（レベル A）** — 非表示スライド内のリンクにフォーカスが飛ばない
- **達成基準 2.5.1 ポインタのジェスチャ（レベル A）** — スワイプ（パスベースのジェスチャ）に、単一ポインタで操作できる代替（ボタン）がある
- **達成基準 2.5.7 ドラッグ movements（レベル AA）** ※WCAG 2.2 新規 — ドラッグ操作に、ドラッグしない代替（ボタン）がある
- **達成基準 1.1.1 非テキストコンテンツ（レベル A）** — 画像スライドの代替テキスト
- **達成基準 1.4.1 色の使用（レベル A）** — 現在位置のドット（カレント表示）を色だけで区別しない（塗りつぶし／サイズ／形状の変化を併用）
- **達成基準 1.4.11 非テキストのコントラスト（レベル AA）** — 前後ボタン・ドットが背景画像の上でも 3:1 以上のコントラストで見える
- **達成基準 1.4.13 ホバー又はフォーカスで表示されるコンテンツ（レベル AA）** — △ ホバーでコントロールを出す実装の場合のみ
- **達成基準 2.3.3 インタラクションによるアニメーション（レベル AAA）** — スライドのアニメーションを無効化できる
- △ **達成基準 3.2.5 要求による変化（レベル AAA）** — 自動回転はユーザーの要求によらないコンテンツ変化
- △ **達成基準 2.4.7 フォーカスの可視化（レベル AA）** — コントロール類のフォーカスリング
- △ **達成基準 1.4.4 文字サイズの変更 ／ 1.4.12 テキストの間隔 ／ 1.4.10 リフロー（いずれもレベル AA)** — 拡大・狭い画面でもスライド内テキストが読める
- △ **達成基準 2.5.8 ターゲットのサイズ（最低限）（レベル AA）** — ドットが小さくなりがち

### キーボード操作仕様（APG）

| キー | 動作 |
|------|------|
| `Tab` / `Shift + Tab` | ページの通常の Tab 順に従ってコントロール間を移動（カルーセル固有のキーはない） |
| `Enter` / `Space` | フォーカス中のボタン（前後・回転・ピッカー）を実行 |

- タブと違い**矢印キーの独自実装は不要**（tabbed carousel バリエーションを除く）
- APG の重要な指示:
  - **回転コントロールをカルーセル内の Tab 順の最初に置く**（動きを止める手段に最初に到達できるように）
  - 前後ボタンの操作で**フォーカスを移動させない**（連打で送れるように）
  - **キーボードフォーカスがカルーセルに入ったら自動回転を止め、ユーザーの明示的な操作なしに再開しない**
  - マウスホバー中も自動回転を止める（1.4.13 の Hoverable と同型の発想）

### ARIA ロールと属性（APG）

| ロール | 付与する要素 | 説明 |
|--------|--------------|------|
| `region`（`section` 要素） | カルーセル全体のコンテナ | ランドマークとして発見可能にする |
| `group` | 各スライド | スライドのまとまりを示す |

| 属性 | 付与先 | 値・説明 |
|------|--------|----------|
| `aria-roledescription="carousel"` | コンテナ | 読み上げを「リージョン」から「カルーセル」に変える |
| `aria-label` / `aria-labelledby` | コンテナ | カルーセル全体のラベル（例:「おすすめ記事」） |
| `aria-roledescription="slide"` | 各スライド | 読み上げを「グループ」から「スライド」に変える |
| `aria-label` | 各スライド | 固有名がなければ「3 / 10」形式の位置情報（アクセシブル名に位置情報を使ってよい例外的パターン） |
| `aria-live` | スライドコンテナ | **自動回転中は `off`、停止中は `polite`** に切り替える |
| `aria-label` | 前後ボタン・回転コントロール | 「次のスライド」「自動再生を停止」等 |

補足:

- `aria-roledescription` の値は**ページの言語に合わせて翻訳する**（仕様上ローカライズが想定されている属性。英語のまま "carousel" と読ませない）
- 非表示スライドは `aria-hidden="true"` ＋フォーカス不能化（または `inert`）で読み上げ・フォーカスの両方から隠す。Heydon は「不可視のコンテンツがフォーカス可能であってはならない」を大原則としている（→ 参考記事 #6）

### WCAG 外のユーザビリティ要件

- **非表示スライドの存在が視覚的に伝わる**: 次のスライドの端をチラ見せする、ドットで枚数を示す等。「1 枚目しかクリックされない」問題への実務的対策
- **ドットの操作性**: ドットは小さく、タップしにくい。進捗表示（読み取り専用）と割り切るか、操作対象にするなら十分なターゲットサイズを確保する
- **`prefers-reduced-motion` でスライドアニメーションを無効化**: 特に自動回転・スワイプアニメーション
  - ライブラリ任せにするときは**何が無効化されるのかを確認する**。Splide は `prefers-reduced-motion: reduce` を検知するとスライドが瞬時に切り替わるが、無効化されるのは CSS transition のみ。独自の演出を足すなら、CSS transition の範囲で実装しておくとこの仕組みに乗れる（過去の社内フレームワーク調査での知見）
- **遅延読み込みとレイアウト**: 画像スライドの lazy loading（Heydon は IntersectionObserver 方式を紹介）。高さを固定してレイアウトシフトを防ぐ
- **JS 初期化前のレイアウトシフト**: カルーセルはライブラリの JS が動くまでレイアウトが確定しないことが多く、CLS の常習犯。スライドの寸法を CSS で明示する（Splide なら `autoWidth` + CSS でサイズ指定）、`img` に `width` / `height` を付ける等で、JS 到着前から高さを確保する
- **ライブラリのラベルの日本語化**: Swiper 等は `aria-label` がデフォルト英語（"Next slide" 等）。日本語サイトでは日本語に設定し直す（→ 参考記事 #12）

### チェック項目案（記事の単位に束ね直す）

#### 自動再生をやめる。使うなら止められるようにする【本章固有】

- 該当基準: 2.2.2 一時停止、停止、非表示（2.3.3・3.2.5〔AAA〕もここに吸収）
- 要件: 第一の推奨は**自動回転をデフォルトで有効にしない**こと。使う場合は（1）停止ボタンを Tab 順の最初に置く、（2）ホバー・フォーカスで停止する、（3）フォーカスが入ったら明示的な再開操作まで回転を再開しない、（4）`prefers-reduced-motion` では最初から回転しない
- 確認方法: 停止ボタンがあるか。`Tab` でカルーセルに入った瞬間に回転が止まるか。ホバー中に止まるか
- 補足: クリック率の統計（1 枚目 89%）も「自動回転で解決しない」根拠として使える

#### キーボードだけですべてのスライドを見られるようにする【本章固有】

- 該当基準: 2.1.1 キーボード、2.4.3 フォーカス順序
- 要件: 前後ボタン・ピッカーがフォーカス可能で `Enter` / `Space` で動く。ボタン操作でフォーカスが失われない。非表示スライド内のリンクは `tabindex="-1"` または `inert` で Tab 順から除外
- 確認方法: マウスなしで全スライドの表示とスライド内リンクの操作ができるか。`Tab` を押し続けたとき、見えていないスライドのリンクにフォーカスが吸い込まれないか

#### スワイプ・ドラッグ以外でも操作できるようにする【本章固有】

- 該当基準: 2.5.1 ポインタのジェスチャ、2.5.7 ドラッグ movements
- 要件: スワイプ（パスベースジェスチャ／ドラッグ）だけに依存せず、単一タップで押せる前後ボタンを常に提供する
- 確認方法: スワイプを使わずに、ボタンのクリック／タップだけで全スライドへ移動できるか
- 補足: モバイルでボタンを非表示にするデザインが NG になる根拠。WCAG 2.2 の 2.5.7 で AA 要件に格上げされた点は記事で強調する価値がある

#### カルーセルであること・現在位置がスクリーンリーダーに伝わるようにする【本章固有】

- 該当基準: 4.1.2 名前・役割・値、1.3.1 情報及び関係性
- 要件: コンテナに `role="region"`（`section`）+ `aria-roledescription="carousel"` + ラベル。各スライドに `role="group"` + `aria-roledescription="slide"` + 「n / N」のラベル。スライド切り替えは `aria-live`（停止中 `polite`）で通知
- 確認方法: スクリーンリーダーで「カルーセル」「スライド、3 / 10」と読まれるか。ボタンでスライドを送ったとき新しいスライドが通知されるか。自動回転中は通知が黙るか（`aria-live="off"`）

#### コントロールが画像の上でも見え、現在位置が色以外でもわかるようにする【本章固有】

- 該当基準: 1.4.11 非テキストのコントラスト、1.4.1 色の使用（2.4.7 フォーカスの可視化も関連）
- 要件: 前後ボタン・ドットは、どんなスライド画像の上でも隣接色と 3:1 以上。写真任せにせず、半透明の座布団や縁取りを付ける。現在位置のドットは色の違いだけでなく、塗りつぶし・サイズ・形状の変化でも区別できるようにする（タブ章「選択中のタブが色以外でもわかる」項と同型の観点）
- 確認方法: もっとも明るい／暗いスライドの上でコントラスト比を計測する。グレースケール表示で現在位置のドットが判別できるか

#### 文字の拡大・行間の変更・画面幅の縮小でも使えるようにする【他章共通】

- 流用元: アコーディオン章の同名項
- 該当基準: 1.4.4 文字サイズの変更、1.4.12 テキストの間隔、1.4.10 リフロー
- 要件（カルーセル固有の観点）: スライド内テキストの拡大時にあふれないか。テキストを画像に焼き込まない（焼き込むと拡大・翻訳・リフローすべてに効かない）
- 確認方法: ズーム 200%・画面幅 320px でスライドの文字が読めるか

#### 見えていないスライドの存在が視覚的に伝わるようにする【本章固有】【ユーザビリティ】

- 該当基準: なし（WCAG 外）
- 要件: 次スライドの端をチラ見せする、「3 / 10」のカウンタやドットを表示する等で、続きがあることを伝える
- 確認方法: 初見のユーザーが「これはカルーセルで、続きがある」と気づけるか

#### 見送り（チェック項目にしない基準）

- **1.1.1 非テキストコンテンツ** — スライドが画像の場合の alt の話であり、カルーセル固有の考慮が薄い。実装例の中で軽く触れる
- **2.4.7 フォーカスの可視化** — 他章（アコーディオン）で扱い済み。「コントロールが画像の上でも見える」項の確認方法に吸収
- **2.5.8 ターゲットのサイズ** — ドットのサイズの話としてユーザビリティ項に吸収（タブ章と同じ扱い）
- **1.4.13 ホバー又はフォーカスで表示されるコンテンツ** — ホバーでコントロールを出す実装をそもそも実装例で採らないため扱わない（採る場合はツールチップ章参照、と流す）

## 3. 具体事例（Evidence）

### 実装事例（デザインシステム・ライブラリ）

| 項目 | W3C APG | Splide | Swiper | Embla | Inclusive Components |
|------|---------|--------|--------|-------|-----------------------|
| **ロール構成** | `region` + `group` + `aria-roledescription` | APG 準拠（`aria-roledescription` 等を自動付与） | `role="list"` / `"listitem"`（APG 非準拠との批判あり） | 素の DOM（自前実装） | `<ul>` + `role="region"` + ラベル |
| **スライド変更の通知** | `aria-live`（停止中 polite） | ✅ 自動。autoplay 中はライブリージョンを無効化 | ライブリージョンはあるが通知テキストが不十分との指摘 | プラグインで対応（`setupLiveRegion`） | 通知なし（スクロール型のため） |
| **非表示スライドの扱い** | `aria-hidden` | ✅ `aria-hidden` 自動切り替え + フォーカス除外 | デフォルトでは隠さない | 自前 | `tabindex="-1"` を IntersectionObserver で動的付与 |
| **ドット（ピッカー）** | ボタン群 or タブ | アクティブ以外 `tabindex="-1"`（roving 方式） | あり（ラベルは英語デフォルト） | 自前 | 採用せず（前後ボタンのみ） |
| **アクセシビリティの位置づけ** | 基準 | 設計目標として明記 | opt-in の A11y モジュール | 意図的にミニマル（プラグイン方式） | スクラッチ実装の教材 |

- **Splide が「アクセシビリティ第一」を明確に掲げており、ライブラリ選定の推奨候補**。autoplay 開始でライブリージョンを止め、停止で戻す挙動まで APG に忠実（→ 参考記事 #10, #13）
- Swiper は普及率最大だが、デフォルトの ARIA が APG とずれている（`list`/`listitem` ロール、英語ラベル）。使うなら手直し前提（→ 参考記事 #11, #12）

#### 設計判断ポイント（実装が割れている論点）

- **切り替え型 vs スクロール型** — 本章の構成を決める最大の分岐
  | | 切り替え型（JS でスライド差し替え） | スクロール型（`overflow` + scroll snap） |
  |---|---|---|
  | スワイプ | JS で実装 | ブラウザ標準 |
  | キーボード | ボタン必須 | スクロール自体は矢印キーで可能（`tabindex="0"` + ラベルが必要） |
  | 非表示スライド | `aria-hidden` / `inert` の管理が必要 | すべて「見えている」扱いで管理不要（画面外なだけ） |
  | 通知 | `aria-live` が必要 | 不要（ユーザー主導のスクロールのため） |
  | 自動回転 | 実装されがち | なじまない（＝自動回転を封じる構成でもある）
- **ドットの実装方式** — APG に 3 バリエーションある: ドットなし（basic）／ボタン群（grouped）／タブ型（tabbed、`tablist` + `tabpanel`）。タブ型はタブ章の要件がそのまま乗ってくるため実装コストが高い。grouped（ボタン群 + roving tabindex）が中庸
- **無限ループの是非** — 端で止める（Heydon・Inclusive Components）か、クローンでループする（Swiper 等の `loop` オプション）か。クローン方式は SR・フォーカスに複製が露出する事故が起きやすい（→ 不採用案）
- **自動回転のデフォルト** — APG は「あってよいが厳格な条件付き」、Heydon は「ユーザー操作起点のみにすべき」、W3C チュートリアルは「一時停止手段必須」。記事は「デフォルト無効」を推す立場が採りやすい

### 失敗事例（ありがちな NG 例）

<!-- 候補ベース。執筆前にコード例化と裏取りをする -->

- **NG: 自動回転が止められない（停止ボタンがない）**
  - 対応する要件: 2.2.2 一時停止、停止、非表示
  - 何が起きるか: 読み終わる前にコンテンツが消える。前庭障害のユーザーには動き自体が害
- **NG: スワイプでしか操作できない（モバイルで前後ボタンを消す）**
  - 対応する要件: 2.5.1 ポインタのジェスチャ、2.5.7 ドラッグ movements
  - 何が起きるか: スワイプ動作が難しいユーザー（運動機能障害、スイッチコントロール利用者）が操作できない
- **NG: 非表示スライドのリンクにフォーカスが飛ぶ**
  - 対応する要件: 2.4.3 フォーカス順序
  - 何が起きるか: `Tab` を押すとフォーカスが画面から消える。キーボードユーザーは現在地を見失う
- **NG: 無限ループのためのクローンスライドがスクリーンリーダーに読まれる**
  - 対応する要件: 1.3.1 情報及び関係性、4.1.2
  - 何が起きるか: 「10 枚中 14 枚目」のような矛盾した読み上げ、同じコンテンツの重複読み上げ。クローン内のフォーム要素の `id` 重複も起きる
  - 出典・実例: Swiper `loop` オプション、slick 等のクローン方式
- **NG: ドット・前後ボタンに名前がない（アイコンのみ）**
  - 対応する要件: 4.1.2 名前・役割・値
  - 何が起きるか: 「ボタン」としか読まれず、何が起きるか予測できない。CSS Carousels の `::scroll-marker` にも同じ問題がある（→ 新しいブラウザ機能）
- **NG: 現在位置のドットが色の違いだけで表現されている**
  - 対応する要件: 1.4.1 色の使用
  - 何が起きるか: 色覚特性によっては、いま何枚目を見ているのか・全体の中のどこかが分からない
- **NG: ライブラリのデフォルトラベルが英語のまま**
  - 対応する要件: 4.1.2（実務上は 3.1.2 その他の言語との関連も）
  - 何が起きるか: 日本語ページで「Next slide」と英語で読み上げられる
  - 出典・実例: Swiper のデフォルト（→ 参考記事 #12）
- **NG: 自動回転中も `aria-live="polite"` のまま**
  - 対応する要件: APG の aria-live 切り替え指示
  - 何が起きるか: スクリーンリーダーが数秒ごとに新しいスライドを読み上げ続け、他の読み上げを妨げる
- **NG: 訴求テキストを画像に焼き込む**
  - 対応する要件: 1.4.4 文字サイズの変更、1.4.5 文字画像、1.4.10 リフロー
  - 何が起きるか: 拡大してもぼやけるだけで読めない。翻訳もされない

### 新しいブラウザ機能: CSS Carousels（`::scroll-button()` / `::scroll-marker`、Chrome 135〜）

CSS Overflow 5 の機能群。スクロール型カルーセルの**前後ボタンとドットを CSS 疑似要素だけで生成**できる。

```css
.carousel {
  overflow-x: auto;
  scroll-snap-type: x mandatory;
  scroll-marker-group: after;
}
.carousel::scroll-button(right) { content: "→" / "次へ"; }
.carousel::scroll-button(left) { content: "←" / "前へ"; }
.carousel > li::scroll-marker { content: ""; }
```

- **何が自動になるか**: ブラウザがボタン・マーカーを適切なロール・Tab 順・状態（端に達したら disabled）付きで生成する。スクロール自体はネイティブなのでスワイプ・キーボードも標準対応
- **対応状況**: Chrome 135（2025 年 4 月）/ Edge 135。Firefox・Safari 未対応（2026 年 7 月時点）
- **未解決のアクセシビリティ問題**（→ 参考記事 #17, #18）:
  - `::scroll-marker` に**アクセシブルな名前を与える手段がない**ケースがあり、そのまま使うと 4.1.2 違反になり得る（`content` の代替テキスト構文で回避できる場合もある）
  - disabled になった `::scroll-button` の状態がスクリーンリーダーに正しく伝わらない既知バグ
  - a11y コミュニティから「CSS から UI 要素を生成すること自体への懸念」が表明されており、仕様側で改善が続いている
- **チャプターでの扱い方**: アコーディオンの `interpolate-size` 等と同じ「新しい手段」枠で紹介しつつ、**ツールチップ章の `interestfor` よりさらに実験的**という温度感。本筋はスクロール型（scroll snap + HTML ボタン）または切り替え型の JS 実装

### フォールバック・不採用案

#### フォールバック: カルーセルを使わずに済ませる選択肢

1. **静的ヒーロー（1 枚に絞る）**: クリック統計が示すとおり、実質 1 枚目しか見られていない。最初から 1 枚に絞る判断は数字で正当化できる
2. **コンテンツグリッド（全部並べる）**: 隠さなければ通知もフォーカス管理も不要。タブ章・アコーディオン章のフォールバックと同型の「隠さない」解
3. **ネイティブ横スクロールリスト + scroll snap**: スワイプ・キーボード・慣性がブラウザ標準。JS はボタン補助のみ。Heydon の実装（→ 参考記事 #6）がこの路線の教材になる

#### 不採用: クローンによる無限ループ

**最大の問題: DOM 上にスライドの複製ができ、スクリーンリーダー・フォーカス・ページ内検索のすべてに複製が露出する。** 「n / N」の位置ラベルとも矛盾する。

**その他の問題:**

- クローン内のフォーム要素・`id` の重複が別のバグを生む
- ループで「端」がなくなると、キーボードユーザーが一巡したことに気づけない
- どうしてもループ感が欲しい場合も、端で逆送りにする・先頭へ戻るボタンを付ける等で足りる

#### 不採用: ホバーでのみ前後ボタンを表示するデザイン

**最大の問題: タッチデバイスとキーボードユーザーにボタンの存在が伝わらない（2.5.7・発見性の両面）。**

**その他の問題:**

- 1.4.13（ホバーで表示されるコンテンツ）の要件も追加で背負い込むことになる
- ボタンを常時表示して薄い座布団を敷くだけで回避できる
