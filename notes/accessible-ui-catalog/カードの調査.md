## 1. コンポーネントの概要（What & Why）

### 定義・解決する問題

カードは、画像（サムネイル）・見出し（タイトル）・説明文・タグなどをひとまとまりにした、一覧の 1 項目となる UI。記事一覧・商品一覧などで最も使用頻度の高いパターンのひとつ。

この章の本質的な問い: **「カード全体をクリックしたい」と「リンクはテキストであるべき」の衝突をどう解くか。**

- ユーザーはカードのどこを押しても遷移することを期待する（小さいタイトルだけがリンクだと押しにくい）
- 一方、カード全体を `a` で包むと、スクリーンリーダーのリンク名がカードの全文（タイトル + 説明 + タグ + 日付…）になり、リンク一覧・読み上げが破綻する（Heydon Pickering が「冗長な告知」問題として整理。→ 参考記事 #5）
- さらにカード内には第 2 のリンク（タグ・著者）が同居しがちで、`a` の入れ子は HTML として不正

### そもそも使うべきかの判断

- カード自体は無害なレイアウトパターンで、「使うべきか」の論点は薄い。判断が要るのは:
  - **カード全体をクリック可能にするか**（しない＝タイトルだけリンク、が最も単純で堅牢。全体クリックは期待に応える分、実装責任が増える）
  - **情報を詰め込みすぎないか**（リンク名・読み上げ・視覚的なスキャンのすべてが悪化する。カードは要約であり、詳細は遷移先に置く）
- 画像だけのカード（テキストなし）は、リンク名を画像の `alt` だけが支えることになる。テキストのあるカードが常に安全

### ネイティブ HTML 要素の有無

- カード専用要素はないが、**`article`（自己完結した項目）+ 見出し + `a` + `ul`（一覧側）の素の HTML で構造は完結する**（過去調査も `article` の採用を 1.3.1 の根拠付きで明記していた）
- 難所は構造ではなく「クリック領域の拡大」だけで、これも CSS（擬似要素）で解ける。JS は補助にすぎない

### 類似・関連パターンとの整理

| 観点 | カード（タイトルリンク + 領域拡大） | カード全体を `a` で包む | リストの行（テキストリンクのみ） |
|------|--------------------------------------|--------------------------|-----------------------------------|
| **リンク名** | タイトルだけ（明快） | カード全文（冗長） | タイトルだけ |
| **カード内の別リンク** | 共存できる | 入れ子になり不正 | 共存できる |
| **テキスト選択** | 工夫すれば可能 | ほぼ不可能 | 可能 |
| **実装コスト** | 中（擬似要素） | 低 | 最低 |

## 2. アクセシブルであるためには（要件・規範）

### WCAG 2.2 該当基準の洗い出し

<!-- △ = 該当するか微妙だが念のため入れておく。詳細な要件・確認方法はチェック項目案側 -->

- **達成基準 2.4.4 リンクの目的（コンテキスト内）（レベル A）** — リンク名がタイトルとして意味を成す（全文リンク・「詳しくはこちら」の回避）
- **達成基準 1.3.2 意味のある順序（レベル A）** — DOM 上の順序が理解できる順序になっている。過去調査は「タイトルの前に他のテキスト要素を置かない（置くなら見出しに含める）」を明記していた
- **達成基準 1.1.1 非テキストコンテンツ（レベル A）** — サムネイルの `alt` の判断。過去調査の整理: タイトルが代替になるため**装飾扱いで `alt=""` が基本**、画像のみのカードでは `alt` 必須
- **達成基準 1.3.1 情報及び関係性（レベル A）** — `article` による項目の自己完結、一覧側の `ul` / `li`、見出しレベル
- **達成基準 2.1.1 キーボード（レベル A）** — リンクとして通常どおり操作できる（過去調査の観点）
- **達成基準 2.3.3 インタラクションによるアニメーション（レベル AAA）** — ホバー時の拡大・浮き上がりアニメーションを `prefers-reduced-motion` で無効化（過去調査の観点）
- △ **達成基準 2.5.8 ターゲットのサイズ（最低限）（レベル AA）** — タグ等の小さな副リンク（Heydon は `padding` での当たり判定拡大を推奨）
- △ **達成基準 2.4.7 フォーカスの可視化（レベル AA）** — 擬似要素でクリック領域を広げた場合、フォーカスリングをカード全体に出すか・タイトルに出すか
- △ **達成基準 1.4.4 ／ 1.4.10（レベル AA）** — カードリストの列数変化・狭幅ではみ出さない（過去の card-list 調査の観点をここに吸収）

### キーボード操作仕様

通常のリンク操作のみ（`Tab` / `Enter`）。固有仕様はないが、**Tab ストップの数**が設計の焦点になる:

- カード 1 枚あたりのフォーカス可能要素は最小限に（タイトルリンク + 本当に必要な副リンクだけ）
- カード全体 + タイトル + 画像 + 「続きを読む」がそれぞれリンクだと、1 枚で 4 ストップになり、一覧全体では膨大になる（Heydon「タブストップは必要な場合のみ」）

### マークアップの定石

| 手段 | 用途 | 説明 |
|------|------|------|
| `article` | カード 1 枚のコンテナ | 自己完結した項目であることを伝える（過去調査の採用理由） |
| `h2`〜`h6` > `a` | タイトルリンク | 見出しの中にリンクを置く（Heydon 推奨）。見出しジャンプでリンク名が得られる。見出しにするかは文脈次第（過去調査は「状況に応じて」と整理） |
| `a` の擬似要素（`::after` 等）を `position: absolute` でカード全体に | クリック領域の拡大 | いわゆる stretched-link。カード側に `position: relative` |
| 副リンク（タグ等）に `position: relative` + `z-index` | 擬似要素の上に浮かせる | 過去実装・Heydon ともに同じ解法。`padding` で当たり判定も拡大 |
| `ul` / `li` | カードの一覧側 | 「n 項目のリスト」が伝わる |
| `img` に `width` / `height` | レイアウトシフト防止 | 過去実装は全カードで明示していた（カルーセル章の CLS 対策と同根） |

### WCAG 外のユーザビリティ要件

- **テキスト選択との両立**: 擬似要素方式はカード上のテキスト選択を「リンクのドラッグ」にしてしまう。対策は（1）テキスト部分だけ `position: relative` で浮かせる、（2）JS で「mousedown から mouseup まで 200ms 以上ならクリック扱いしない」冗長クリック方式（Heydon）。過去実装は擬似要素 + JS ホバークラスの構成だった
- **DOM 順序と視覚順序**: 見出しジャンプで移動するスクリーンリーダーユーザーは、見出しより DOM 上で前にある画像を見落とす。**DOM はテキスト（見出し）先行、視覚は CSS の `order` で画像を上に**が Heydon の解法（フォーカス可能要素を並べ替えない限り 2.4.3 の問題は生じない）
- **カードリストのレイアウト**（過去の card-list / container 調査から吸収）:
  - 画面幅を変えたときの列数変化を確認する。極端に狭い幅でカードがはみ出さない（`grid` の `minmax(min(100%, Npx), 1fr)` 等）
  - 極端に広い画面でコンテンツ幅を制限する。1 行の文字数が長すぎると読みにくい（達成基準 1.4.8〔AAA〕の「80 字（全角 40 字）」が参考値になる、というのが過去 container 調査の整理）
- **ホバーフィードバック**: タイトルだけがリンクでも、カード全体にホバースタイルを出すと「全体が押せる」ことが伝わる。過去実装は JS でホバークラスを付与していたが、**現在は `.card:has(.card__link:hover)` で CSS だけで書ける**（`:has()` 全ブラウザ対応済み。過去実装の JS が不要になった例）

### チェック項目案（記事の単位に束ね直す）

#### リンクの名前がタイトルになるようにする【本章固有】

- 該当基準: 2.4.4 リンクの目的、4.1.2
- 要件: `a` の中身はタイトルテキストのみ。カード全体を `a` で包まない。「詳しくはこちら」だけのリンクを作らない
- 確認方法: スクリーンリーダーのリンク一覧で、各カードがタイトル名で並ぶか

#### カード全体をクリックできるようにしつつ、読み上げを壊さないようにする【本章固有】

- 該当基準: 2.4.4（前項の帰結）、実務要件
- 要件: 擬似要素でクリック領域を拡大する（stretched-link）。副リンク（タグ等）は `position: relative` で浮かせて共存させる
- 確認方法: カードの余白クリックで遷移するか。タグをクリックしたときはタグ先に遷移するか。読み上げのリンク名はタイトルのままか

#### DOM の順序を「タイトル先行」にする【本章固有】

- 該当基準: 1.3.2 意味のある順序
- 要件: タイトル（見出し）を DOM の先頭側に置き、画像を視覚的に上へ出すのは CSS（`order`）で行う。タイトルの前に表示すべきテキスト（カテゴリラベル等）があるなら、見出しの中に含める（過去調査の指示）
- 確認方法: CSS を無効化した状態（または読み上げ順）で、タイトル → 説明の順に意味が通るか

#### サムネイルの alt を「タイトルとの重複」で判断する【本章固有】

- 該当基準: 1.1.1 非テキストコンテンツ
- 要件: タイトルテキストがあるカードでは `alt=""`（重複読み上げを避ける）。画像のみのカードでは内容を表す `alt` を必須にする（過去調査の整理そのまま）
- 確認方法: スクリーンリーダーでカードを読んだとき、同じ内容が 2 回読まれないか

#### ホバーアニメーションを無効にできるようにする【他章共通】

- 流用元: アコーディオン章「モーションアニメーションを無効にできる」項
- 該当基準: 2.3.3 インタラクションによるアニメーション
- 要件: 拡大・浮き上がり等の動きは `prefers-reduced-motion: reduce` で止める（色変化などの動かないフィードバックは残してよい）
- 確認方法: OS の「視覚効果を減らす」設定でホバーしても動かないか

#### カードリストが列数の変化・狭い画面でも崩れないようにする【他章共通】

- 流用元: アコーディオン章「文字の拡大・行間の変更・画面幅の縮小でも〜」項（+ 過去の card-list 調査）
- 該当基準: 1.4.10 リフロー、1.4.4
- 確認方法: 画面幅を連続的に変えて列数の切り替わりを確認。320px でカードがはみ出さないか。長いタイトルで崩れないか

#### 見送り（チェック項目にしない基準）

- **2.5.8 ターゲットのサイズ** — タグ等の副リンクの `padding` 拡大は実装例の中で示す（ページネーション章が主戦場）
- **2.4.7 フォーカスの可視化** — 「フォーカスリングをカード全体に出す」デザイン選択はビジュアルデザイン節で扱う
- **1.4.8 視覚的提示（AAA）** — コンテンツ幅・行長の話は参考値としてユーザビリティ節に一言（過去 container 調査の位置づけを踏襲）

## 3. 具体事例（Evidence）

### 実装手法の比較（Heydon Pickering の整理 + 過去実装）

| 手法 | 読み上げ | テキスト選択 | 副リンク共存 | 実装 |
|------|----------|--------------|--------------|------|
| **カード全体を `a` で包む** | ✖ 全文がリンク名になる | ✖ ドラッグが遷移になる | ✖ 入れ子で不正 | 最も簡単 |
| **擬似要素（stretched-link）** | ✅ タイトルのみ | △ 工夫が必要 | ✅ `position: relative` で浮かす | CSS のみ |
| **JS 冗長クリック（200ms 判定）** | ✅ タイトルのみ | ✅ 可能 | ✅ | JS が必要 |

- 過去の社内実装は**擬似要素方式**（+ JS ホバークラス）。Heydon の推奨と一致しており、記事の実装例の本筋もこれでよい。テキスト選択を重視するメディアサイト等では JS 冗長クリックを発展形として紹介
- Bootstrap の `.stretched-link` が擬似要素方式の普及名。「stretched-link」という語は検索性のために本文で出す価値がある

#### 設計判断ポイント（実装が割れている論点）

- **どの手法でクリック領域を広げるか** — 上表。「全体を `a`」だけは避け、擬似要素を基本に
- **タイトルを見出し（`h2`〜）にするか** — 一覧の構造次第（過去調査は「状況に応じて」）。見出しにすると見出しジャンプで一覧を高速に巡回できる。ページ全体の見出し階層と整合させる
- **画像を DOM で先に置くか後に置くか** — 視覚デザインは画像が上でも、DOM はテキスト先行 + `order`（Heydon）。ただし `order` の乱用は 1.3.2 / 2.4.3 の火種なので「フォーカス不能な画像に限る」と限定する
- **カード全体クリックをやめる選択肢** — タイトルリンクのみ + ホバーフィードバックで「押せる場所」を明確にする構成も、実装がゼロコストで堅牢。全体クリックが本当に要件かは確認する価値がある

### 失敗事例（ありがちな NG 例）

<!-- 候補ベース。執筆前にコード例化と裏取りをする -->

- **NG: カード全体を `a` で包み、リンク名が全文になる**
  - 対応する要件: 2.4.4
  - 何が起きるか: リンク一覧が「タイトル 説明文説明文… タグ タグ 2026 年 7 月 4 日」のような長文の羅列になる。読み上げも 1 リンクで数十秒かかる
- **NG: `a` の中に `a`（タグリンク）を入れて HTML が壊れる**
  - 対応する要件: 1.3.1（パーサーによる構造破壊）
  - 何が起きるか: ブラウザが入れ子を解消するため DOM が予測不能になり、クリック領域も読み上げも壊れる
- **NG: `div` + `onclick` のカード（リンクですらない）**
  - 対応する要件: 2.1.1、4.1.2
  - 何が起きるか: キーボード到達不能・「クリック可能」と伝わらない・新しいタブで開けない
- **NG: 画像が DOM 先頭で、見出しジャンプすると画像を通り過ぎる**
  - 対応する要件: 1.3.2
  - 何が起きるか: 見出し単位で流し読みするスクリーンリーダーユーザーに画像（や画像内の情報）が届かない
- **NG: サムネイルの `alt` にタイトルを重複して書く**
  - 対応する要件: 1.1.1（過剰な代替）
  - 何が起きるか: すべてのカードでタイトルが 2 回読まれ、一覧の読み上げが倍の長さになる
- **NG: ホバーで浮き上がるアニメーションが `prefers-reduced-motion` を無視**
  - 対応する要件: 2.3.3
  - 何が起きるか: 一覧をポインタが横切るだけで多数のカードが動き、前庭障害のユーザーに負担
- **NG: 狭い画面でカードが `min-width` を主張してはみ出す**
  - 対応する要件: 1.4.10 リフロー
  - 何が起きるか: 320px で横スクロールが発生する（過去 card-list 調査の「極端に狭いときの確認」の実害）

### 新しいブラウザ機能

- **`:has()` の全ブラウザ対応**により、「タイトルリンクのホバーでカード全体のスタイルを変える」が CSS だけで書ける（`.card:has(.card__link:hover)`）。過去実装の JS ホバークラス付与は不要になった（フォームの `label` 内包問題と同じく、`:has()` が過去の実装判断を無効化した例）

### フォールバック・不採用案

#### フォールバック: タイトルリンクのみ（領域拡大をやめる）

- クリック領域の拡大は「あると嬉しい」であって必須ではない。工数や検証体制がないなら、タイトルリンク + 明確なホバー表示だけでも要件はすべて満たせる

#### 不採用: カード全体を `a` で包む方式

**最大の問題: リンク名がカードの全文になり、スクリーンリーダーのリンク一覧・読み上げが実用にならない。**

**その他の問題:**

- カード内の副リンク（タグ・著者）と両立できない（入れ子の `a` は不正）
- テキスト選択がほぼ不可能になる
- 「実装が一番簡単」なだけに最も普及している形なので、失敗例の筆頭として丁寧に扱う
