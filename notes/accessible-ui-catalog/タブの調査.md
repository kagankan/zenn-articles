# タブ UI コンポーネント — 調査結果まとめ

## 1. コンポーネントの概要（What & Why）

### 定義・解決する問題

タブは、同じ領域内で複数のコンテンツパネルを切り替えて表示する UI パターン。常に 1 つのパネルだけを表示することで、限られた画面領域に並列なコンテンツを収められる。

### そもそも使うべきかの判断

- タブは**コンテンツを隠す UI**。選択中以外のパネルは見えないため、流し見するユーザーには非選択パネルの存在が伝わらない可能性がある
- タブで隠す必然性がないなら、全セクションを並べて表示するほうがユーザーにとって楽な場合もある（→ 層 3「フォールバック」の選択肢 2）
- 向いているのは**並列・同等で、相互に比較しなくてよいコンテンツ**（2〜6 セクション程度）。順序がある・長さが不均一なコンテンツはアコーディオンや通常の見出し構造のほうが適する
- NN/g「Tabs, Used Right」による使用判断のガイドライン（→ 参考記事 #20）:
  - **タブ間の比較が必要なコンテンツには使わない**。ユーザーがタブを往復して切り替えることになり、短期記憶に負荷がかかる
  - **明確なグループ分けがないなら使わない**。単一ページ＋見出し構成のほうが適切
  - **タブ数を増やしすぎない**。タブバーがスクロール／カルーセル化すると、隠れたタブの発見性が下がり操作コストが増える
  - **短いラベルで内容が予測できること**。非選択タブは中身が見えないので、ラベルの情報の匂い（information scent）だけが頼りになる
  - **デフォルトタブ以外は注目されにくい**。非デフォルトタブには補足的なコンテンツを入れ、重要な情報を隠さない
  - **ページ内タブとナビゲーションタブを混ぜない**。同じ見た目で「内容の切り替え」と「ページ遷移」が混在するとユーザーが混乱する
- タブ vs アコーディオンの使い分け（NN/g、→ 参考記事 #21）: タブは「少数の長いセクション」、アコーディオンは「多数の短いセクション」向き。モバイルではタブラベルがあふれやすく、アコーディオンが適する場面が多い
- **フォームをタブで分割しない**（Baymard のユーザーテスト、→ 参考記事 #22）: どのフィールドが送信されるのか（表示中のタブだけか、隠れたタブも含むのか）がユーザーにわからなくなる。相互排他の選択肢ならタブではなくラジオボタン等の標準フォーム要素を使う

### ネイティブ HTML 要素の有無

- **タブに相当するネイティブ HTML 要素は現時点で存在しない**（アコーディオンの `details`/`summary` のようなものがない）
  - → ARIA + JS の正しい実装が本筋になり、「正しく実装できない場合のフォールバック」（層 3）が特に重要になる
- CSS のみの実装（ラジオボタン `:checked`、`:target` 方式）はアクセシビリティ上の問題が多く、APG のタブパターンを満たせない
- Open UI コミュニティが `<panelset>` 等のネイティブ要素を検討中だが、まだ仕様策定段階

### 類似コンポーネント（アコーディオン）との使い分け

| 観点 | アコーディオン | タブ |
|------|------------|------|
| **ネイティブ要素** | `details`/`summary` で JS 不要 | なし。ARIA + JS が必須 |
| **キーボード操作** | ブラウザが自動提供 | 自前で実装（roving tabindex、矢印キー） |
| **ロール・状態** | `details`/`summary` が自動提供 | 手動で ARIA 設定 |
| **ページ内検索** | 閉じていてもヒット | `display: none` パネルはヒットしない |
| **複数パネルの同時表示** | 可能 | 不可（常に 1 つだけ） |
| **フォーカス管理** | 各 `summary` が独立 | タブリスト内で roving tabindex |

## 2. アクセシブルであるためには（要件・規範）

### WCAG 2.2 該当基準の洗い出し

<!-- △ = 該当するか微妙だが念のため入れておく。詳細な要件・確認方法はチェック項目案側 -->

- **達成基準 2.1.1 キーボード（レベル A）** — タブの選択・切り替え・タブリスト内の移動がすべてキーボードで可能（矢印キーでタブ間移動、Tab でパネルへ、Enter/Space で選択）
- **達成基準 2.4.7 フォーカスの可視化（レベル AA）** — 矢印キーでタブリスト内を移動するとき、どのタブにフォーカスがあるか見える
- **達成基準 4.1.2 名前・役割・値（レベル A）** — `role` 3 点セットの付与、`aria-selected` による選択状態の通知
- **達成基準 1.3.1 情報及び関係性（レベル A）** — タブとパネルの関連付けがプログラム的に伝わる（`aria-controls` / `aria-labelledby`）
- **達成基準 2.4.3 フォーカス順序（レベル A）** — アクティブタブ → パネルの論理的な順序。非選択タブは `tabindex="-1"` で Tab 順序から外す
- **達成基準 3.2.1 フォーカス時（レベル A）** — タブにフォーカスを当てただけでコンテキストの変化を起こさない（パネル切り替えはコンテキストの変化に当たらない＝自動アクティベーションの許容根拠）
- **達成基準 1.4.11 非テキストのコントラスト（レベル AA）** — 選択状態を示す視覚的変化（下線等）が隣接色と 3:1 以上
- **達成基準 1.4.1 色の使用（レベル A）** — 選択中のタブを色だけで示さない
- **達成基準 2.3.3 インタラクションによるアニメーション（レベル AAA）** — 切り替えアニメーションを無効にできる
- **達成基準 1.4.4 文字サイズの変更 ／ 1.4.12 テキストの間隔 ／ 1.4.10 リフロー（いずれもレベル AA）** — 拡大 200%・行間 1.5・画面幅 320px でもラベルと中身が読める
- **達成基準 2.4.11 隠されないフォーカス（最低限）（レベル AA）** ※WCAG 2.2 新規 — フォーカスされたタブがスティッキーヘッダー等で隠れない
- **達成基準 2.1.2 キーボードトラップなし（レベル A）** — タブリスト・パネルからフォーカスが抜け出せる
- △ **達成基準 2.4.6 見出し及びラベル（レベル AA）** — タブラベルがパネル内容を適切に表している
- △ **達成基準 3.2.4 一貫した識別性（レベル AA）** — サイト内で同じ機能のタブには一貫したラベル
- △ **達成基準 2.5.8 ターゲットのサイズ（最低限）（レベル AA）** ※WCAG 2.2 新規 — 各タブの操作領域が 24×24 CSS ピクセル以上
- △ **達成基準 2.4.13 フォーカスの外観（レベル AAA）** — インジケータの太さ 2 CSS ピクセル以上・コントラスト比 3:1 以上

### キーボード操作仕様（APG）

| キー | 動作 |
|------|------|
| `Tab` | タブリストに入る（選択中タブにフォーカス）→ 次の `Tab` でパネルへ |
| `→` / `←` | 次/前のタブにフォーカス移動（末尾↔先頭ループ） |
| `↑` / `↓` | 縦タブの場合に前後移動 |
| `Enter` / `Space` | 手動アクティベーション時：フォーカス中のタブを選択 |
| `Home` / `End` | 最初/最後のタブにフォーカス（任意） |

※矢印キー移動時に「フォーカスと同時に切り替えるか（自動）／Enter で切り替えるか（手動）」は実装が割れている論点。→ 層 3「設計判断ポイント」

### ARIA ロールと属性（APG）

| ロール | 付与する要素 | 説明 |
|--------|------------|------|
| `tablist` | タブの並びを囲むコンテナ | タブのグループであることを伝える |
| `tab` | 各タブ要素 | `tablist` の中に配置する |
| `tabpanel` | 各タブに対応するコンテンツ領域 | タブに紐づくコンテンツであることを伝える |

| 属性 | 付与先 | 値・説明 |
|------|--------|----------|
| `aria-labelledby` / `aria-label` | `tablist` | タブリスト全体のラベル |
| `aria-selected="true"` / `"false"` | `tab` | 選択状態 |
| `aria-controls` | `tab` | 対応する `tabpanel` の `id` を参照 |
| `tabindex="0"` / `"-1"` | `tab` | 選択中は `0`、非選択は `-1`（roving tabindex） |
| `aria-labelledby` | `tabpanel` | 対応する `tab` の `id` を参照 |
| `tabindex="0"` | `tabpanel` | パネル内にフォーカス可能要素がない場合に付与 |
| `aria-orientation` | `tablist` | 縦タブなら `"vertical"`。水平なら省略可 |

補足（APG の推奨）:

- **タブパネルのフォーカス管理**: パネル内にフォーカス可能要素がない場合は `tabindex="0"` を付与（Tab キーでパネルに移動できるようにする）。一貫性のため全パネルに付けるのが安全
- **非表示パネルの扱い**: `hidden` 属性または `display: none` で非表示にする。`aria-hidden="true"` 単体は不適切（視覚的にも隠す必要がある）
- **`<button>` で実装する場合は `type="button"` を明示する**: `type` 属性のデフォルトは `submit` のため、フォーム内に置いたタブがフォーム送信を発火させてしまう

### WCAG 外のユーザビリティ要件

- **ページ内検索**: `display: none` の非選択パネルはページ内検索（`Ctrl` / `⌘` + `F`）にヒットしない。`hidden="until-found"` を使うと、非表示のパネルも検索対象になり、ヒットすると表示される（TAKLOG の記事が実装例。→ 参考記事 #6）
  - アコーディオン（`details`/`summary` で自動的に満たせる）と違い、タブでは意識して実装しないと満たせない

### チェック項目案（記事の単位に束ね直す）

<!-- 16 基準＋WCAG 外要件を、記事の「実装するときに気をつけること」の粒度に束ねたもの -->

#### キーボードだけでタブを切り替えられるようにする【他章共通】

- 流用元: アコーディオン章「キーボードだけで開閉できる」。ただしタブ固有の拡張（矢印キー移動・roving tabindex）が本項の中心になるため、文面の大部分は書き下ろしになる
- 該当基準: 2.1.1 キーボード、2.4.3 フォーカス順序、2.1.2 キーボードトラップなし
- 要件: `Tab` でタブリストに入ると選択中タブにフォーカスされ、矢印キーでタブ間を移動し、`Tab` でパネルへ抜けられる。非選択タブは `tabindex="-1"`（roving tabindex）。フォーカスが閉じ込められない
- 確認方法: マウスを使わず、`Tab` → 矢印キー →（手動アクティベーションなら `Enter` / `Space`）の操作ですべてのパネルに到達できるか。選択中タブで `Tab` を押すと、他のタブを飛ばしてパネルへ移動するか

#### フォーカスインジケータが見えるようにする【他章共通】

- 流用元: アコーディオン章「フォーカスインジケータが見える」
- 該当基準: 2.4.7 フォーカスの可視化（補足として 2.4.13〔AAA: 太さ・コントラスト〕と 2.4.11〔スティッキーヘッダー等で隠れない〕もここに吸収）
- 要件: 矢印キーでタブ間を移動しているとき、どのタブにフォーカスがあるか視覚的にわかる
- 確認方法: 矢印キーでタブ間を移動してフォーカスリングが見えるか。スティッキーヘッダーがあるページで隠れないか
- タブ固有の落とし穴: タブリストに `overflow: hidden`（横スクロールタブや装飾のために付けがち）を指定していると、タブ外周に描かれるフォーカスリングが切り取られて見えなくなることがある。`overflow` を使う場合はフォーカスリングが隠れないか確認する

#### タブであること・選択状態・パネルとの対応がスクリーンリーダーに伝わるようにする【本章固有】

- 該当基準: 4.1.2 名前・役割・値、1.3.1 情報及び関係性
- 要件: `role="tablist"` / `"tab"` / `"tabpanel"` の 3 点セット、`aria-selected` による選択状態、`aria-controls` / `aria-labelledby` によるタブとパネルの関連付け
- 確認方法: スクリーンリーダーで「タブ」「○個中○番目」「選択中」が読み上げられるか。パネルに移動したとき、対応するタブ名がパネルのラベルとして伝わるか
- 補足: ネイティブ要素がないため、本章の中心となる項目。正しく実装できない場合のフォールバックは層 3 参照

#### 選択中のタブが色以外でもわかるようにする【本章固有】

- 該当基準: 1.4.1 色の使用、1.4.11 非テキストのコントラスト
- 要件: 下線・太字・形状など色以外の手がかりを併用し、選択インジケータは隣接色と 3:1 以上のコントラスト
- 確認方法: グレースケール表示でも選択中タブが判別できるか。インジケータと背景のコントラスト比を計測して 3:1 以上か

#### 切り替えアニメーションを無効にできるようにする【他章共通】

- 流用元: アコーディオン章「モーションアニメーションを無効にできる」（ほぼ同文で流用可）
- 該当基準: 2.3.3 インタラクションによるアニメーション
- 確認方法: `prefers-reduced-motion` を有効にした状態で、アニメーションせず瞬時に切り替わるか

#### 文字の拡大・行間の変更・画面幅の縮小でも使えるようにする【他章共通】

- 流用元: アコーディオン章の同名項
- 該当基準: 1.4.4 文字サイズの変更、1.4.12 テキストの間隔、1.4.10 リフロー
- 要件（タブ固有の観点）: ラベルが長くなった・拡大されたときのタブリストの挙動（折り返すか、横スクロールにするか）を決める必要がある（→ 層 3「設計判断ポイント」の「タブが多い場合」と関連）
- 確認方法: ズーム 200%・`line-height: 1.5`・画面幅 320px のそれぞれで、ラベルが切れず・重ならず読めるか

#### 開いていないパネルの中身もページ内検索で見つかるようにする【本章固有】【ユーザビリティ】

- 該当基準: なし（WCAG 外。前節「WCAG 外のユーザビリティ要件」参照）
- 要件: `hidden="until-found"` で非選択パネルを検索対象にする
- 確認方法: 非選択パネル内のテキストを `Ctrl` / `⌘` + `F` で検索してヒットし、該当パネルが自動的に表示されるか

#### 見送り（チェック項目にしない基準）

- **3.2.1 フォーカス時** — チェック項目にはしない。「自動アクティベーション（フォーカス移動と同時のパネル切り替え）が WCAG 違反にならない」根拠として、実装例の自動/手動の説明内で触れる
- **2.4.6 見出し及びラベル** — ラベルの付け方の一般論で、タブ特有の考慮が薄い。扱わない
- **3.2.4 一貫した識別性** — サイト全体にまたがる話で、コンポーネント単体の章では扱わない
- **2.5.8 ターゲットのサイズ** — タブは操作領域が小さくなりがちなので迷うが、チェック項目にはせず、実装例のスタイリングで軽く触れる候補に留める

## 3. 具体事例（Evidence）

### 実装事例（デザインシステム・ライブラリ）

| 項目 | W3C APG | MUI | Radix UI | React Aria (Adobe) | Inclusive Components |
|------|---------|-----|----------|--------------------|-----------------------|
| **デフォルトのアクティベーション** | 両方の例を提供 | 手動 | 自動 | 自動 | 手動 |
| **非アクティブパネル** | DOM に残し `hidden` | 実装依存 | アンマウント（`forceMount` で残せる） | inert（`shouldForceMount` で常時マウント可） | `hidden` 属性 |
| **縦タブ** | `aria-orientation` | サポート | `orientation` prop | `orientation` prop | 言及なし |
| **roving tabindex** | ✅ | ✅ | ✅ | ✅ | ✅ |
| **レスポンシブ** | 言及なし | スクロール可能タブ | CSS に委ねる | `overflow-x: auto` | 言及なし |

#### 設計判断ポイント（実装が割れている論点）

- **自動 vs 手動アクティベーション** — 上表のとおり実装が真っ二つに割れている（MUI・Inclusive Components は手動、Radix・React Aria は自動）

  | | 自動 | 手動 |
  |---|---|---|
  | **動作** | 矢印キーでフォーカス移動と同時にタブ切り替え | 矢印キーではフォーカスのみ。Enter/Space で切り替え |
  | **使い分け** | パネル表示に遅延がない場合 | ネットワーク通信等で遅延がある場合 |
  | **APG 推奨** | 遅延がなければ自動を推奨（操作ステップが少ない） | — |

- **非アクティブパネルの DOM 上の扱い** — `hidden` で DOM に残す（APG・Inclusive Components）か、アンマウントする（Radix デフォルト）か。ページ内検索・`hidden="until-found"` の利用可否に直結する
- **そもそも矢印キー移動＋roving tabindex を実装すべきか** — APG は矢印キーでの移動を規定するが、「一般の Web ユーザーが『タブ UI なら矢印キーで移動できる』と期待・理解しているか」は疑わしいという指摘がある（→ 参考記事 #25）。多くのコンテンツは Tab キーでのフォーカス移動と Enter での決定で操作されており、左右矢印キーはコンテンツ閲覧ではめったに使われない。この不確実性が、フォールバック案 1（`role="tab"` を使わず各ボタンを独立フォーカスにする＝矢印キー移動なし）を選ぶ実務的な根拠にもなる。`role="tab"` を付けるなら矢印キー移動＋roving tabindex はセットで実装する（付けないと APG のタブパターンとして不完全）が、「タブロールを付けるか自体を状況で判断する」という選択肢がある
- **タブが多い場合**: 横スクロール、オーバーフローメニュー
- **レスポンシブ**: デスクトップでタブ、モバイルでアコーディオンに切り替えるパターンが一般的
- **縦タブ**: `aria-orientation="vertical"` + ↑/↓キーでの移動

### 失敗事例（ありがちな NG 例）

<!-- 候補ベース。執筆前にコード例化と裏取りをする -->

- **NG: `role="tab"` を付けたのに `aria-selected` を切り替えない**
  - 対応する要件: 4.1.2 名前・役割・値
  - 何が起きるか: スクリーンリーダーに嘘の選択状態が伝わる。「何もしないより悪い」（No ARIA is better than Bad ARIA）の典型例
  - 出典・実例: James Bateson の記事（→ 参考記事 #12）
- **NG: 見出しや `div` にクリックイベントを付けただけのタブ**
  - 対応する要件: 2.1.1 キーボード、4.1.2 名前・役割・値
  - 何が起きるか: キーボードでフォーカスできず、役割も選択状態も伝わらない
- **NG: 非選択タブも `tabindex="0"` のまま（roving tabindex 未実装）**
  - 対応する要件: 2.4.3 フォーカス順序
  - 何が起きるか: `Tab` キーで全タブを 1 つずつ通過しないとパネルに到達できない。タブが多いと極端に操作が増える
- **NG: ラジオボタン + `:checked` の CSS のみタブ**
  - 対応する要件: 4.1.2（役割が「ラジオボタン」と伝わる）、2.1.1
  - 何が起きるか: スクリーンリーダーには「タブ」ではなくフォームの選択肢として伝わり、操作モデルが噛み合わない
  - 出典・実例: dfkaye の記事に「完全なアクセシビリティは難しい」との注意あり（→ 参考記事 #17）
- **NG: 選択中タブを色の変化だけで表現**
  - 対応する要件: 1.4.1 色の使用、1.4.11 非テキストのコントラスト
  - 何が起きるか: 色覚特性によっては、どのタブが選択中かわからない
- **NG: パネルを `display: none` で隠し、ページ内検索でヒットしない**
  - 対応する要件: WCAG 外のユーザビリティ要件（ページ内検索）
  - 何が起きるか: 非選択パネル内の情報が「無い」と判断される。`hidden="until-found"` で回避できる

### 新しいブラウザ機能: `focusgroup` 属性（Chrome 150〜）

Chrome 150（2026 年 6 月 30 日）で追加された `focusgroup` 属性は、**roving tabindex パターンを HTML 属性だけで宣言的に実現**するもの。タブ UI の矢印キー移動の JS 実装を置き換えられる。

#### タブ UI での利用例

```html
<div role="tablist" focusgroup="horizontal wrap">
  <button role="tab" tabindex="0" aria-selected="true">Tab 1</button>
  <button role="tab" tabindex="-1" aria-selected="false">Tab 2</button>
  <button role="tab" tabindex="-1" aria-selected="false">Tab 3</button>
</div>
```

これだけで以下が自動的に動く:

- **左右矢印キー**でタブ間のフォーカス移動（`horizontal`）
- 末尾→先頭のループ（`wrap`）
- Tab キーでの出入りは既存の tabindex に従う（変更なし）

#### roving tabindex との比較

| | roving tabindex（従来） | focusgroup（Chrome 150〜） |
|---|---|---|
| 矢印キー移動 | JS で keydown リスナー実装 | HTML 属性だけで実現 |
| tabindex の切り替え | JS で `0` / `-1` を動的に管理 | 初期値を設定すればブラウザが管理 |
| ループ（wrap） | JS で先頭/末尾の判定が必要 | `wrap` キーワードで宣言 |
| 縦タブ | JS で ↑/↓ を処理 | `vertical` に変えるだけ |

#### 使えるキーワード

| キーワード | 効果 |
|-----------|------|
| `horizontal` | 左右矢印のみ（タブ UI の標準） |
| `vertical` | 上下矢印のみ（縦タブ用） |
| （省略） | 4 方向すべて |
| `wrap` | 端で折り返し |
| `grid` | 2 次元ナビゲーション |
| `extend` | 親の focusgroup に統合（ネスト構造用） |

#### 対応状況と注意点

- **Chrome 150（2026 年 6 月 30 日）で Ship**。Firefox・Safari は未対応（2026 年 7 月時点）
- `focusgroup` が担うのは**矢印キーのフォーカス移動だけ**。以下は引き続き JS が必要:
  - `aria-selected` の切り替え
  - タブパネルの表示/非表示切り替え
  - 自動アクティベーション時のパネル切り替え
- 「最後にフォーカスされた要素の記憶」は現時点では未実装（将来 CSS Toggles との組み合わせで対応予定）

#### チャプターでの扱い方の検討

アコーディオンの章で `interpolate-size`（Chromium 系のみ）を紹介したのと同じ構成で、「対象ブラウザで推奨実装が変わるパターン」として書ける:

- `focusgroup` が使えるブラウザのみ → focusgroup 版（矢印キー移動の JS 不要）
- 古いブラウザも対象 → JS 版（従来の roving tabindex）

ただし、`focusgroup` を使っても `aria-selected` 切り替えやパネル表示切り替えの JS は必要なので、アコーディオンの CSS 版ほど劇的な簡素化にはならない。「矢印キー移動の部分だけが宣言的になる」という位置づけ。

### フォールバック・不採用案

#### フォールバック: 「No ARIA is better than Bad ARIA」— ARIA を正しく実装できないときの選択肢

タブ UI はアコーディオンと違い、ネイティブ HTML 要素がないため ARIA + JS の正しい実装が前提になる。しかし、ARIA の実装が不完全だと「何もしないより悪い」結果になりうる（例: `role="tab"` を付けたのに `aria-selected` を切り替えない → スクリーンリーダーに嘘の状態が伝わる）。

この懸念は統計的にも裏付けがある。WebAIM Million 2026（100 万ホームページの自動検査、→ 参考記事 #23）では、ARIA を使用しているページ（全体の 82.7%）のほうが検出エラーが多く（ARIA あり平均 59.1 件 vs なし平均 42 件）、「ARIA 属性が多いページほど検出エラーも多い」傾向が報告されている。ただし ARIA 自体がエラーの原因とは限らず、ARIA を使うページはそもそも複雑という側面もあると注記されている。

ARIA を正しく実装するスキルや工数がない場合、以下のフォールバックが考えられる:

1. **`role="tab"` を使わず `<button>` + `aria-pressed` で実装する**
   - `role="tablist"` / `role="tab"` / `role="tabpanel"` を付けず、単純な `<button type="button">` を並べ、選択状態を `aria-pressed="true"` / `"false"` で表す（各ボタンはトグルボタンとして読み上げられる）
   - スクリーンリーダーには「タブ」とは伝わらないが、「ボタンを押すと内容が変わる」という基本動作＋「押されている／いない」の状態は伝わる。`role="tab"` を中途半端に付けて `aria-selected` を切り替え忘れるより安全
   - roving tabindex も矢印キー移動も不要（各ボタンが独立したフォーカス対象になるため、Tab キーで順にフォーカスできる）
   - 欠点: Tab キーで全ボタンを順に通過するため、タブ数が多いと煩わしい。矢印キーでの移動もできない
   - 出典・実例: beeworks-framework のタブサンプル（`button` ロール + `aria-pressed` 版と `tab` ロール版の 2 パターンを併記）

2. **すべてのコンテンツを表示する（タブを使わない）**
   - コンテンツを隠さず全セクションを並べて表示する
   - タブで隠す必然性がないなら、そもそも全部見せるほうがユーザーにとって楽な場合もある

3. **アコーディオンで代替する**
   - `details` / `summary` ならネイティブで ARIA 相当の情報が伝わる
   - タブとアコーディオンは「複数コンテンツの切り替え」という点で機能的に近い
   - 見た目はタブではなくなるが、アクセシビリティの担保は圧倒的に楽

4. **別ページに分ける／アンカーリンクで遷移させる**
   - 情報量が多い場合や、各セクションが独立したコンテンツなら、タブで 1 画面に詰め込まず別ページに分割する（あるいは 1 ページに全掲載してアンカーリンクで該当箇所へ移動させる）
   - 非表示のパネルが生じないため、ページ内検索・SEO・共有（各セクションに個別 URL）の面で有利。マルチデバイスではページ遷移のほうがアクセシブルという指摘もある（→ 参考記事 #24）

チャプターでは ARIA を正しく実装する方法を本筋として解説しつつ、冒頭や「使用の前に」等で「正しく実装する自信がなければ、ARIA なしのボタンやアコーディオンで代替するほうが安全」という選択肢を示すのがよさそう。

#### 不採用: `details`/`summary` + CSS Grid で疑似タブ UI を作る案

`details` を複数並べ、`name` 属性で排他制御し、`summary` を横並び、各 `details` の中身を `grid-area` で同じ領域に重ねることで、見た目だけタブに見せる手法。検討したが不採用。

**最大の問題: DOM 順序と視覚的な順序が乖離する。** `details` 要素は「summary → 中身」がセットなので、DOM 上の読み順は「タブ1 → タブ1の中身 → タブ2 → タブ2の中身 → …」になる。CSS で見た目を「タブ1・タブ2・タブ3（横並び）→ 選択中の中身」に並べ替えても、スクリーンリーダーやキーボード操作は DOM 順に従うため、タブ2に移動するにはタブ1の中身を通過しなければならない。

**その他の問題:**

- スクリーンリーダーには「アコーディオンが並んでいる」としか伝わらない。見た目がタブなのに操作モデルがアコーディオンなので、期待と実際の挙動がずれる
- ただし、世のサイトが矢印キー移動をちゃんと実装しているかは怪しく、ユーザーが「タブ UI なら矢印キーで移動できるはず」と期待しているかは疑問（→ 参考記事 #25 が同じ問題を提起）。並列のボタンとして実装しているサイトも多い。とはいえ、DOM 順序の問題のほうが致命的なので、この手法は採用しない
