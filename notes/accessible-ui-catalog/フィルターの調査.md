## 1. コンポーネントの概要（What & Why）

### 定義・解決する問題

フィルター（絞り込み）は、一覧コンテンツ（商品・記事・画像など）をユーザーの選んだ条件（カテゴリ・属性）で絞り込む UI。大量の選択肢から目的のものへ効率よく到達させる。

構成要素: 条件の入力 UI（チェックボックス・ラジオ・セレクト）、結果の一覧、**件数などの結果フィードバック**、リセット手段。フォーム章（入力 UI そのもの）とトースト章（結果変化の通知）の知見が合流する応用章という位置づけ。

### そもそも使うべきかの判断

- 件数が少ない一覧（1〜2 画面で見渡せる量）にフィルターは不要。並び順やグルーピングの見直しで足りることが多い
- フィルターは**組み合わせ次第で簡単に「0 件」を作る** UI。0 件時の受け皿（通知・リセット・条件緩和の提案）まで設計してはじめて成立する
- 「即時反映（選ぶたびに結果が変わる）」を選ぶと、変化の通知・フォーカス維持・操作の予測可能性という動的 UI の要件を背負う。**ページリロード型（フォーム送信でサーバーが絞り込む）なら、これらの要件がほぼ消える**（→ 層 3「フォールバック」）
- カテゴリが相互排他で少数なら、フィルターではなくタブ（タブ章）やリンクのナビゲーションで足りる場合もある

### ネイティブ HTML 要素の有無

- **入力側はすべてネイティブで揃う**（フォーム章参照）。さらに、検索・絞り込み領域を示す **`search` 要素**が 2023 年に HTML へ追加された（`role="search"` ランドマークの HTML 版。search は長らく「HTML に対応要素がない唯一のランドマーク」だった）
  - 対応状況: Chrome 118 / Firefox 118 / Safari 17（いずれも 2023 年）で Baseline 済み。過去のサンプルは移行期の推奨に従い `<search role="search">` と併記していたが、現在は `search` 単独で実用域
- **結果の変化を伝える部分だけがネイティブで完結しない**。ライブリージョン（`output` 要素 / `role="status"`）が本筋になる（トースト章の知見の再利用）
- 過去サンプルが件数表示と 0 件表示に **`output` 要素**（暗黙で `role="status"`）を使っていたのは筋がよく、実装例に引き継げる

### 類似コンポーネントとの使い分け

| 観点 | フィルター | 検索（キーワード） | ソート | タブ（カテゴリ切替） |
|------|------------|---------------------|--------|-----------------------|
| **入力** | 既定の選択肢から選ぶ | 自由入力 | 並び順の選択 | 1 つのカテゴリを選ぶ |
| **結果** | 部分集合 | 部分集合 | 同じ集合の並べ替え | カテゴリごとの表示 |
| **0 件の可能性** | 高い（組み合わせ） | 高い | なし | 低い |
| **典型実装** | チェックボックス群 | `input type="search"` | `select` | タブ／リンク |

- 実際には検索 + フィルター + ソートが同居することが多い。`search` 要素はこれら一式を包むランドマークとして使える（仕様上「検索またはフィルタリング」の両方が守備範囲）

## 2. アクセシブルであるためには（要件・規範）

### WCAG 2.2 該当基準の洗い出し

<!-- △ = 該当するか微妙だが念のため入れておく。詳細な要件・確認方法はチェック項目案側 -->

- **達成基準 4.1.3 ステータスメッセージ（レベル AA）** — 中核基準。絞り込み結果の変化（件数・0 件）がフォーカス移動なしでスクリーンリーダーに伝わる（過去調査で唯一明記されていた基準でもある）
- **達成基準 3.2.2 入力時（レベル A）** — チェック操作と同時に「予測できない変化」を起こさない。ページ内の結果一覧が更新されるだけなら通常コンテキストの変化には当たらないが、ページ遷移・フォーカス移動を伴うなら違反領域に入る
- **達成基準 2.4.3 フォーカス順序（レベル A）** — 結果更新でフォーカスを奪わない・失わない（操作中のチェックボックスにフォーカスが留まる）
- **達成基準 1.3.1 情報及び関係性（レベル A）** — 条件グループの構造（`fieldset` / `legend`）、検索・絞り込み領域のランドマーク
- **達成基準 4.1.2 名前・役割・値（レベル A）** — 各条件の名前と選択状態、リセットボタンの名前
- **達成基準 2.1.1 キーボード（レベル A）** — ネイティブコントロールなら自動で満たせる
- **達成基準 1.4.1 色の使用（レベル A）** — 選択中の条件（チップ・ボタン型 UI の場合）を色だけで表現しない
- △ **達成基準 2.5.8 ターゲットのサイズ（最低限）（レベル AA）** — チップ型・タグ型の条件 UI が小さくなりがち
- △ **達成基準 1.1.1 非テキストコンテンツ（レベル A）** — アイコンのみのフィルター開閉ボタン等
- △ **達成基準 1.4.10 リフロー（レベル AA）** — 狭い画面でのフィルターパネルの扱い（ディスクロージャー化）

### キーボード操作仕様

入力側はネイティブコントロールの標準操作（フォーム章参照）。フィルター固有の論点は「結果が更新された後」に集中する:

- 操作したコントロールから**フォーカスを動かさない**（更新のたびにフォーカスがリセットされると、複数条件を連続で選べない）
- 「もっと表示する」ボタンは、追加読み込み後のフォーカス管理が必要（ページネーション章「もっと見る」の論点と同一）
- モバイルでフィルターパネルを開閉式にする場合は、ディスクロージャー（アコーディオン章）の要件が乗る

### ARIA ロールと属性・マークアップ

| 手段 | 用途 | 説明 |
|------|------|------|
| `search` 要素 | 検索・絞り込み領域のランドマーク | スクリーンリーダーのランドマークジャンプで直行できる。複数ある場合は `aria-label` で区別 |
| `form` + `fieldset` / `legend` | 条件グループの構造 | 「カテゴリ」「色」等のグループ名を `legend` に（過去サンプルは `p` テキストだったため、改善ポイント） |
| `output` 要素（暗黙 `role="status"`） | 件数・結果フィードバック | 「表示件数 12 件」の自動読み上げ。ライブリージョンは**事前設置**（トースト章の罠と同じ） |
| `role="status"` / `aria-live="polite"` | 同上（output を使わない場合） | `aria-atomic="true"` で全文読み上げ |
| `button type="reset"` / リセットボタン | 条件の一括解除 | 0 件からの回復手段。`type="reset"` はフォーム標準で動く |
| `aria-pressed` / `checked` | チップ型 UI の選択状態 | ボタン型の条件 UI にする場合。基本はチェックボックスが素直 |

補足（Sara Soueidan のライブリージョン実践論より。→ 参考記事 #5, #6）:

- 件数の通知は `polite` でよいが、**「0 件」は assertive（`role="alert"`）で即時に伝える**価値がある（結果が消えたことに気づけないのが最大の事故のため）
- チェックボックスを連打すると読み上げが洪水になる。**通知はデバウンス**して「操作が落ち着いてから 1 回」にする
- 通知に含める文言は「12 件に絞り込みました」のように、件数 + 何が起きたかをセットにする

### WCAG 外のユーザビリティ要件

- **URL に絞り込み状態を残す**（`?category=animal&color=green`）: 共有・リロード・戻るで状態が復元できる。クライアントサイドフィルタでも `history.replaceState` で同期する（ページネーション・リダイレクト章と共通の論点）
- **選択中の条件の可視化と個別解除**: 何で絞り込んでいるかを常に見えるようにし（選択済みチップの列等）、個別に外せるようにする
- **各選択肢に件数を併記する**（「動物 (5)」）: 選ぶ前に結果量の見当がつき、0 件の組み合わせを事前に避けられる
- **非表示アイテムの DOM 上の扱い**: クライアントサイドで `display: none` にする方式は、絞り込み前のアイテムがページ内検索にヒットしない・大量 DOM が残る。件数が多いなら DOM から外すかサーバーサイドに寄せる
- **「もっと表示する」との併用**（過去サンプルの構成）: 絞り込みと追加表示が同居する場合、絞り込み変更時に表示件数をリセットするか等の状態設計を明確に

### チェック項目案（記事の単位に束ね直す）

#### 絞り込み結果の変化がスクリーンリーダーに伝わるようにする【他章共通】

- 流用元: トースト章「表示した内容が、フォーカスを移さずにスクリーンリーダーへ伝わる」項（ライブリージョンの実装知見を全面的に流用）
- 該当基準: 4.1.3 ステータスメッセージ
- 要件: 事前設置した `output`（または `role="status"`）に「12 件に絞り込みました」等を書き込む。連続操作はデバウンスして通知を 1 回にまとめる
- 確認方法: スクリーンリーダーでチェックボックスを操作し、フォーカスを動かさずに件数の変化が読み上げられるか。連打したとき読み上げが洪水にならないか

#### 0 件になったことに気づけて、回復できるようにする【本章固有】

- 該当基準: 4.1.3、実務要件（回復手段）
- 要件: 0 件時は明確なメッセージを表示・通知し（assertive を検討）、リセットボタンや条件緩和の提案を近くに置く
- 確認方法: 0 件になる組み合わせを選んだとき、視覚・読み上げの両方で気づけるか。そこからワンアクションで回復できるか

#### 検索・絞り込みの領域だと識別できるようにする【本章固有】

- 該当基準: 1.3.1 情報及び関係性、4.1.2
- 要件: 条件 UI 一式を `search` 要素で包む。条件グループは `fieldset` / `legend` でラベル付け
- 確認方法: スクリーンリーダーのランドマーク一覧に「検索」が現れるか。各チェックボックスにフォーカスしたときグループ名（「色」等）も読まれるか

#### 操作した瞬間に予期しないことが起きないようにする【本章固有】

- 該当基準: 3.2.2 入力時、2.4.3 フォーカス順序
- 要件: チェック操作でページ遷移・フォーカス移動・スクロールジャンプを起こさない。結果一覧の更新だけに留める（それを超える変化が必要ならページリロード型 + 適用ボタンにする）
- 確認方法: キーボードで条件を操作した直後、フォーカスが同じコントロールに残っているか。矢印キーでラジオを探っている最中に破壊的な変化が起きないか

#### 選択中の条件が色以外でもわかり、解除できるようにする【本章固有】

- 該当基準: 1.4.1 色の使用、4.1.2（選択状態の伝達）
- 要件: 選択状態をチェックマーク・塗り・枠などで冗長に表現（ネイティブのチェックボックスなら自動で満たせる）。何で絞り込み中かが一覧でわかり、個別解除と一括リセットができる
- 確認方法: グレースケールで選択中の条件が判別できるか。リセットで全条件が外れて結果と通知も戻るか

#### キーボードで操作でき、フォーカスが見えるようにする【他章共通】

- 流用元: ページネーション章の同名項（入力側はフォーム章のネイティブ操作に委譲）
- 該当基準: 2.1.1、2.4.7
- 確認方法: マウスなしで条件選択 → 結果確認 → リセットまで一巡できるか

#### 絞り込み状態を URL に残すようにする【本章固有】【ユーザビリティ】

- 該当基準: なし（WCAG 外）
- 要件: クエリパラメータに状態を反映し、リロード・共有・戻るで復元できるようにする
- 確認方法: 絞り込んだ状態でリロードして同じ結果になるか。戻る操作で直前の状態に戻るか

#### 見送り（チェック項目にしない基準)

- **2.5.8 ターゲットのサイズ** — チップ型 UI を採る場合のスタイリング注意として実装例で触れる
- **1.1.1 非テキストコンテンツ** — アイコンボタンの一般論（他章で既出）。フィルター開閉ボタンの実装例内で触れる
- **1.4.10 リフロー** — モバイルでのパネル折りたたみはディスクロージャー（アコーディオン章）への参照で済ませる

## 3. 具体事例（Evidence）

### 実装事例

| 項目 | 過去の社内フレームワーク | GOV.UK（検索・フィルタ関連） | Sara Soueidan の実践論 |
|------|---------------------------|-------------------------------|--------------------------|
| **領域の明示** | `<search role="search">`（移行期の併記） | `role="search"` 相当 | — |
| **件数の通知** | `output` で「表示件数 n 件」 | 結果更新の通知を重視 | `polite` + デバウンス、通知文言の設計 |
| **0 件時** | `output` で「表示できるコンテンツがありません」 | 回復手段の提示 | **assertive で即時通知** |
| **リセット** | `button type="reset"` | — | — |
| **追加表示** | 「もっと表示する」ボタン | — | — |

- 過去サンプルの構成（`search` + `output` ×2 + リセット + もっと表示）は骨格として現在でも通用する。改善ポイントは（1）条件グループを `fieldset` / `legend` にする、（2）通知のデバウンス、（3）URL 同期、の 3 点

#### 設計判断ポイント（実装が割れている論点）

- **即時反映 vs 適用ボタン** — 本章最大の分岐
  | | 即時反映 | 適用ボタン |
  |---|---|---|
  | 操作感 | 軽快（結果を見ながら調整） | ワンテンポ遅い |
  | 通知 | 操作ごとに必要（デバウンス必須） | ボタン押下後に 1 回 |
  | サーバー往復 | 多い（クライアント処理向き） | 1 回（サーバー処理向き） |
  | 3.2.2 との相性 | 「結果更新のみ」なら適合 | 最も安全（要求による変化） |
  | 向く場面 | 条件が少ない・結果が軽い | 条件が多い・モバイル・サーバー処理 |
- **クライアントサイド vs サーバーサイド** — 全件を DOM に持てる規模ならクライアント（過去サンプル方式）、大規模ならサーバー + ページリロード or 部分更新。リロード型は通知が不要になる（ページロード自体が通知）
- **非表示アイテムの扱い** — `display: none`（過去サンプル方式）は簡単だがページ内検索・DOM 量に難。`hidden` 属性、DOM からの除去、サーバー側での除外、と段階がある
- **条件 UI の形** — チェックボックス（素直・推奨）／チップ型ボタン（`aria-pressed` が必要）／セレクト。見た目の都合でボタン化するなら選択状態の伝達を忘れない

### 失敗事例（ありがちな NG 例）

- **NG: 絞り込んでも何も通知されない**
  - 対応する要件: 4.1.3 ステータスメッセージ
  - 何が起きるか: スクリーンリーダーには「チェックを入れた」ことしか伝わらず、結果が変わったこと・何件になったかが分からない
- **NG: 0 件になっても無言（空白の一覧だけ）**
  - 対応する要件: 4.1.3、回復手段の欠如
  - 何が起きるか: 「壊れた」と誤解して離脱する。視覚でも空白だけでは 0 件かロード中か区別できない
- **NG: 条件を変えるたびにフォーカスがリセットされる・ページ先頭に飛ぶ**
  - 対応する要件: 2.4.3 フォーカス順序
  - 何が起きるか: 複数条件を連続で選べない。キーボードユーザーは毎回フィルターまで Tab で戻る羽目になる
- **NG: セレクトの選択と同時にページ遷移する**
  - 対応する要件: 3.2.2 入力時
  - 何が起きるか: 矢印キーで選択肢を探るだけで遷移が暴発する（リダイレクト章の SCR19 と同一の失敗）
- **NG: チップ型の選択状態が色だけ・`aria-pressed` なし**
  - 対応する要件: 1.4.1、4.1.2
  - 何が起きるか: どの条件が有効なのか、色覚特性のあるユーザーにもスクリーンリーダーにも伝わらない
- **NG: チェック連打で読み上げが洪水になる（デバウンスなし）**
  - 対応する要件: 4.1.3 の運用（トースト章の「大量連投」と同型）
  - 何が起きるか: 通知が邪魔になり、ユーザーが読み上げを無視するようになる
- **NG: 絞り込み状態が URL に残らない**
  - 対応する要件: WCAG 外（ユーザビリティ項目）
  - 何が起きるか: リロード・共有・戻るで状態が消え、やり直しになる

### 新しいブラウザ機能: `search` 要素（Baseline 2023）

- 検索・絞り込み領域を示すランドマークの HTML 版。`<div role="search">` を置き換える
- 対応状況: Chrome 118 / Firefox 118 / Safari 17（2023 年）で **Baseline 済み**。過去サンプルのように `role="search"` を併記する移行期対応は、現在はほぼ不要
- 仕様上の守備範囲は「検索**または**フィルタリング」。キーワード検索がなくても絞り込み UI を包んでよい（Scott O'Hara の解説。→ 参考記事 #8）
- 補足: CSS の `:has()` も全ブラウザ対応済みで、「チェック状態に応じたフィルタ UI 側のスタイル」は JS なしで書けるようになった（ただし絞り込みロジック自体を CSS でやるのは不採用。→ 下記）

### フォールバック・不採用案

#### フォールバック: ページリロード型（フォーム送信 + サーバーサイド絞り込み）

- `form method="get"` で送信し、サーバーが絞り込んだ一覧を返す。**JS ゼロで、通知（4.1.3）も不要になり（ページロードが通知そのもの）、URL 同期も自動で手に入る**
- 動的フィルタが正しく実装できないなら、この形に落とすのが最も堅牢。プログレッシブエンハンスメントの土台（JS ありなら同じフォームを fetch + ライブリージョンに強化）としても機能する

#### 不採用: CSS のみのフィルタリング（`:checked` + 兄弟セレクタ／`:has()` で表示切り替え）

**最大の問題: 結果の変化を通知する手段がなく、4.1.3 を満たせない。** 件数も 0 件も伝えられない。

**その他の問題:**

- URL 同期・リセット・件数表示など、結局 JS が必要な要件が残る
- 「JS なしで動く」ことが目的なら、ページリロード型のほうが正攻法
