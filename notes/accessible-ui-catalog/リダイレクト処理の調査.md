## 1. テクニックの概要（What & Why）

### 定義・解決する問題

ユーザーの明示的な操作（リンク・ボタンのクリック）を介さずに、別の URL・画面へ移動させる処理。以下を含む:

- **URL 転送**: 旧 URL → 新 URL、HTTP→HTTPS、地域・言語別 URL への振り分け
- **認証フロー**: 未ログイン時のログインページ行き、ログイン後の元ページ復帰
- **時間経過での自動遷移**: 「5 秒後にトップページへ移動します」型、セッションタイムアウト
- **入力に応じた自動遷移**: セレクトボックスの選択と同時にページ移動する等
- **SPA のプログラム遷移**: ルーターによる `redirect()` / `navigate()`

解決する問題は正当（URL の永続性、認証、導線の自動化）だが、**「ユーザーが要求していないコンテキストの変化」**である点にアクセシビリティ上のリスクが集中する。画面が突然変わると、認知障害のあるユーザー・スクリーンリーダーのユーザー・読むのが遅いユーザーは、何が起きたか把握できない。

### そもそも（その方式を）使うべきかの判断

この章の使用判断は「リダイレクトを使うか」ではなく「**どの方式でやるか**」になる。原則の序列:

1. **サーバーサイド（HTTP 3xx）が常に第一候補**。WCAG の Understanding も「認知的な制限があるユーザーはサーバーサイドのリダイレクトのほうが混乱しにくい」と明記している（→ 参考記事 #1）。ユーザーには中間状態が見えず、「そういう URL だった」のと区別がつかない
2. サーバーを触れない場合のみ、**0 秒の meta refresh**（クライアントサイドの即時リダイレクト）
3. **時間差のあるリダイレクト（カウントダウン型）は原則使わない**（F40 で明確に失敗例とされている）
4. **入力・フォーカスをトリガーにした自動遷移は使わない**（3.2.1 / 3.2.2 違反。実行ボタンを分ける）

### ネイティブ（プラットフォーム標準）手段の有無

UI コンポーネントの「ネイティブ要素」に相当するのは **HTTP のリダイレクト（301 / 302 / 303 / 307 / 308）**。ブラウザ・支援技術・検索エンジン・履歴のすべてが正しく扱ってくれる、最も枯れた手段。

- クライアントサイド手段（meta refresh、`location.replace()`、SPA ルーター）は、HTTP リダイレクトの模倣であり、**履歴・戻るボタン・支援技術への通知のどこかに自前の配慮が必要になる**
- 「ネイティブ要素があるならそれを使う」という本書の一貫した原則が、この章では「HTTP でできることは HTTP でやる」に対応する

### 遷移方式の比較

| 観点 | HTTP 3xx（サーバー） | meta refresh 0 秒 | meta refresh n 秒 | JS（`location.replace`） | SPA ルーター |
|------|----------------------|--------------------|--------------------|---------------------------|---------------|
| **ユーザーへの見え方** | 気づかない（理想） | 一瞬で切り替わる | 中間ページが見える | 実装次第 | 実装次第 |
| **戻るボタン** | 正常（301/308 等） | `0;url=` なら履歴に残らない扱いが主流 | **ループの危険** | `replace` なら安全、`href` 代入はループの危険 | ルーターの `replace` 指定次第 |
| **WCAG 上の扱い** | SVR1（推奨） | G110 + H76（許容） | **F40（失敗）** | G110 相当（即時なら） | 即時なら可。通知・フォーカスは自前 |
| **主な用途** | URL 転送全般 | サーバーを触れない静的サイト | 使わない | 認証後の遷移等 | アプリ内遷移 |

## 2. アクセシブルであるためには（要件・規範）

### WCAG 2.2 該当基準の洗い出し

<!-- △ = 該当するか微妙だが念のため入れておく。詳細な要件・確認方法はチェック項目案側 -->

- **達成基準 2.2.1 タイミング調整可能（レベル A）** — 時間差リダイレクト・自動リロードは「時間制限」。中核基準その 1
- **達成基準 3.2.1 フォーカス時（レベル A）** — フォーカスしただけで遷移などのコンテキスト変化を起こさない
- **達成基準 3.2.2 入力時（レベル A）** — セレクト選択・チェック操作と同時に自動遷移しない（する場合は事前説明）。中核基準その 2
- **達成基準 2.4.2 ページタイトル（レベル A）** — 遷移先でタイトルが正しく変わる（SPA で漏れがち）
- **達成基準 2.4.3 フォーカス順序（レベル A）** — SPA 遷移後のフォーカス位置が論理的（前ページの残骸に留まらない）
- **達成基準 4.1.3 ステータスメッセージ（レベル AA）** — △ SPA 遷移をスクリーンリーダーに通知する場合の実装手段
- **達成基準 2.2.4 中断（レベル AAA）** — 自動更新・割り込みを延期・抑制できる
- **達成基準 3.2.5 要求による変化（レベル AAA）** — コンテキスト変化はユーザーの要求で起こす。AAA だが章全体の設計原則として機能する
- △ **達成基準 2.2.6 タイムアウト（レベル AAA）** ※WCAG 2.1 新規 — データ喪失を伴うタイムアウトの事前警告
- △ **達成基準 2.2.2 一時停止、停止、非表示（レベル A）** — カウントダウン表示そのものが動くコンテンツになる場合

#### 達成方法・失敗例の対応表（この章は Techniques が特に充実している）

| 種別 | ID | 内容 |
|------|----|------|
| 達成方法 | **SVR1** | サーバーサイドで自動リダイレクトを実装する |
| 達成方法 | **G110** | 即時のクライアントサイドリダイレクトを使う |
| 達成方法 | **H76** | `<meta http-equiv="refresh" content="0;url=...">`（**0 秒**が条件。リダイレクト専用ページにし、他のコンテンツを置かない） |
| 達成方法 | **G76**（自動更新の代替） | 自動更新せず「更新」ボタンでユーザーに要求させる |
| 達成方法 | **SCR19**（3.2.2 関連） | セレクトの `onchange` で自動送信・遷移しない |
| 失敗例 | **F40** | 時間差のある meta refresh でリダイレクトする（2.2.1 / 2.2.4 違反） |
| 失敗例 | **F41** | meta refresh でページを定期リロードする（2.2.1 / 2.2.4 / 3.2.5 違反） |
| 失敗例 | **F60**（3.2.5） | 入力中に新しいウィンドウ・画面を開く |
| 失敗例 | **F61**（3.2.5） | ユーザーが止められない自動更新 |

- ACT ルール「Meta element has no refresh delay」もあり、機械的チェックの対象になっている（→ 参考記事 #6）
- 2.2.1 の例外: 時間制限が**20 時間超**なら適合（トースト章と同じ「実質無期限」ルール）。またリアルタイム性が本質（オークション等）の場合の例外もある

### SPA のクライアントサイド遷移で必要になること（規範外だが要件級）

サーバー遷移ならブラウザが自動でやること（フォーカスリセット・タイトル更新・読み上げ開始位置）が、SPA では全部自前になる。Gatsby チームと Marcy Sutton による支援技術ユーザーテストの知見（→ 参考記事 #7）:

- **フォーカス管理**: 遷移後、新しいコンテンツの先頭（見出しやラッパーに `tabindex="-1"`）へフォーカスを移す。「ページが変わったのにフォーカスが虚空にある」のが最悪
- **通知**: ライブリージョン（`role="status"`）で「○○ページに移動しました」を読み上げる（ルーターのアナウンサー機能。Next.js 等は組み込み済み）
- **タイトル更新**: `document.title` を遷移ごとに更新（2.4.2）
- **スクロール位置**: 先頭に戻す（ブラウザ遷移の模倣）

### チェック項目案（記事の単位に束ね直す）

<!-- テクニック章なので、チェック項目は「方式の選択」と「やってはいけないこと」中心の構成になる -->

#### リダイレクトはサーバーサイド（HTTP 3xx）で行うようにする【本章固有】

- 該当基準: 3.2.5 要求による変化（推奨実装）、2.2.1
- 要件: URL 転送は HTTP ステータスコード（恒久なら 301/308、一時なら 302/307）で行う。サーバーを触れない場合のみ `meta refresh` の **0 秒**指定（H76。リダイレクト専用ページにする）
- 確認方法: リダイレクト元 URL を開いたとき、中間ページが見えずに遷移先が表示されるか。戻るボタンが正常に機能するか（ループしないか）

#### 「n 秒後に移動します」型のリダイレクトをしないようにする【本章固有】

- 該当基準: 2.2.1 タイミング調整可能（F40）、2.2.4
- 要件: カウントダウン型の中間ページを作らない。案内ページが必要なら、自動遷移せず「移動する」リンクをユーザーに押させる（時間制限をなくす）
- 確認方法: 放置しても勝手に遷移しないか。遷移するなら、読む速度に関係なく全員が内容を読み切れる設計か（＝実質、自動遷移をやめる）
- 補足: 「5 秒あれば読めるだろう」が成立しないのがポイント（読む速度・操作速度の個人差は桁で違う）

#### フォーカス・入力をきっかけに勝手に遷移しないようにする【本章固有】

- 該当基準: 3.2.1 フォーカス時、3.2.2 入力時
- 要件: セレクトボックスの選択（`onchange`）やラジオボタンのチェックで自動的にページ移動しない。「移動」「適用」ボタンを分ける。どうしても自動にするなら、動作を事前にテキストで説明する（3.2.2 の但し書き）
- 確認方法: キーボードでセレクトの選択肢を矢印キーで探っている最中に、ページが飛ばないか（`onchange` 自動遷移はこの操作で暴発する）

#### 自動リロード・自動更新をやめる。必要なら止められるようにする【本章固有】

- 該当基準: 2.2.1、2.2.4、3.2.5（F41・F61・G76）
- 要件: `meta refresh` やタイマーによる定期リロードをしない。鮮度が必要なら「更新」ボタン（G76）か、更新の一時停止・間隔調整の手段を提供する。部分更新ならライブリージョンで通知を制御（トースト章参照）
- 確認方法: ページを開いたまま放置して、勝手にリロード・遷移が起きないか。スクリーンリーダーの読み上げ中にリロードで先頭に戻されないか

#### セッションタイムアウトは事前警告と延長手段をつけるようにする【本章固有】

- 該当基準: 2.2.1 タイミング調整可能（2.2.6〔AAA〕もここに吸収）
- 要件: タイムアウトでログイン画面へ自動遷移させる前に、警告（残り時間 + 延長ボタン）を出す。警告自体に 20 秒以上の応答時間を与え、簡単な操作で延長できる。入力内容が失われる場合はその旨を事前に知らせる（2.2.6）
- 確認方法: タイムアウト直前に警告が出るか。警告ダイアログはダイアログ章の要件（フォーカス管理）を満たしているか
- 補足: 警告ダイアログの実装はダイアログ章（`alertdialog`）とのクロスリファレンスになる

#### SPA の画面遷移でフォーカス・タイトル・通知を管理するようにする【本章固有】

- 該当基準: 2.4.3 フォーカス順序、2.4.2 ページタイトル、4.1.3 ステータスメッセージ
- 要件: プログラム遷移（ログイン後の復帰等）の後、（1）新コンテンツの先頭へフォーカスを移す、（2）`document.title` を更新する、（3）ライブリージョンで遷移を通知する。フレームワークのルーターが持つ機能（Next.js のルートアナウンサー等）を殺さない
- 確認方法: スクリーンリーダーで遷移操作をして、新しいページ名が読み上げられるか。遷移後に `Tab` を押したとき、新コンテンツの妥当な位置から始まるか

#### 見送り（チェック項目にしない基準）

- **2.2.2 一時停止、停止、非表示** — カウントダウン表示の話は「n 秒後に移動しない」項で消滅するため独立させない
- **3.2.5 要求による変化（AAA）** — 個別項目ではなく章全体の設計原則として冒頭で提示する（各項目の「なぜ」を束ねる役割）
- **4.1.3** — SPA 項の実装手段として吸収。詳細はトースト章に委譲

## 3. 具体事例（Evidence）

### 実装事例（フレームワーク・プラットフォーム）

| 項目 | HTTP（Apache / nginx 等） | Next.js | React Router | 静的サイト（サーバー設定不可） |
|------|---------------------------|---------|--------------|--------------------------------|
| **リダイレクト手段** | 301/302 等の設定 | `redirect()`（サーバーサイドで 3xx を返せる）、`next.config` の `redirects` | ローダーの `redirect()` | `<meta http-equiv="refresh" content="0;url=...">` |
| **戻るボタン** | ブラウザが正しく処理 | `replace` 系の挙動 | `replace` 指定可 | 0 秒なら履歴に残らない扱いが主流 |
| **遷移の通知** | 不要（フルロード） | ルートアナウンサー内蔵 | 自前（`ScrollRestoration` 等と併用） | 不要（フルロード） |

- SSR フレームワークの `redirect()` は「フレームワークの書き味のまま、実体はサーバーサイドリダイレクト」なので、原則（SVR1）とモダン開発が両立する。記事ではここを接続すると実務的になる

#### 設計判断ポイント（実装が割れている・迷いやすい論点）

- **`location.href` 代入 vs `location.replace()`** — JS でリダイレクトする場合、`href` 代入は履歴にリダイレクト元が残り、**戻るボタンで戻る→また飛ばされるループ**を作る。即時リダイレクトは `replace()` が原則
- **ログインページ行きのリダイレクトで「元いた場所」を失わない** — 認証後に元のページへ戻す（`?redirect_to=` 等）。戻さない実装は、支援技術ユーザーに限らず全員の文脈を破壊する
- **リダイレクトの連鎖** — 301 → 302 → … の多段は遅延と混乱のもと。1 段に集約する
- **国・言語の自動振り分け** — IP や `Accept-Language` での強制リダイレクトは、意図しない言語に飛ばされたユーザーが戻れなくなりがち。提案（バナー）に留めて選択させる設計が無難

### 失敗事例（ありがちな NG 例）

<!-- 候補ベース。執筆前にコード例化と裏取りをする -->

- **NG: 「5 秒後にトップページへ移動します」のカウントダウンページ**
  - 対応する要件: 2.2.1（F40）
  - 何が起きるか: 読み終わる前に飛ばされる。スクリーンリーダーでは読み上げ途中で強制的にコンテキストが変わる
- **NG: `meta refresh` で 60 秒ごとにページを自動リロード**
  - 対応する要件: 2.2.1 / 2.2.4 / 3.2.5（F41）
  - 何が起きるか: 読み上げ・入力・スクロール位置がすべてリセットされ続ける。ページを読み終えられない
- **NG: セレクトボックスの `onchange` でページ遷移**
  - 対応する要件: 3.2.2 入力時（SCR19）
  - 何が起きるか: キーボードで選択肢を矢印キーで探るだけで遷移が暴発し、目的の選択肢に到達できない
- **NG: JS リダイレクトで戻るボタンがループする**
  - 対応する要件: G110 の但し書き（戻る機能を壊さない）
  - 何が起きるか: 戻るを押すたびにリダイレクト元へ行き、また飛ばされる。ユーザーが閉じ込められる
- **NG: セッションタイムアウトで警告なしにログイン画面へ飛ばし、入力内容が消える**
  - 対応する要件: 2.2.1、2.2.6
  - 何が起きるか: 入力に時間がかかるユーザー（支援技術・運動障害・認知障害）ほど、長文入力を失いやすい。実害が最も大きい失敗例
- **NG: SPA のプログラム遷移で何も通知せず、フォーカスも放置**
  - 対応する要件: 2.4.3、2.4.2、4.1.3
  - 何が起きるか: スクリーンリーダーには「何も起きていない」。画面は変わったのに読み上げは前ページのまま
- **NG: リダイレクト専用ページに本文コンテンツを置く**
  - 対応する要件: H76 の条件（リダイレクトページには関連情報以外を置かない）
  - 何が起きるか: 0 秒でも一瞬表示され、読めないコンテンツが存在することになる

### 新しいブラウザ機能: Navigation API（SPA 遷移の標準化）

- **Navigation API** は SPA のクライアントサイド遷移を標準化する API。`navigation.navigate()` の `intercept()` で遷移を横取りしつつ、**`focusReset: "after-transition"`（デフォルト）でブラウザがフォーカスをリセットしてくれる**。SPA が自前でやっていたフォーカス管理の一部をブラウザに返上できる
- 対応状況（2026 年 7 月時点）: Chrome 102（2022 年）から先行。Firefox・Safari は実装が進行中（Interop 対象。執筆時に最新状況を要確認）
- **View Transitions API**（同一ドキュメント: Baseline / クロスドキュメント: Chrome・Safari 先行）は遷移の視覚的連続性を与える。アニメーションになるため `prefers-reduced-motion` との組み合わせを実装例で示す価値がある
- チャプターでの扱い方: 「SPA 遷移の 3 点セット（フォーカス・タイトル・通知）」の将来的な省力化として紹介。現状はフレームワークのルーター機能を正しく使うのが本筋

### フォールバック・不採用案

#### フォールバック: 自動遷移を諦めてユーザーに選ばせる

- カウントダウン・自動振り分け・自動更新は、いずれも「**リンク／ボタンを置いてユーザーに押させる**」に置き換えられる。時間制限系の達成基準がすべて消えるうえ、実装も単純になる
- 「移転しました。新しいページはこちら」+ リンク、が最古で最強のフォールバック

#### 不採用: 時間差 meta refresh（`content="5;url=..."`）

**最大の問題: F40 として WCAG が名指しで失敗例にしている（2.2.1 / 2.2.4 違反）。**

**その他の問題:**

- 戻るボタンの挙動がブラウザ間で不安定
- 「読める時間」の見積もりが原理的に不可能（個人差が桁違い）
- 使ってよいのは 0 秒（= H76、即時リダイレクト）のみ、と明確に線を引ける

#### 不採用: IP・ブラウザ言語による強制自動振り分け

**最大の問題: ユーザーの要求によらないコンテキストの変化（3.2.5）であり、誤判定時にユーザーが目的のページへ到達できなくなる。**

**その他の問題:**

- VPN・出張・多言語話者など誤判定の要因が多い
- 検索エンジン・共有リンクとの相性も悪い
- バナー等での「提案 + ユーザー選択」に置き換える
