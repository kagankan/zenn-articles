## 1. コンポーネントの概要（What & Why）

### 定義・解決する問題

ヘッダーナビゲーションは、サイト共通のヘッダーに置かれる主要ナビゲーション。構成要素: ロゴ（ホームへのリンク）、ナビゲーションリンク、サブメニュー（ドロップダウン）、モバイル用の開閉ボタン（ハンバーガー）。

この章の本質的な問い: **「サブメニュー（ドロップダウン）をどう実装するか」**。結論から言えば、

- **サイトナビゲーションに ARIA の `menu` ロールを使ってはいけない**（APG が明言。`menu` はアプリケーションのメニュー〔右クリックメニュー等〕のための複雑なウィジェットロールで、矢印キー操作等の期待を支援技術に発生させる）
- 正解は**ディスクロージャーパターン**: `button` + `aria-expanded` でサブメニューを開閉する、アコーディオンと同族の単純な構造（→ 参考記事 #1）

これが過去調査の「TODO: サブメニューの最適解を検討」への回答になる。

### そもそも使うべきかの判断

- サブメニュー（ドロップダウン）は「隠す UI」。階層が浅いならサブメニューなしのフラットなナビゲーションが常に単純で堅牢
- ホバー開閉は「マウスの通り道で誤開閉する」「タッチに存在しない」問題を持ち込む。**クリック（タップ）開閉が基本形**で、ホバーは追加のエンハンスメントと位置づける
- メガメニュー（大型サブメニュー）ほど 1.4.13・フォーカス管理の要件が重くなる。リンク数が少ないならサブメニューではなく着地ページ（カテゴリトップ）に一覧を置く構成も検討する

### ネイティブ HTML 要素の有無

- 骨格はネイティブで揃う: `header`（`banner` ランドマーク）+ `nav` + `ul` + `a` / `button`
- サブメニューの開閉に相当するネイティブ要素はない（`details` は使えるが、ナビゲーションでの `details` はフォーカス管理・ホバー対応の面で癖がある）。**`button` + `aria-expanded` + JS が本筋**
- 新しめの選択肢として `popover` 属性 + CSS Anchor Positioning でサブメニューを作る手法が登場している（light dismiss・`Esc`・トップレイヤーが自動。→ 層 3「新しいブラウザ機能」）

### 類似コンポーネントとの使い分け

| 観点 | ディスクロージャーナビゲーション | ARIA `menu` / `menubar` | メガメニュー | ハンバーガーメニュー（モバイル） |
|------|-----------------------------------|--------------------------|--------------|-----------------------------------|
| **用途** | サイトナビゲーションの標準 | アプリの操作メニュー（エディタ等） | 大量のリンクの一覧提示 | 狭い画面での格納 |
| **ロール** | `nav` + `button` + `aria-expanded` | `menubar` / `menu` / `menuitem` | ディスクロージャーの大型版 | ディスクロージャー or ダイアログ |
| **キーボード** | `Tab` / `Enter` / `Esc` のみ | 矢印キー・文字キー移動を実装する義務 | 同左（ディスクロージャー準拠） | 開閉 + （ダイアログ型なら）フォーカス管理 |
| **判断** | **基本形** | サイトナビには使わない | リンク数が多い場合 | モバイルの標準 |

## 2. アクセシブルであるためには（要件・規範）

### WCAG 2.2 該当基準の洗い出し

<!-- △ = 該当するか微妙だが念のため入れておく。詳細な要件・確認方法はチェック項目案側 -->

- **達成基準 2.1.1 キーボード（レベル A）** — サブメニューの開閉・全リンクへの到達がキーボードで可能（過去調査の観点）
- **達成基準 1.4.13 ホバー又はフォーカスで表示されるコンテンツ（レベル AA）** — ホバー開閉のサブメニューは Dismissible（`Esc`）・Hoverable・Persistent の 3 要件（過去調査が Esc を明記していた。詳細はツールチップ章の整理を流用）
- **達成基準 4.1.2 名前・役割・値（レベル A）** — ハンバーガーボタンの名前（過去実装は `aria-label="メニュー"`）と開閉状態（`aria-expanded`）、サブメニュートグルの状態
- **達成基準 1.3.1 情報及び関係性（レベル A）** — `nav` ランドマーク + `aria-label`、リスト構造
- **達成基準 2.4.1 ブロックスキップ（レベル A）** — 全ページ共通のナビゲーションを読み飛ばす手段（スキップリンク、ランドマーク）。ヘッダー章でしか扱えない重要基準
- **達成基準 2.4.7 フォーカスの可視化（レベル AA）** — リンク・ボタンのフォーカスリング（`overflow: hidden` の注意は過去調査の定番指摘）
- **達成基準 2.4.3 フォーカス順序（レベル A）** — サブメニューが DOM 上でトグルの直後にあり、開いたら次の `Tab` で入れる
- **達成基準 3.2.3 一貫したナビゲーション（レベル AA）** — 全ページで同じ順序・構成（ヘッダーはこの基準の主対象）
- **達成基準 1.4.10 リフロー（レベル AA）** — 画面幅 320px・ズーム 400% で使える。デスクトップでもズームするとモバイルレイアウトになるため、**ハンバーガー版は「モバイル用」ではなく「全ユーザーの拡大時 UI」**でもある
- **達成基準 2.4.2 ページタイトル ／ 2.4.5 複数の手段（レベル AA）** — △ サイト全体の話として軽く
- △ **達成基準 1.1.1 非テキストコンテンツ（レベル A）** — ロゴ画像の `alt`（サイト名）、ハンバーガーアイコン
- △ **達成基準 2.5.8 ターゲットのサイズ（最低限）（レベル AA）** — ナビリンクの密集
- △ **達成基準 3.2.1 フォーカス時（レベル A）** — フォーカスしただけでサブメニューを開くかどうか（開くなら 1.4.13 も絡む）

### キーボード操作仕様（APG ディスクロージャーナビゲーション）

| キー | 動作 |
|------|------|
| `Tab` / `Shift + Tab` | リンク・トグルボタンを順に移動。開いているサブメニュー内も通常の Tab 順 |
| `Enter` / `Space` | トグルボタンでサブメニューを開閉。リンクは遷移 |
| `Esc` | 開いているサブメニューを閉じ、フォーカスをトグルに戻す |
| （フォーカスがナビ領域から出る） | 開いているサブメニューを閉じる |

- **矢印キーの実装は不要**（APG のディスクロージャーナビゲーション例ではオプション扱い。`menubar` にしない限り義務ではない）。タブ章の「矢印キーをユーザーが期待しているか」問題と同じ議論がここにもある
- ハンバーガー（モバイル）で画面を覆うメニューにする場合は、ダイアログ章のフォーカス管理（閉じ込め・背景 inert・`Esc`）がそのまま乗ってくる

### ARIA ロールと属性

| 属性・要素 | 付与先 | 値・説明 |
|------------|--------|----------|
| `header` 要素 | ヘッダー全体 | `banner` ランドマーク（ページ直下に置いた場合） |
| `nav` + `aria-label` | ナビゲーション | 「メインメニュー」等。フッターのナビ等と区別（過去実装も付与済み） |
| `button` + `aria-expanded` | サブメニュートグル・ハンバーガー | 開閉状態。`false` ↔ `true` を JS で切り替え |
| `aria-controls` | トグル | 対応するメニューの `id`（任意。効果は限定的） |
| `aria-current="page"` | 現在ページのリンク | ナビ内の現在地表示（パンくず章と共通の属性） |
| `aria-label` / 視覚的に隠すテキスト | ハンバーガーボタン | 「メニュー」。`span` 3 本線だけにしない（過去実装は付与済み） |

- **使わないもの**: `role="menu"` / `menuitem` / `menubar`（サイトナビには不適切）、`aria-haspopup`（`menu` 用の属性であり、ディスクロージャーには `aria-expanded` だけでよい）

### WCAG 外のユーザビリティ要件

- **ホバー開閉の誤作動対策**: 開閉に遅延（intent 判定）を入れる、ポインタの通り道で閉じない（safe triangle）。ツールチップ章の遅延設計と同じ系譜
- **クリックとホバーの併用**（過去実装の「ホバー開閉・クリック固定」方式）: ホバーで開き、クリックで固定する形はタッチ・キーボードとの整合が取りやすい。ただし「トグルがリンクを兼ねる」形（→ 下記）とは区別する
- **スキップリンク**: `Tab` の最初に「本文へスキップ」を置く。ヘッダー章の実装例に含める価値が高い（2.4.1）
- **モバイルメニュー展開中の背景**: スクロールロック・フォーカスの閉じ込めが必要ならダイアログとして実装する（`dialog` / `inert`。ダイアログ章参照）
- **ロゴの `alt`**: 画像ロゴはサイト名を `alt` に（「ロゴ」ではなく）。ホームリンクであることは `a` が伝える

### チェック項目案（記事の単位に束ね直す）

#### サブメニューはディスクロージャー（button + aria-expanded）で作るようにする【本章固有】

- 該当基準: 4.1.2、2.1.1
- 要件: トグルは `button type="button"` + `aria-expanded`。`role="menu"` 系は使わない。`Esc` で閉じてフォーカスをトグルへ戻す。フォーカスがナビの外へ出たら閉じる
- 確認方法: スクリーンリーダーで「折りたたみ／展開」の状態が読まれるか。「メニュー」ウィジェットとして読まれて**いない**か

#### トグルとリンクの役割を混ぜないようにする【本章固有】

- 該当基準: 4.1.2（役割の一貫性）、3.2.1
- 要件: 「親項目がリンクでもあり、サブメニューも開く」場合は、リンクとトグルボタンを**別の要素に分離**する（Adrian Roselli の推奨。→ 参考記事 #4）。過去実装の「ホバー開閉・リンク」（`a` に `role="button"` + `aria-expanded`）は、リンクとボタンの性質が 1 要素に混在する形で、キーボードでは「Enter で遷移するのか開くのか」が予測できない。改善対象の実例として使える
- 確認方法: キーボードだけで「親ページへ行く」と「サブメニューを開く」の両方が迷わず実行できるか

#### ホバーで開くなら 1.4.13 の 3 要件を満たすようにする【他章共通】

- 流用元: ツールチップ章「消せる・ホバーし続けられる・勝手に消えない」項（過去調査もこの基準と Esc を明記）
- 該当基準: 1.4.13
- 要件: `Esc` で閉じられる。サブメニューへポインタを移動しても消えない。時間経過で勝手に閉じない
- 確認方法: ホバーで開いた状態で（1）`Esc`、（2）サブメニュー上へのポインタ移動、（3）放置、の 3 点を確認

#### ハンバーガーボタンに名前と状態があるようにする【本章固有】

- 該当基準: 4.1.2、1.1.1
- 要件: `aria-label`（または視覚的に隠すテキスト）で「メニュー」等の名前、`aria-expanded` で開閉状態。展開時に全リンクへキーボードで到達できる
- 確認方法: スクリーンリーダーで「メニュー ボタン 折りたたみ」と読まれ、開くと「展開」に変わるか

#### ナビゲーションを読み飛ばせるようにする（スキップリンク）【本章固有】

- 該当基準: 2.4.1 ブロックスキップ
- 要件: ページ先頭に「本文へスキップ」リンク（フォーカス時に可視化）。`nav` / `main` ランドマークを正しく張る（ランドマーク移動も 2.4.1 の達成手段）
- 確認方法: ページを開いて最初の `Tab` でスキップリンクが現れ、`Enter` で本文にフォーカスが移るか

#### 狭い画面・高倍率ズームでも使えるようにする【他章共通】

- 流用元: アコーディオン章の拡大系項目 + ダイアログ章「拡大・狭い画面でも閉じられる」項
- 該当基準: 1.4.10 リフロー
- 要件: 320px・ズーム 400% でハンバーガー版に切り替わり、すべての操作が可能。デスクトップユーザーの拡大時にも同じ UI が使われることを意識する
- 確認方法: デスクトップブラウザでズーム 400% にし、メニューの開閉・全リンク到達を確認

#### 見送り（チェック項目にしない基準）

- **3.2.3 一貫したナビゲーション** — サイト全体の運用の話。「〜とは」で一言触れるに留める
- **2.4.5 複数の手段** — サイト構造の話（検索・サイトマップ）。扱わない
- **aria-current によるナビ内の現在地表示** — 価値はあるがパンくず章と重複するため、実装例の補足に留める
- **2.5.8 ターゲットのサイズ** — スタイリングの注意として実装例で触れる

## 3. 具体事例（Evidence）

### 実装事例

| 項目 | APG ディスクロージャーナビゲーション | APG ハイブリッド例（トップレベルがリンク） | 過去の社内フレームワーク |
|------|----------------------------------------|---------------------------------------------|---------------------------|
| **トグル** | `button` + `aria-expanded` | リンク + 隣接する開閉ボタンの分離 | 3 方式併記（クリック開閉が APG 準拠） |
| **`Esc`** | 閉じてトグルへフォーカス | 同左 | 1.4.13 として明記 |
| **フォーカス離脱で閉じる** | ✅ | ✅ | — |
| **矢印キー** | オプション（実装例あり） | オプション | なし |
| **ホバー** | 扱わない（クリック基本） | 扱わない | ホバー開閉 + クリック固定方式あり |

- 過去実装の 3 方式のうち「クリック開閉」が APG のディスクロージャーとほぼ一致しており、これを本筋に据える。「ホバー開閉・リンク」（`a role="button"`）は分離型（ハイブリッド）への改善例として使える

#### 設計判断ポイント（実装が割れている論点）

- **親項目をリンクにするか、トグルにするか** — 3 案: （1）親はトグル専用（サブメニュー内の先頭に親ページへのリンクを置く。過去実装のサブメニュータイトルリンクがこの形）、（2）親リンク + 隣接トグルボタンの分離型（APG ハイブリッド・Roselli）、（3）1 要素で兼用（非推奨）。（1）が最も単純で、（2）は「親ページに直行したい」要求が強い場合
- **ホバー開閉を足すか** — クリック開閉を土台にした上で、ポインタ環境にだけホバーを足す（`hover` メディア特性で判定）。ホバー単独は不可
- **モバイルメニューをダイアログにするか** — 画面全体を覆う・背景操作を防ぎたいならダイアログ（`dialog` + `showModal()`）、一部だけ覆うインライン展開ならディスクロージャーのまま。中途半端（見た目は全画面・実装はただの表示切替）が最悪で、背景へフォーカスが抜ける
- **`details` でサブメニューを作る案** — JS なしで開閉できるが、「フォーカスが外れたら閉じる」「`Esc` で閉じる」を足すには結局 JS が要る。モバイル限定のシンプルなメニューなら選択肢になる

### 失敗事例（ありがちな NG 例）

- **NG: ホバーでしか開かないサブメニュー**
  - 対応する要件: 2.1.1
  - 何が起きるか: キーボード・タッチのユーザーはサブメニュー内のリンクに一切到達できない
- **NG: サイトナビに `role="menu"` / `menuitem` を付ける**
  - 対応する要件: 4.1.2（役割の過剰申告）
  - 何が起きるか: スクリーンリーダーが「矢印キーで操作するメニュー」と案内するのに Tab でしか動かない等、期待と実装が食い違う。No ARIA is better than Bad ARIA のナビゲーション版
- **NG: `a` に `role="button"` + `aria-expanded` を付けてリンクとトグルを兼用**
  - 対応する要件: 4.1.2、3.2.1
  - 何が起きるか: `Enter` で遷移するのか開くのか予測できない。`Space` では動かない
  - 出典・実例: 過去の社内フレームワークの「ホバー開閉・リンク」方式（改善例として記事で使える）
- **NG: ハンバーガーボタンが `span` 3 本線だけで名前がない**
  - 対応する要件: 4.1.2、1.1.1
  - 何が起きるか: 「ボタン」としか読まれず、メニューの入り口だと分からない
- **NG: サブメニューを開いてもすぐ閉じる（ポインタの通り道で消える）**
  - 対応する要件: 1.4.13（Hoverable）
  - 何が起きるか: トグルからサブメニューへポインタを移動する途中で閉じ、拡大表示のユーザーや手の震えがあるユーザーは開けない
- **NG: モバイルメニュー展開中も背景に `Tab` が抜ける**
  - 対応する要件: 2.4.3
  - 何が起きるか: 見えない背景のリンクにフォーカスが移り、現在地を見失う（ダイアログ章の「なんちゃってモーダル」と同じ失敗）
- **NG: スキップリンクがない（またはフォーカスしても見えない）**
  - 対応する要件: 2.4.1、2.4.7
  - 何が起きるか: キーボードユーザーが全ページで数十個のナビリンクを通過してから本文に着く

### 新しいブラウザ機能: `popover` + CSS Anchor Positioning でのサブメニュー

- サブメニューを `popover` 属性で作ると、**light dismiss（外側クリックで閉じる）・`Esc`・トップレイヤー表示**をブラウザが処理する。`popovertarget`（または `commandfor`）で JS なしの開閉も可能
- 位置合わせは CSS Anchor Positioning（Baseline 済み。ツールチップ章参照）で宣言的に書ける
- 注意点: `popover` はフォーカスが離れても閉じない・`aria-expanded` は `popovertarget` 使用時に自動管理される、など従来のディスクロージャー実装と挙動の細部が異なる。「開閉の骨格をブラウザに任せる新しい選択肢」として紹介し、本筋は従来のディスクロージャーに置くのが現時点の温度感
- ハンバーガー側では、全画面メニューを `dialog` + `showModal()` で作る構成が新機能の恩恵（inert・フォーカス管理の自動化）を最も受けやすい（ダイアログ章と接続）

### フォールバック・不採用案

#### フォールバック: サブメニューをやめてフラットにする

- 階層をなくし、カテゴリトップページに一覧を置く。「隠す UI」を消せば開閉の要件がすべて消える。リンク数が少ないサイトでは常にこれが最善

#### 不採用: ARIA `menubar` パターンでの実装

**最大の問題: サイトナビゲーションに対して過剰なウィジェットセマンティクスで、矢印キー・文字キー移動・`menuitem` 管理の実装義務を負う割に、ユーザーの期待（ただのリンク集）と一致しない。** APG 自身がサイトナビには非推奨と明言している。

**その他の問題:**

- `menuitem` の中では見出し・リンク以外の構造が使えず、メガメニューと相性が悪い
- 実装例の多く（コピペ元）が壊れており、事故率が高い

#### 不採用: CSS `:hover` のみのドロップダウン

**最大の問題: キーボード・タッチで開けない（2.1.1 違反）。**

**その他の問題:**

- `:focus-within` を足せばキーボードで開けるが、「閉じる」制御（`Esc`・意図しない開閉）ができず 1.4.13 を満たせない
- JS を書かない動機なら、`popover` 属性（新機能）のほうが正攻法になりつつある
