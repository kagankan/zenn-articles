# ダイアログ（モーダル）UI コンポーネント — 調査結果まとめ

## 1. コンポーネントの概要（What & Why）

### 定義・解決する問題

モーダルダイアログは、ページに重ねて表示され、**閉じるまで背後のコンテンツへの操作を遮る**ウィンドウ。ユーザーの注意と操作を一時的に 1 つのタスク（確認・入力・警告）に限定するために使う。

「モーダル」の本質は見た目（オーバーレイ）ではなく、**背後が不活性（inert）になること**。視覚的に薄暗くするだけで背後が操作できてしまう実装は、モーダルの要件を満たしていない。

### そもそも使うべきかの判断

- モーダルは**ユーザーの作業を強制的に中断する UI**。開くたびにコンテキストが切り替わり、認知負荷がかかる。特に画面拡大・スクリーンリーダーのユーザーには「突然世界が置き換わる」体験になる
- 使うべきでないケース:
  - 中断する必然性のない情報表示（→ ページ内に置く、詳細ページに遷移する）
  - 長大なフォームや複数ステップの作業（→ 専用ページのほうが戻る・保存・拡大に強い）
  - ページ表示直後の広告・案内（ユーザーはまだ何も要求していない。3.2.5 の精神に反する）
- **閉じているダイアログの中身はページ内検索（`Ctrl` / `⌘` + `F`）にヒットしない**（アコーディオン・タブ章と同じ「隠す UI」の弱点。ダイアログでは `hidden="until-found"` のような回避策も事実上ない）。検索されてほしいコンテンツをモーダルに入れない
- 代替の選択肢: ページ内に見出しを置いてアンカーリンクで遷移させる／スペース節約が目的ならアコーディオン（`details`）にする／情報量が多いなら別ページに分ける（→ 参考記事 #19「Web サイトにモーダルは必要か」が使用判断の日本語文献として有用）
- 使ってよい典型: 破壊的操作の確認、作業の途中で必要になる短い入力、セッション切れ警告
- モーダルにするなら「背後を遮る」ことに責任を持つ（inert・スクロールロック・フォーカス管理）。**その責任を負わない情報なら、そもそもモーダルにしない**、が判断の軸になる

### ネイティブ HTML 要素の有無

- **ネイティブの `dialog` 要素があり、`showModal()` で開けばモーダルの難所をブラウザが自動処理する**。本書の中では `details`/`summary`（アコーディオン）に次ぐ「ネイティブ要素がある」章で、これを土台にした解説が本筋になる
- `showModal()` が自動でやってくれること（→ 参考記事 #5）:
  - **背景の不活性化**: ダイアログ外が `inert` 相当になる（フォーカス・クリック・読み上げから除外）
  - **フォーカス移動**: 開いたときにダイアログ内へフォーカスが移る（`autofocus` 属性があればそこへ）
  - **`Esc` で閉じる**（close request の仕組みに統合。iOS の戻るジェスチャ等も同扱い）
  - **トップレイヤー表示**: `z-index` 戦争から解放。`::backdrop` 疑似要素でオーバーレイも標準提供
- `dialog` 要素自体は Baseline Widely available（Chrome 37 / Firefox 98 / Safari 15.4〔いずれも 2022 年 3 月までに対応済み〕）。**もはや「対応状況を理由に自前実装を選ぶ」段階ではない**
- Scott O'Hara（ARIA/HTML 仕様への貢献者）も 2023 年に「dialog 要素を（分別を持って）使え」と結論。「開発者が知っておくべきアクセシビリティ要件の大部分をブラウザが肩代わりするようになった」（→ 参考記事 #5）
- ただし `showModal()` にも残る注意点がある（初期フォーカス位置・スクロールロック・閉じたあとのフォーカス戻し等。→ 層 2・層 3）。日本語圏でも「期待の星かと思ったらだめな子」という批判記事があり（→ 参考記事 #11）、**「ネイティブなら全自動」ではない**ことを記事で正直に扱うと信頼性が上がる

### 類似コンポーネントとの使い分け

| 観点 | モーダルダイアログ | ノンモーダルダイアログ | ポップオーバー（`popover` 属性） |
|------|--------------------|------------------------|----------------------------------|
| **背後の操作** | 遮る（inert） | 遮らない | 遮らない |
| **開き方** | `dialog.showModal()` | `dialog.show()` | `popover` + `popovertarget` / `commandfor` |
| **`Esc` で閉じる** | 自動 | 自前 | 自動（`auto` の場合） |
| **外側クリックで閉じる** | `closedby="any"`（新機能）または自前 | 自前 | 自動（light dismiss） |
| **フォーカス移動** | ダイアログ内へ自動 | 移動しない | 移動しない |
| **典型用途** | 確認・短い入力 | ツールパレット、チャットウィンドウ | メニュー、ヒント、選択 UI |

- `alertdialog` ロール（重大な警告用。開いた瞬間に内容が読み上げられやすい）はモーダルダイアログの亜種として層 2 で触れる
- ノンモーダル `dialog.show()` は仕様上の挙動にまだ議論があり（Scott O'Hara も「大きな疑問符が残る」と指摘）、記事ではモーダル（`showModal()`）を主役にするのが安全

## 2. アクセシブルであるためには（要件・規範）

### WCAG 2.2 該当基準の洗い出し

<!-- △ = 該当するか微妙だが念のため入れておく。詳細な要件・確認方法はチェック項目案側 -->

- **達成基準 2.1.2 キーボードトラップなし（レベル A）** — フォーカスをダイアログ内に留めること自体は正当だが、**キーボードだけで閉じて抜け出せる**ことが必須
- **達成基準 2.4.3 フォーカス順序（レベル A）** — 開いたらダイアログ内へ、閉じたら呼び出し元へ、という論理的なフォーカスの流れ
- **達成基準 2.1.1 キーボード（レベル A）** — 開く・操作する・閉じるがすべてキーボードで可能
- **達成基準 4.1.2 名前・役割・値（レベル A）** — `dialog` ロールとダイアログの名前（タイトルとの関連付け）
- **達成基準 1.3.1 情報及び関係性（レベル A）** — タイトル・本文との関連（`aria-labelledby` / `aria-describedby`）
- **達成基準 2.4.7 フォーカスの可視化（レベル AA）** — ダイアログ内の初期フォーカスやボタンのフォーカスリング
- **達成基準 1.4.10 リフロー（レベル AA）** — 画面幅 320px・拡大 400% でもダイアログが画面内でスクロールでき、閉じるボタンに到達できる
- **達成基準 1.4.4 文字サイズの変更 ／ 1.4.12 テキストの間隔（いずれもレベル AA）** — 拡大・行間変更でボタンやテキストがあふれない
- △ **達成基準 3.2.1 フォーカス時（レベル A）** — フォーカスしただけでダイアログを開かない（開くのはクリック等の明示操作で）
- △ **達成基準 2.5.8 ターゲットのサイズ（最低限）（レベル AA）** — 閉じる「×」ボタンが小さくなりがち
- △ **達成基準 2.2.1 タイミング調整可能（レベル A）** — セッション切れ警告ダイアログ等、時間制限があるダイアログの場合
- △ **達成基準 1.4.3 コントラスト（最低限）（レベル AA）** — ダイアログと背景の区別というより文字コントラストの一般論
- △ **達成基準 2.4.11 隠されないフォーカス（最低限）（レベル AA）** ※WCAG 2.2 新規 — ノンモーダルやトースト併用時にフォーカス要素を覆わない

### キーボード操作仕様（APG）

| キー | 動作 |
|------|------|
| `Tab` | ダイアログ内の次のフォーカス可能要素へ。最後の要素からは最初の要素へ循環 |
| `Shift + Tab` | 逆方向。最初の要素からは最後の要素へ循環 |
| `Esc` | ダイアログを閉じる |

- **初期フォーカスの置き場所**は APG がかなり細かくガイドしている（このガイダンスは記事の差別化ポイントになる）:
  - 原則: 最初のフォーカス可能要素
  - **不可逆な操作（削除確認等）のダイアログでは、最も破壊的でないボタン（キャンセル側）に置く**
  - コンテンツが長い場合、最初の操作要素に飛ばすと冒頭が読まれない・見えないため、先頭の静的要素（タイトル等）に `tabindex="-1"` を付けてそこに置く
- **閉じたときは、原則として開いた要素（呼び出し元）にフォーカスを戻す**。ただし呼び出し元が消えるワークフロー（行の削除等）では、文脈上妥当な要素へ
- 補足: ネイティブ `showModal()` のフォーカス封じ込めは JS ループ式のトラップと違い、`Tab` でブラウザの UI（アドレスバー等）に抜けることができる。これは仕様上意図された挙動で、2.1.2 的にはむしろ健全

### ARIA ロールと属性（APG / ネイティブ dialog）

| ロール | 付与する要素 | 説明 |
|--------|--------------|------|
| `dialog` | ダイアログコンテナ | ネイティブ `dialog` 要素なら暗黙で付く |
| `alertdialog` | 重大な警告のダイアログ | 開いた時点で本文が読み上げられることを期待できる。`dialog` 要素に明示付与して使う |

| 属性 | 付与先 | 値・説明 |
|------|--------|----------|
| `aria-modal="true"` | ダイアログ | モーダルであることを支援技術に伝える。ネイティブ `showModal()` なら不要（自動） |
| `aria-labelledby` | ダイアログ | タイトル要素の `id` を参照（または `aria-label`） |
| `aria-describedby` | ダイアログ | 短い本文の `id`。確認ダイアログでは有効。長い複雑な内容では省略が推奨 |
| `autofocus` | 初期フォーカスを置きたい要素 | `showModal()` の初期フォーカス先を制御する標準手段 |

補足:

- APG の重要な注意: `aria-modal="true"` は「**実際に背後を操作不能にし、視覚的にも覆っている場合のみ**」付ける。実態が伴わない `aria-modal` は、支援技術ユーザーから背後のコンテンツを不当に隠す
- 自前実装で背後を隠す手段は、歴史的な `aria-hidden="true"` の付け回しより **`inert` 属性**（全ブラウザ対応済み）が現在の推奨
- ネイティブ `dialog` を使う場合も `aria-labelledby` でのタイトル関連付けは自前で行う

### WCAG 外のユーザビリティ要件

- **背景のスクロールロック**: `showModal()` は**背景のスクロールまでは止めない**。CSS での対応が必要（`body { overflow: hidden; }` の付け外し、またはモダンには `html:has(dialog:modal) { overflow: hidden; }`）。スクロールバー消失による画面幅のガタつきは `scrollbar-gutter: stable` で防ぐ（→ 参考記事 #12, #13, #21）
  - JS でロックを付け外しする実装は、**解除処理が失敗するとページ全体がスクロール不能のまま残る**リスクがある（過去の社内フレームワーク調査では「可能な限り使用しない」判断だった）。まずは低リスクな `overscroll-behavior: contain`（ダイアログ内から背景へのスクロール連鎖だけを断つ。→ 参考記事 #20）で足りないかを検討し、ロックするなら CSS の `:has()` 方式のように「開いている状態」に宣言的に追従する書き方を選ぶ
- **外側クリックで閉じるか**: 慣習として期待されるが、誤操作で入力内容が消える事故もある。入力を伴うダイアログでは慎重に（→ 層 3「設計判断ポイント」）
- **閉じる手段の多重化**: 「×」ボタン・キャンセルボタン・`Esc`・（許すなら）外側クリック。`Esc` だけに頼らない
- **開いている間の背景の視覚処理**: `::backdrop` で薄暗くし、モーダルであることを視覚的にも伝える

### チェック項目案（記事の単位に束ね直す）

#### キーボードだけで開く・操作する・閉じるができるようにする【本章固有】

- 該当基準: 2.1.1 キーボード、2.1.2 キーボードトラップなし
- 要件: トリガーは `button`。ダイアログ内の全操作がキーボードで可能。`Esc` で必ず閉じられる（＝トラップからの脱出手段）
- 確認方法: マウスなしで開く → 操作する → `Esc` と キャンセルボタンの両方で閉じられるか

#### フォーカスがダイアログの中に閉じ込められ、外に漏れないようにする【本章固有】

- 該当基準: 2.4.3 フォーカス順序、2.1.2（正当なトラップの条件）
- 要件: 開いている間、`Tab` で背後のコンテンツにフォーカスが移らない。ネイティブ `showModal()` を使えば自動
- 確認方法: `Tab` を押し続けて、フォーカスが背後のリンクやフォームに当たらないか。スクリーンリーダーの読み上げカーソルでも背後に降りられないか（inert の確認）

#### 開いたとき・閉じたときにフォーカスが適切な場所に移るようにする【本章固有】

- 該当基準: 2.4.3 フォーカス順序
- 要件: 開いたらダイアログ内（内容・危険度に応じた位置。破壊的操作の確認ではキャンセル側に `autofocus`）。閉じたら呼び出し元のボタンへ戻す（ネイティブ `dialog` は自動で戻す）
- 確認方法: 開閉の前後でフォーカス位置を目視（またはスクリーンリーダーの読み上げ）で確認

#### ダイアログであることと名前がスクリーンリーダーに伝わるようにする【本章固有】

- 該当基準: 4.1.2 名前・役割・値、1.3.1 情報及び関係性
- 要件: `dialog` 要素（暗黙ロール）+ `aria-labelledby` でタイトルを関連付ける。短い確認文は `aria-describedby` も
- 確認方法: 開いた瞬間に「○○ ダイアログ」とタイトル付きで読み上げられるか

#### 拡大・狭い画面でも、はみ出さず・閉じられるようにする【他章共通】

- 流用元: アコーディオン章「文字の拡大・行間の変更・画面幅の縮小でも〜」項（＋ダイアログ固有の観点を追加）
- 該当基準: 1.4.10 リフロー、1.4.4 文字サイズの変更、1.4.12 テキストの間隔
- 要件（ダイアログ固有）: `max-height` + 内部スクロールで、小さい画面・高倍率ズームでも**閉じるボタンに到達できる**。ボタンが画面外に出て閉じられなくなるのが典型事故
- 確認方法: 画面幅 320px・ズーム 200〜400% で、全ボタンに到達・操作できるか

#### 背景がスクロールしないようにする【本章固有】【ユーザビリティ】

- 該当基準: なし（WCAG 外）
- 要件: ダイアログ表示中に背景ページがスクロールしない。スクロールバー消失によるガタつきもない
- 確認方法: ダイアログ内とオーバーレイ上でホイール・スワイプしたとき背景が動かないか
- 補足: `showModal()` が面倒を見てくれない代表項目。`html:has(dialog:modal)` + `overflow: hidden` と `scrollbar-gutter: stable`

#### 見送り（チェック項目にしない基準）

- **3.2.1 フォーカス時** — 「フォーカスしただけでダイアログを開かない」は当然すぎて項目化しない。トリガーの実装例で触れる程度
- **2.5.8 ターゲットのサイズ** — 「×」ボタンのサイズはスタイリングの話としてビジュアルデザイン節で触れる（タブ・ツールチップ章と同じ扱い）
- **2.2.1 タイミング調整可能** — セッション切れ警告など特定用途の話。汎用チェック項目にはせず、コラムか「使用の前に」で言及候補
- **2.4.11 隠されないフォーカス** — モーダル単体では起きにくい（背景は inert なので）。見送り
- **1.4.3 コントラスト** — ダイアログ固有の考慮が薄い（ツールチップ章と違い、背景色前提のデザインでもない）。扱わない

## 3. 具体事例（Evidence）

### 実装事例（デザインシステム・ライブラリ）

| 項目 | W3C APG | ネイティブ `dialog` + `showModal()` | a11y-dialog | Radix UI Dialog |
|------|---------|--------------------------------------|-------------|-----------------|
| **実装方式** | `role="dialog"` + JS の教科書実装 | ブラウザ標準 | 軽量ライブラリ（歴史的に `dialog` 非依存で発展） | React。portal + 独自フォーカス管理 |
| **フォーカス封じ込め** | JS でループトラップ | ブラウザ（ブラウザ UI へは抜けられる） | JS | JS |
| **`Esc` で閉じる** | JS | 自動 | ✅ | ✅ |
| **背景の不活性化** | `aria-hidden` / `inert` を自前管理 | 自動 | 自前補助 | ✅ |
| **フォーカス戻し** | JS | 自動 | ✅ | ✅ |
| **外側クリックで閉じる** | 実装例による | `closedby="any"`（新機能）または自前 | オプション | デフォルト有効 |

- 方向性としては**「ライブラリの存在意義だった部分がブラウザに吸収されつつある」**構図。新規実装でフレームワーク都合がなければネイティブ `dialog` が第一候補
- TAKLOG の 2 記事（→ 参考記事 #12, #13）が日本語圏の実装水準として参考になる。特に 2025 年版は `command`/`commandfor` による「JS を書かないモーダル」まで踏み込んでいる

#### 設計判断ポイント（実装が割れている論点）

- **初期フォーカスの位置** — 最初のフォーカス可能要素／キャンセルボタン／タイトル（`tabindex="-1"`）で分かれる。APG のガイダンス（破壊的操作ではキャンセル側、長文ではタイトル）を判断基準として紹介できる。ネイティブでは `autofocus` で明示するのが Scott O'Hara の推奨
- **外側クリック（light dismiss）の是非** — 閲覧系ダイアログでは便利、入力系では誤爆で入力消失のリスク。「確認・閲覧はあり、フォームはなし」が実務的な落とし所。`closedby="any"` の登場で「有効にするコスト」は下がった
- **閉じたあとのフォーカス戻し先** — 原則は呼び出し元。呼び出し元が消える場合（削除確認 → 行が消える）にどこへ戻すかは設計判断（一覧の先頭・隣接行など）
- **ページロード直後に開くモーダル** — 技術的に可能だが、呼び出し元が存在せずフォーカス戻し先がない・ユーザーが要求していない、の二重で筋が悪い。「使用の前に」で扱う
- **ブラウザバック（戻る操作）で閉じるか** — モバイルでは「戻るジェスチャでモーダルが閉じる」ことを期待するユーザーが多い。`history.pushState` で履歴に積んで戻るで閉じる実装（過去の社内フレームワークでオプション化していた手法）があるが、履歴汚染との引き換えになる。なお Chrome では Android の戻る操作が close request として扱われ、`showModal()` のダイアログを閉じる方向にプラットフォーム側が進んでいる（`CloseWatcher` API）。全画面に近いモーダルほど「戻るで閉じたい」期待が強まる、という判断軸で書ける
- **URL（ハッシュ）でダイアログを直接開けるようにするか** — `#dialog-1` のようなディープリンクでロード時に開く設計。共有・導線には便利だが、「開いた状態」のフォーカス管理と、閉じたときの戻し先（呼び出し元が存在しない）を設計する必要がある
- **閉じるときのアニメーション** — `close()` を即座に呼ぶとアニメーションできないため「アニメ完了を待ってから閉じる」JS を書く実装が多かったが、現在は CSS だけで書ける（`@starting-style` + `transition-behavior: allow-discrete`。主要ブラウザ対応済み）。いずれの場合も `prefers-reduced-motion` では即時に閉じる

### 失敗事例（ありがちな NG 例）

<!-- 候補ベース。執筆前にコード例化と裏取りをする -->

- **NG: `div` + オーバーレイだけの「なんちゃってモーダル」（背後が操作できる）**
  - 対応する要件: 2.4.3 フォーカス順序、`aria-modal` の実態要件
  - 何が起きるか: `Tab` やスクリーンリーダーの操作で背後のコンテンツに入り込み、見えない場所を操作してしまう
- **NG: `Esc` でもキーボードでも閉じられない**
  - 対応する要件: 2.1.2 キーボードトラップなし
  - 何が起きるか: キーボードユーザーがダイアログから永久に出られない。WCAG の中でも最も深刻な違反類型
- **NG: 閉じたあとフォーカスが `body` に落ちる**
  - 対応する要件: 2.4.3 フォーカス順序
  - 何が起きるか: スクリーンリーダー・キーボードユーザーがページ先頭からやり直しになる
- **NG: `dialog` 要素を `open` 属性や `show()` で開いてモーダルのつもりになる**
  - 対応する要件: 2.4.3、4.1.2（`aria-modal` が付かない）
  - 何が起きるか: `showModal()` の自動処理（inert・`Esc`・フォーカス）が一切効かない。ネイティブ要素を使っているのに自前実装より悪い状態になる
- **NG: `showModal()` を使ったが背景がスクロールする**
  - 対応する要件: WCAG 外（ユーザビリティ項目）
  - 何が起きるか: 背景の位置がずれて、閉じたあとに文脈を見失う。拡大ユーザーほど影響が大きい
- **NG: 巨大なダイアログで閉じるボタンが画面外**
  - 対応する要件: 1.4.10 リフロー
  - 何が起きるか: ズーム 200% やスマートフォンの小さい画面で、閉じる手段そのものに到達できない
- **NG: タイトルと関連付けられていない（名前のないダイアログ）**
  - 対応する要件: 4.1.2 名前・役割・値
  - 何が起きるか: 「ダイアログ」としか読み上げられず、何のダイアログか分からない
- **NG: 確認ダイアログで削除ボタンに初期フォーカス**
  - 対応する要件: APG の初期フォーカスガイダンス（基準というより設計事故）
  - 何が起きるか: `Enter` 連打・反射的な操作で不可逆な削除が実行される

### 新しいブラウザ機能: `closedby` 属性と Invoker Commands（`command` / `commandfor`）

#### `closedby` 属性 — light dismiss の標準化

```html
<dialog closedby="any">…</dialog>
```

| 値 | 挙動 |
|----|------|
| `any` | 外側クリックでも `Esc` でも閉じる（light dismiss） |
| `closerequest` | `Esc` 等の close request のみ（デフォルト相当） |
| `none` | 明示的な `close()` 呼び出しのみ |

- 対応状況（2026 年 7 月時点）: Chrome 134（2025 年 3 月）/ Firefox 141（2025 年 7 月）。**Safari 未対応**（Interop 2026 の対象なので年内対応が見込まれる）
- 「外側クリックで閉じる」の自前 JS（クリック座標判定等の壊れやすいコード）を丸ごと置き換える

#### Invoker Commands（`command` / `commandfor`）— 開閉の宣言化

```html
<button commandfor="my-dialog" command="show-modal">開く</button>
<dialog id="my-dialog">
  <button commandfor="my-dialog" command="close">閉じる</button>
</dialog>
```

- **Baseline Newly available（2025 年 12 月 12 日）**: Chrome 135（2025 年 4 月）/ Firefox 144（2025 年 10 月）/ Safari 26.2（2025 年 12 月）
- ダイアログの開閉・popover の制御を **JS ゼロで宣言的に**書ける。ツールチップ章の `interestfor`（Interest Invokers）と同じ Invoker ファミリー
- チャプターでの扱い方: `closedby` は Safari 待ちだが、`command`/`commandfor` は**全ブラウザ Baseline 到達済みなので実装例の「モダン版」に採用できる**。「`showModal()` を呼ぶだけの JS」すら消える構成が書ける（TAKLOG 2025 年版と同路線）

### フォールバック・不採用案

#### フォールバック: 正しく実装できないときの選択肢

1. **モーダルにしない（ページ遷移・ページ内展開にする）**: 確認は確認ページへ、詳細はアコーディオンや別ページへ。フォーカス管理の難所が丸ごと消える
2. **ネイティブ `dialog` + `showModal()` に寄せる**: 「自前のフォーカストラップを書く」こと自体を避ける。ライブラリを足す前にまずネイティブを検討
3. **確認だけなら `window.confirm()`**: 見た目は選べないが、モーダル性・フォーカス管理・キーボード対応はブラウザ保証。プロトタイプや管理画面では十分な場面もある

#### 不採用: `role="dialog"` + 自前フォーカストラップのスクラッチ実装（を本筋にすること）

**最大の問題: ブラウザが自動化した処理（inert・トップレイヤー・close request・フォーカス戻し）を JS で再発明することになり、再発明部分がそのままバグ源になる。** keydown での `Tab` ハイジャック式トラップは、ブラウザ UI へ抜けられない点でネイティブより挙動が悪い。

**その他の問題:**

- `aria-hidden` の付け回しによる背景隠しは、付け忘れ・外し忘れ事故が定番
- 歴史的経緯（`dialog` 未対応時代のフォールバック）としては言及価値があるので、「かつての実装」「ライブラリの内部で行われていること」として層 3 で紹介する位置づけが妥当

#### 不採用: `popover` 属性でモーダルダイアログを作る案

**最大の問題: popover はノンモーダル専用で、背後が不活性にならない。** モーダルの中核要件を満たせない。

**その他の問題:**

- `Esc`・light dismiss など表面的な挙動が似ているため混同されやすいが、用途はメニュー・ヒント等の非遮断 UI。使い分け表（層 1）で明確化する
