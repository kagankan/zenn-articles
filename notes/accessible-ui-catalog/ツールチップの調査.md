## 1. コンポーネントの概要（What & Why）

### 定義・解決する問題

ツールチップは、要素（ボタンやアイコンなど）にホバーまたはキーボードフォーカスしたときに、その要素を補足する短いテキストを浮かべて表示する UI パターン。アイコンのみのボタンの意味を補ったり、操作の補足説明を添えたりするために使う。

- Sarah Higley による機能的定義（→ 参考記事 #5）: 「テキストのみを含む、ノンモーダルなオーバーレイ。既存の UI コントロールに関連付けられ、デフォルトでは隠れている」
- **中身が「名前（name）」か「説明（description）」かで意味論が分かれる**のがツールチップ最大の特徴（→ 層 3「設計判断ポイント」）:
  - **説明型**: 既にラベルがある要素への補足。`aria-describedby` で関連付ける
  - **名前型**: アイコンのみのボタンのラベルそのもの。`aria-labelledby` で関連付ける
  - この区別が曖昧なまま実装されるのが失敗の主因（Higley・Heydon Pickering がともに指摘）

### そもそも使うべきかの判断

- ツールチップは**ホバー／フォーカスしないと見えない UI**。流し見するユーザーには情報の存在自体が伝わらない
- **タッチデバイスにはホバーがない**。実装によってはスマートフォンのユーザーに中身が一切表示されない。Sarah Higley は「フォーム以外のツールチップには、タッチアクセスの根本的な回避策が現状ない」とまで述べている（→ 参考記事 #5）
- スクリーンリーダーの説明（`aria-describedby`）の読み上げは**ユーザー設定でオフにできる**ため、確実に伝わる保証がない（→ 参考記事 #5）
- したがって、**操作に必須の情報をツールチップだけに入れてはいけない**（NN/g・Inclusive Components・Higley の全員が一致。→ 参考記事 #5, #6, #20）
  - NN/g の例: パスワード要件、必須フィールドの情報などをツールチップに入れるのは NG
- Inclusive Components（→ 参考記事 #6）: 「スペースがあるなら常時表示のテキストラベルを置くべき。ツールチップは**最後の手段**」
- **ツールチップとトグルチップの取り違え**に注意（→ 下の使い分け表）。クリックで開く「ⓘ」ボタン型はトグルチップであり、実装の考え方が異なる

### ネイティブ HTML 要素の有無

- **`title` 属性がネイティブのツールチップに相当するが、アクセシビリティ上使えない**（→ 層 3「不採用」）
  - キーボードでは表示できない。タッチでも表示できない。スクリーンリーダーのサポートも不安定
  - HTML 仕様自体が `title` 属性への依存に警告を出している
  - なお `title` 属性のツールチップは「表示が UA 制御で著者が改変していないコンテンツ」として達成基準 1.4.13 の**例外に該当**するが、例外だから安全という意味ではない（キーボード非対応は残る）
- → 記事の本筋は **ARIA（`role="tooltip"` + `aria-describedby`）+ JS の実装**になる
- ただし新しいブラウザ機能の組み合わせ（`popover="hint"` + `interestfor` + CSS Anchor Positioning）で、**Chrome では JS なしの宣言的ツールチップが可能**になりつつある（→ 層 3「新しいブラウザ機能」）
- APG の Tooltip パターン自体が「**work in progress（タスクフォースの合意に至っていない）**」と明記されている点に注意（→ 参考記事 #1）。タブやアコーディオンと違い、規範となる仕様がまだ固まりきっていない

### 類似コンポーネント（トグルチップ・ポップオーバー）との使い分け

| 観点 | ツールチップ | トグルチップ | ノンモーダルダイアログ（ポップオーバー） |
|------|--------------|--------------|------------------------------------------|
| **開き方** | ホバー／フォーカス | クリック（タップ） | クリック（タップ） |
| **中身** | テキストのみ | テキスト中心（少しリッチ可） | 操作要素を含められる |
| **フォーカス移動** | しない（トリガーに留まる） | しない | する（ダイアログ内へ） |
| **タッチデバイス** | 実装依存（表示されないことが多い） | 問題なく使える | 問題なく使える |
| **ARIA** | `role="tooltip"` + `aria-describedby` | ボタン + ライブリージョン（`role="status"`） | `role="dialog"` |
| **典型例** | アイコンボタンの説明 | 「ⓘ」ボタンの補足情報 | ホバーカード、設定パネル |

- 使い分けの原則（Inclusive Components）: 操作要素の説明を補うなら tooltip、独立した情報をオンデマンドで見せるなら toggletip
- **ツールチップの中に操作可能な要素（リンク・ボタン）を入れてはいけない**。ツールチップにはフォーカスを移動できないため到達不能になる。操作要素が必要なら APG も「ノンモーダルダイアログを使え」としている（→ 参考記事 #1）

## 2. アクセシブルであるためには（要件・規範）

### WCAG 2.2 該当基準の洗い出し

<!-- △ = 該当するか微妙だが念のため入れておく。詳細な要件・確認方法はチェック項目案側 -->

- **達成基準 1.4.13 ホバー又はフォーカスで表示されるコンテンツ（レベル AA）** — ツールチップの中核基準。消去可能（Dismissible）・ホバー可能（Hoverable）・持続（Persistent）の 3 要件
- **達成基準 2.1.1 キーボード（レベル A）** — ホバーだけでなくキーボードフォーカスでも表示できる
- **達成基準 4.1.2 名前・役割・値（レベル A）** — `role="tooltip"` と `aria-describedby` の関連付け。トリガー自体のアクセシブルな名前
- **達成基準 1.3.1 情報及び関係性（レベル A）** — トリガーとツールチップの関係がプログラム的に伝わる（4.1.2 と実質一体）
- **達成基準 1.1.1 非テキストコンテンツ（レベル A）** — アイコンのみのトリガーにテキストの代替（名前）がある
- **達成基準 1.4.3 コントラスト（最低限）（レベル AA）** — ツールチップの文字と背景のコントラスト比 4.5:1 以上
- **達成基準 1.4.4 文字サイズの変更 ／ 1.4.12 テキストの間隔（いずれもレベル AA）** — 拡大 200%・行間 1.5 でも中身が切れず読める
- △ **達成基準 1.4.10 リフロー（レベル AA）** — 画面幅 320px でもツールチップが画面外にはみ出さない（画面端の配置問題と関連）
- △ **達成基準 2.4.7 フォーカスの可視化（レベル AA）** — トリガーのフォーカスリング（ツールチップ固有の考慮は薄い）
- △ **達成基準 2.5.8 ターゲットのサイズ（最低限）（レベル AA）** ※WCAG 2.2 新規 — トリガーがアイコンボタンの場合 24×24 CSS ピクセル以上
- △ **達成基準 2.3.3 インタラクションによるアニメーション（レベル AAA）** — フェード等の表示アニメーションを無効にできる
- △ **達成基準 2.2.1 タイミング調整可能（レベル A）** — 時間経過での自動消去をしない（1.4.13 の Persistent に実質吸収される）
- △ **達成基準 3.2.1 フォーカス時（レベル A）** — フォーカスでツールチップが出ることは「コンテキストの変化」に当たらない（適合の根拠として引く基準）
- △ **達成基準 2.1.2 キーボードトラップなし（レベル A）** — フォーカスがトリガーに留まる設計なのでトラップは構造上生じにくい

#### 1.4.13 の 3 要件の詳細（中核基準なので個別にメモ）

| 要件 | 内容 | 実装上の意味 |
|------|------|--------------|
| **消去可能（Dismissible）** | ポインタやフォーカスを動かさずに追加コンテンツを消せる | `Esc` キーで閉じられるようにする |
| **ホバー可能（Hoverable）** | ポインタを追加コンテンツの上に移動しても消えない | ツールチップ自体にホバーしても表示が維持される |
| **持続（Persistent）** | ホバー／フォーカスが外れるか、ユーザーが消すか、情報が無効になるまで表示され続ける | タイマーで勝手に消さない |

- 厳密には、Dismissible には「**追加コンテンツが他のコンテンツを覆い隠さず・置き換えない場合は不要**」という但し書きがある。ただしツールチップは要素の近くに浮かぶ以上、何かを覆う可能性が常にあるため、実務上は `Esc` 対応が必須と考えてよい
- 1.4.13 の想定読者はロービジョンで拡大表示するユーザー（ツールチップが下のコンテンツを覆って読めない）と、手の震えなどでポインタが意図せずトリガーを通過するユーザー
- Sarah Higley は「`Esc` だけではマウス主体のユーザーが消し方を知らない可能性がある」として、キーボード（`Esc`）とポインタの**両方の消去手段**を推奨している（→ 参考記事 #5）

### キーボード操作仕様（APG）

| キー | 動作 |
|------|------|
| `Tab`（トリガーへのフォーカス） | ツールチップを表示 |
| フォーカスが外れる | ツールチップを閉じる |
| `Esc` | ツールチップを閉じる（フォーカスはトリガーに残る） |

- タブやメニューと違い、**ツールチップ自体への操作キーは存在しない**（フォーカスは常にトリガーに留まる）
- APG の補足: ホバーで表示した場合は、カーソルがツールチップ上にある間は表示を維持する（= 1.4.13 の Hoverable）

### ARIA ロールと属性（APG）

| ロール | 付与する要素 | 説明 |
|--------|--------------|------|
| `tooltip` | ツールチップ本体 | フォーカスを受け取らないポップアップであることを示す |

| 属性 | 付与先 | 値・説明 |
|------|--------|----------|
| `aria-describedby` | トリガー要素 | ツールチップの `id` を参照（説明型の場合） |
| `aria-labelledby` | トリガー要素 | ツールチップの `id` を参照（名前型の場合。→ 層 3「設計判断ポイント」） |

補足（仕様外だが重要な知見）:

- **`role="tooltip"` の実効性は限定的**。Sarah Higley は「スクリーンリーダーへの意味のある影響はない」、Heydon Pickering は「`aria-describedby` が確実に機能する保証を広げる程度」と評価している（→ 参考記事 #5, #6）。付けるのが無難だが、これを付ければアクセシブルになるという類のものではない
- **`aria-haspopup` は付けない**。メニュー・リストボックス等の対話的ポップアップ用の属性で、非対話的なツールチップには不適切（→ 参考記事 #5）
- **`aria-live` でツールチップを読み上げさせない**。ユーザーが再読できず、他のアナウンスに割り込む（→ 参考記事 #5）。※トグルチップでは逆に `role="status"` のライブリージョンが正解（`aria-describedby` だとボタンを押す前に読まれてしまい、押しても何も起きないように感じる。→ 参考記事 #6）。tooltip と toggletip で正反対になるので混同注意
- トリガーは `button` / `a` など**フォーカス可能な要素**であること（`span` や `div`、disabled なボタンには付けられない）

### WCAG 外のユーザビリティ要件

- **タッチデバイスでのアクセス**: WCAG にタッチでの代替表示を直接求める基準はないが、実務上最大の弱点。「必須情報を入れない」を守った上で、タッチでも読ませたいならトグルチップへの変更を検討する（→ 層 3「フォールバック」）
- **画面端でのはみ出し**: トリガーが画面端にあるとき、固定方向に出すツールチップは画面外にはみ出す。CSS Anchor Positioning の `position-try` で自動フリップできる（→ 層 3「新しいブラウザ機能」）
- **表示遅延**: ポインタが通過しただけでツールチップが乱発されるとうるさい。主要ライブラリは「初回はウォームアップ遅延（700ms 前後）、一度表示されたら隣接要素へは遅延なし、しばらく操作がなければ遅延復活（クールダウン）」というパターンでほぼ一致している（→ 層 3「実装事例」）。キーボードフォーカス時は遅延なしで即表示が通例
- **関連コンテンツを覆わない配置**: 入力中のフィールドや関連するラベルを覆わない位置に出す（NN/g）
- **矢印（しっぽ）で対応関係を示す**: 要素が密集している場合、どの要素の説明かを矢印で明確にする（NN/g）

#### キーボード（フォーカス）でもツールチップを表示できるようにする【本章固有】

- 該当基準: 2.1.1 キーボード
- 要件: トリガーを `button` / `a` などフォーカス可能な要素にし、`:hover` だけでなくフォーカスでも表示する
- 確認方法: マウスを使わず `Tab` でトリガーにフォーカスしたとき、ツールチップが表示されるか
- 補足: キーボードフォーカス時は遅延なしで即表示するのが主要ライブラリの共通実装

#### 表示したツールチップが「消せる」「ホバーし続けられる」「勝手に消えない」ようにする【本章固有】

- 該当基準: 1.4.13 ホバー又はフォーカスで表示されるコンテンツ（2.2.1 タイミング調整可能も実質ここに吸収）
- 要件: `Esc` で閉じられる（Dismissible）、ツールチップ上にポインタを乗せても消えない（Hoverable）、時間経過で勝手に消えない（Persistent）
- 確認方法: 表示した状態で（1）`Esc` で閉じられるか、（2）ツールチップ自体にポインタを乗せても消えないか、（3）放置しても消えないか
- 補足: 本章の中核項目。CSS の `:hover` / `:focus` だけでは Dismissible を満たせないため、JS が必須になる根拠でもある

#### ツールチップの内容がスクリーンリーダーに伝わるようにする【本章固有】

- 該当基準: 4.1.2 名前・役割・値、1.3.1 情報及び関係性
- 要件: トリガーに `aria-describedby` でツールチップの `id` を指定し、ツールチップに `role="tooltip"` を付ける
- 確認方法: スクリーンリーダーでトリガーにフォーカスしたとき、名前に続けて内容が「説明」として読み上げられるか
- 補足: 説明の読み上げはユーザー設定でオフにできる → 「必須情報を入れない」原則の裏付けとして本文で触れる

#### トリガー自体にアクセシブルな名前があるようにする（アイコンのみのボタンの場合）【本章固有】

- 該当基準: 4.1.2 名前・役割・値、1.1.1 非テキストコンテンツ
- 要件: ツールチップは「説明」であって「名前」ではない。アイコンボタンには視覚的に隠したラベルか `aria-label` で名前を付ける
- 確認方法: スクリーンリーダーで「○○ ボタン」と名前が読み上げられるか
- 補足: 名前型ツールチップ（`aria-labelledby` 方式）を採る場合はこの項目と統合的に説明する（→ 層 3「設計判断ポイント」）

#### ツールチップの文字と背景に十分なコントラストがあるようにする【本章固有】

- 該当基準: 1.4.3 コントラスト（最低限）
- 要件: 文字色と背景色のコントラスト比 4.5:1 以上（大きい文字は 3:1 以上）
- 確認方法: コントラスト比を計測する。半透明背景の場合は下のコンテンツ次第で比が変わる点に注意

#### 文字の拡大・行間の変更でも、中身が切れたり重ならないようにする【他章共通】

- 流用元: アコーディオン章「文字の拡大・行間の変更・画面幅の縮小でも、見出しや中身が切れたり重ならない」項
- 該当基準: 1.4.4 文字サイズの変更、1.4.12 テキストの間隔（△ 1.4.10 リフローは画面端問題としてユーザビリティ項目側で扱う）
- 要件（ツールチップ固有の観点）: 固定の `width` / `height` や `white-space: nowrap` を避け、`max-width` で折り返す
- 確認方法: ズーム 200%・`line-height: 1.5` で文字が切れず・重ならず読めるか

#### 画面の端でもツールチップがはみ出さず読めるようにする【本章固有】【ユーザビリティ】

- 該当基準: なし（強いて言えば 1.4.10 リフローに接続するが、WCAG 外のユーザビリティ要件として扱う）
- 要件: トリガーが画面端にあるときも、ツールチップが画面内に収まる
- 確認方法: トリガーを画面の上下左右の端に置いた状態で表示し、はみ出さないか。狭い画面幅（320px）でも確認
- 補足: CSS Anchor Positioning（`position-try`）で自動化できる（→ 層 3「新しいブラウザ機能」）

#### 見送り（チェック項目にしない基準）

- **3.2.1 フォーカス時** — チェック項目にはしない。「フォーカスでツールチップが表示されてもコンテキストの変化には当たらない」という適合の根拠として本文で触れる程度
- **2.4.7 フォーカスの可視化** — トリガーは通常のフォーカス可能要素で、ツールチップ固有の考慮が薄い。アコーディオン章等で扱っており、本章では扱わない
- **2.5.8 ターゲットのサイズ** — トリガーがアイコンボタンになりがちなので迷うが、タブ章と同じ扱い（チェック項目にせず、実装例のスタイリングで軽く触れる候補）
- **2.3.3 インタラクションによるアニメーション** — ツールチップの表示はフェード程度で、前庭障害を誘発するようなモーションになりにくい。チェック項目にはせず、実装例の CSS で `prefers-reduced-motion` に触れるに留める（アコーディオン・タブ章と粒度を変える判断。フェードすら止めたいユーザーへの配慮としてコード例には入れる）
- **2.1.2 キーボードトラップなし** — フォーカスがトリガーに留まる設計上、トラップが構造的に生じない。扱わない
- **タッチデバイス対応** — チェック項目ではなく「使用の前に✋」で扱う。「タッチで見えない可能性がある UI である」こと自体が使用判断の材料であり、チェックで担保する性質のものではないため

## 3. 具体事例（Evidence）

### 実装事例（デザインシステム・ライブラリ）

| 項目 | W3C APG | MUI | Radix UI | React Aria (Adobe) | Inclusive Components |
|------|---------|-----|----------|--------------------|-----------------------|
| **関連付け** | `aria-describedby`（説明型） | デフォルトは名前型。`describeChild` で説明型 | `aria-describedby` 相当 | `aria-describedby`（説明型） | 名前型は `aria-labelledby`、説明型は `aria-describedby` と使い分け |
| **`role="tooltip"`** | ✅ | ✅ | ✅ | ✅ | ✅（describedby の確実性を上げる保険と位置づけ） |
| **フォーカスで表示** | ✅ | ✅ | ✅（キーボード操作時は遅延なし） | ✅（キーボードフォーカス時のみ。クリックによるフォーカスでは出さない） | ✅ |
| **タッチでの挙動** | 言及なし | 長押しで表示（1500ms 後に自動非表示） | 言及なし | **表示しない**（「ツールチップなしでも使える UI にせよ」と明記） | 言及なし（タッチが必要ならトグルチップを推奨） |
| **表示遅延** | 言及なし | `enterDelay` / `leaveDelay` | 700ms + `skipDelayDuration`（300ms） | ウォームアップ + クールダウン方式 | 言及なし |
| **`Esc` で消去** | ✅ | 記載なし（要実機確認） | ✅ | 記載なし（要実機確認） | ✅ |
| **ホバー可能（1.4.13）** | ✅ | ✅（デフォルトで interactive、1.4.13 準拠を明記） | ✅（`disableHoverableContent` で無効化可） | ✅ | ✅ |

その他の注目実装:

- **MUI の disabled 要素対応**: disabled なボタンはイベントを発火しないため、`<span>` でラップしてそこにツールチップを付ける方式を案内している。「disabled な要素にはツールチップが出ない」問題への数少ない明文化された対処
- **Scott O'Hara の実装例**（→ 参考記事 #8）: Higley が「より詳細な実装」として参照。エッジケースの処理が参考になる

#### 設計判断ポイント（実装が割れている論点）

- **名前型 vs 説明型** — 本章最大の論点。ツールチップの中身が何かで ARIA の張り方が変わる

  | | 名前型（`aria-labelledby`） | 説明型（`aria-describedby`） |
  |---|---|---|
  | **中身** | アイコンボタンのラベルそのもの（例:「設定」） | 既にラベルがある要素への補足（例:「アプリの設定を開きます」） |
  | **採用例** | MUI のデフォルト、Inclusive Components（アイコンボタンの場合） | APG、React Aria、MUI の `describeChild` |
  | **注意** | 名前と別にツールチップを持つ場合は不可 | トリガーに別途名前が必要 |

  - 既存ドラフト章は「名前は visually-hidden ラベルで付け、ツールチップは説明型」の構成。これは Higley / APG 寄りの設計で、名前・説明の役割分担が最も明快。この方針を維持するのがよさそう
- **タッチデバイスでの扱い** — 実装が三つ巴に割れている: 出さない（React Aria）／長押しで出す（MUI）／言及しない（Radix）。React Aria の「出さない代わりに、ツールチップなしでも使える UI にする」という割り切りは「必須情報を入れない」原則と整合しており、記事の立場として採りやすい。なお MUI の「長押し表示 → 1500ms で自動非表示」は 1.4.13 の Persistent に照らすとグレー
- **フォーカスの種別判定** — クリックでフォーカスしたときにも出すか。React Aria はキーボードフォーカス（`:focus-visible` 相当）のときだけ表示する。クリック時のツールチップは邪魔になりやすいという判断
- **表示遅延の設計** — 初回ウォームアップ（700ms 前後）→ 表示中は隣へ即時 → クールダウンで遅延復活、が業界の共通解。`interestfor` の `interest-delay` プロパティも同じモデル（`p:has(button:interest-source) button { interest-delay-start: 0s; }` のように書ける）

### 失敗事例（ありがちな NG 例）

<!-- 候補ベース。執筆前にコード例化と裏取りをする -->

- **NG: ホバーでしか表示できない（`div` / `span` トリガー + `:hover`）**
  - 対応する要件: 2.1.1 キーボード
  - 何が起きるか: キーボード利用者はツールチップを一切表示できない。トリガーがフォーカス不能だとスクリーンリーダーにも読まれない
- **NG: `Esc` で閉じられない・ツールチップにポインタを乗せると消える・数秒で自動的に消える**
  - 対応する要件: 1.4.13（Dismissible / Hoverable / Persistent）
  - 何が起きるか: 拡大表示のユーザーは覆われた下のコンテンツを読めず、読むのが遅いユーザーは読み終わる前に消える
  - 出典・実例: CSS のみ（`:hover` / `:focus`）の実装は構造的に Dismissible を満たせない（→ 不採用案）
- **NG: `title` 属性で済ませる**
  - 対応する要件: 2.1.1（キーボードで表示不可）、タッチアクセス
  - 何が起きるか: マウスホバー以外のどの手段でも表示されない。スクリーンリーダーの読み上げも環境依存
  - 出典・実例: Inclusive Components「モバイル・支援技術・キーボードのユーザーからコンテンツを隠したければ `title` 属性を使えばよい」という皮肉（→ 参考記事 #6）
- **NG: ツールチップを要素の「名前」代わりにしている（`aria-describedby` だけのアイコンボタン）**
  - 対応する要件: 4.1.2 名前・役割・値、1.1.1 非テキストコンテンツ
  - 何が起きるか: 名前のないボタンになる。説明はあっても名前がないため、音声操作ユーザーはボタンを呼べず、スクリーンリーダーの要素一覧でも識別できない
- **NG: ツールチップの中にリンクやボタンを入れる**
  - 対応する要件: 2.1.1（フォーカス到達不能）
  - 何が起きるか: `role="tooltip"` の中身にはフォーカスを移せないため、キーボードでは操作要素に到達できない。操作要素が必要ならノンモーダルダイアログ（ポップオーバー）にすべき（APG）
- **NG: 操作に必須の情報をツールチップに入れる（パスワード要件など）**
  - 対応する要件: 使用判断の原則（層 1）。WCAG 基準では捉えきれないがユーザー実害が大きい
  - 何が起きるか: タッチユーザー・説明読み上げをオフにしたスクリーンリーダーユーザーには情報が存在しないのと同じになる
  - 出典・実例: NN/g がフォームのパスワード要件を典型 NG として挙げている（→ 参考記事 #20）
- **NG: 固定サイズ・`white-space: nowrap` で文字がはみ出す**
  - 対応する要件: 1.4.4 文字サイズの変更、1.4.12 テキストの間隔
  - 何が起きるか: 拡大・行間変更・翻訳でテキストがあふれて読めなくなる
- **NG: disabled なボタンにツールチップを付けて、出ないことに気づかない**
  - 対応する要件: 2.1.1 ほか（そもそも表示されない）
  - 何が起きるか: disabled 要素はホバー・フォーカスイベントを発火しないため、「なぜ押せないか」を説明するはずのツールチップが誰にも表示されない
  - 出典・実例: MUI が `<span>` ラッパー方式を明文化（→ 参考記事 #16）
- **NG: `aria-live` でツールチップの表示を読み上げさせる**
  - 対応する要件: 4.1.2 の適切な関連付け（`aria-describedby` を使うべき箇所）
  - 何が起きるか: ユーザーが内容を再読できず、他のアナウンスに割り込む。※トグルチップでは逆に `role="status"` が正解という非対称性があり、記事で混同を解いておく価値がある

### 新しいブラウザ機能: `interestfor` + `popover="hint"` + CSS Anchor Positioning

3 つの新機能を組み合わせると、**Chrome では JS なしの宣言的ツールチップ**が書ける。

```html
<button interestfor="tooltip-1" aria-describedby="tooltip-1">
  設定
</button>
<div id="tooltip-1" popover="hint" role="tooltip">
  アプリの設定を開きます
</div>
```

#### 各機能の役割と対応状況（2026 年 7 月時点）

| 機能 | 置き換える JS | Chrome/Edge | Firefox | Safari |
|------|---------------|--------------|---------|--------|
| `interestfor` 属性（Interest Invokers） | ホバー・フォーカス・`Esc`・遅延のイベント処理すべて | **142（2025 年 10 月 28 日）** | 未対応 | 未対応 |
| `popover="hint"` | 表示/非表示の切り替え、トップレイヤー管理 | 133（2025 年 2 月） | 149（2026 年 3 月） | 未対応 |
| CSS Anchor Positioning | 画面端でのフリップ（Floating UI 等の配置ライブラリ） | 125 | 147（2026 年 1 月） | 26 |

- CSS Anchor Positioning は 3 エンジン揃い **Baseline Newly available**（caniuse 全体対応率 約 81%）。`popover="hint"` と `interestfor` は Safari が未対応で Baseline 入りしていない

#### `interestfor` で何が自動になるか

- **ホバー／フォーカスで表示、外れたら非表示**（interest / loseinterest イベントのデフォルト動作）
- **`Esc` で消去**（1.4.13 の Dismissible をブラウザが処理）
- **ターゲット上へのホバーで表示維持**（1.4.13 の Hoverable 相当）
- **タッチでは長押し → コンテキストメニューから表示**。ホバーがないタッチデバイスへの回答をブラウザ側が持つ（`::interest-button` 疑似要素でタップ用ボタンの表示にオプトインする提案もある）
- **表示遅延を CSS で宣言**: `interest-delay`（`interest-delay-start` / `interest-delay-end`）。ライブラリの warmup/cooldown 相当を `:has()` と組み合わせて表現できる
- **アクセシビリティの自動マッピング（Open UI 提案）**: テキストのみの「plain hint」は、トリガーに名前があれば説明（describedby 相当）、なければ名前として自動計算される設計。ただしこの部分は仕様策定中の挙動なので、当面は `aria-describedby` の明示的な併記が安全（→ 参考記事 #26）

#### 何はまだ JS / 手動が必要か

- Safari・Firefox 対応（フォールバック実装そのもの）
- `aria-describedby` の付与（自動マッピングが安定するまで）
- 矢印（しっぽ）等のリッチな見た目や、`anchor-name` / `position-try` による配置指定（CSS で書くが、宣言は必要）

#### チャプターでの扱い方の検討

- アコーディオン章の `interpolate-size`、タブ章の `focusgroup` と同じ「対象ブラウザで推奨実装が変わるパターン」として書ける
- ただし `interestfor` は Chrome のみ（2026 年 7 月時点）なので、**本筋はあくまで JS 版**。「ツールチップの難所（1.4.13 の 3 要件・タッチ・遅延）をブラウザが標準で解こうとしている」という文脈で紹介する位置づけがよい
- 既存ドラフト章は Anchor Positioning を「ビジュアルデザインのための考慮事項」で紹介済み（2025 年 12 月時点の記述で「Chromium 系のみ」）。**Firefox 147 / Safari 26 で状況が変わった（Baseline 入り）ため、執筆時に要更新**

### フォールバック・不採用案

#### フォールバック: ツールチップを使わずに済ませる選択肢

ツールチップはタッチアクセスに構造的な弱点があるため、「正しく実装する」以前に「使わない」選択肢が他コンポーネント以上に有力。

1. **常時表示のテキストラベルにする（最善）**
   - Inclusive Components の第一推奨。「スペースがない」はレイアウトの工夫で解決すべき設計課題であり、ツールチップは最後の手段
   - 全ユーザー（タッチ・スクリーンリーダー・流し見）に平等に情報が届く
2. **トグルチップ（クリックで開く「ⓘ」ボタン）にする**
   - タッチで確実に使える。中に少しリッチな内容も入れられる
   - 実装は tooltip と別物: ボタン + ライブリージョン（`role="status"`）方式。`aria-describedby` や `aria-expanded` は使わない（→ 参考記事 #6）
3. **操作要素を入れたいならノンモーダルダイアログ（ポップオーバー）にする**
   - APG の指示。`role="dialog"` + フォーカス移動ありの設計に切り替える

#### 不採用: `title` 属性

**最大の問題: マウスホバー以外のどの手段でも表示されない。** キーボード・タッチ・視線入力のユーザーには存在しないのと同じ。

**その他の問題:**

- スクリーンリーダーの読み上げサポートが環境・設定依存で不安定
- 表示までの遅延・表示時間・見た目がすべて UA 任せで制御できない
- HTML 仕様自体が「`title` 属性への依存は現状多くのユーザーに届かないため非推奨」と警告している
- なお 1.4.13 に限っては「UA 制御のコンテンツ」の例外に該当して違反にならない。「WCAG 違反ではないが使うべきでない」例として記事で紹介する価値がある

#### 不採用: CSS のみ（`:hover` / `:focus-visible`）の実装

**最大の問題: 1.4.13 の Dismissible（`Esc` で消去）を CSS だけでは実装できない。**

**その他の問題:**

- Persistent は満たせるが、Hoverable はトリガーとツールチップを隙間なく隣接させる等の壊れやすいレイアウトハックが必要になる
- 将来的には `interestfor` + `popover="hint"` が「JS なし」の正攻法になるため、CSS ハックに投資する意味が薄い
- ただし既存ドラフト章の実装例のように「表示スタイルは CSS、表示制御と `Esc` は JS」という役割分担は妥当
