## 1. コンポーネントの概要（What & Why）

### 定義・解決する問題

グラフ（チャート）は、数値データを視覚的な形（棒・折れ線・円など）に変換して、傾向・比較・割合を直感的に伝える表現。テキストや表では把握しにくい「パターン」を一目で伝えられるのが存在意義。

アクセシビリティ観点での本質的な問題: **グラフは「視覚でパターンを把握する」ことに最適化された表現であり、視覚を使わないユーザーには情報がゼロになる**。他章の UI パターンと違い、「操作できるか」ではなく「**同じ情報・同じ結論に別ルートで到達できるか**」が主題になる。

### そもそも使うべきかの判断

- そのグラフは**装飾か、コンテンツか**をまず決める。本文で結論を十分に述べていて、グラフが添え物なら、要件は軽くなる（簡潔な代替テキストで足りる）。グラフでしか伝えていない情報があるなら、その全情報に代替ルートが必要になる
- **データポイントが少ないなら、そもそもグラフにしない選択肢がある**。3〜4 個の数値比較なら、文章や表のほうが正確に伝わる
- 複雑さの上限（Chartability の推奨。→ 参考記事 #5）: カテゴリは 5 個程度まで、二重軸（デュアルアクシス）は避ける。**視覚的に読み解けないグラフは、そもそも誰にとってもアクセシブルでない**
- インタラクティブ（ホバーで値表示、ズーム等）にするほど要件が増える（キーボード・タッチ・1.4.13）。静的なグラフ + 完全なテキスト代替のほうが、実装コストとアクセシビリティの両面で有利な場面が多い

### ネイティブ HTML 要素の有無

- **グラフを描くネイティブ HTML 要素はない**。ただし「グラフの情報の代替」としては **`table` 要素という完璧なネイティブ手段がある**のがこの章の特徴。「データテーブルを併記する」が実装戦略の柱になる
- 描画手段は大きく 2 つで、アクセシビリティの出発点が違う:
  - **SVG**: DOM を持つため、`<title>` / `<desc>` / `role` / テキスト要素で構造を伝える余地がある
  - **`canvas`**: 描画結果はピクセルのみで、**支援技術には何も存在しない**。代替コンテンツ（`canvas` 内のフォールバック、`role="img"` + `aria-label`、外部のテーブル）が必須
- APG にグラフのパターンは存在しない。規範に最も近いのは WAI の複雑な画像チュートリアル（→ 参考記事 #2）と、コミュニティ標準の Chartability（→ 参考記事 #5）

### 類似コンポーネント（表・インフォグラフィック）との使い分け

| 観点 | グラフ | データテーブル | 文章での記述 |
|------|--------|----------------|--------------|
| **得意なこと** | 傾向・比較の直感的把握 | 正確な値の参照 | 結論・解釈の伝達 |
| **スクリーンリーダー** | 代替がなければゼロ | ネイティブに探索可能（行・列見出し） | 完全に伝わる |
| **正確さ** | 概観 | 厳密 | 書き手の要約次第 |
| **役割分担** | パターンを見せる | 値を引けるようにする | 結論を述べる |

- 三者は競合ではなく**組み合わせるもの**。「グラフ（視覚）＋テーブル（探索）＋本文の結論（要約）」の 3 点セットが理想形

## 2. アクセシブルであるためには（要件・規範）

### WCAG 2.2 該当基準の洗い出し

<!-- △ = 該当するか微妙だが念のため入れておく。詳細な要件・確認方法はチェック項目案側 -->

- **達成基準 1.1.1 非テキストコンテンツ（レベル A）** — グラフの中核基準。同等の目的を果たすテキスト代替
- **達成基準 1.4.1 色の使用（レベル A）** — 系列・カテゴリの区別を色だけで行わない（凡例が色頼みになりがち）
- **達成基準 1.3.1 情報及び関係性（レベル A）** — 代替のデータテーブルが正しくマークアップされている（`th` / `scope` / `caption`）
- **達成基準 1.4.3 コントラスト（最低限）（レベル AA）** — 軸ラベル・値ラベル・凡例の文字のコントラスト 4.5:1
- **達成基準 1.4.11 非テキストのコントラスト（レベル AA）** — 棒・線・点そのものが背景と 3:1 以上。隣接する系列同士の区別も
- **達成基準 1.4.4 文字サイズの変更 ／ 1.4.10 リフロー（レベル AA）** — 拡大してもラベルが読める。SVG がリフローに追従する
- **達成基準 2.1.1 キーボード（レベル A）** — インタラクティブなグラフの場合。データポイントの探索・操作
- **達成基準 1.4.13 ホバー又はフォーカスで表示されるコンテンツ（レベル AA）** — ホバーで値ツールチップを出す場合（ツールチップ章の要件がそのまま乗る）
- **達成基準 4.1.2 名前・役割・値（レベル A）** — グラフ全体の名前（`role="img"` + ラベル）、操作 UI の名前
- △ **達成基準 1.4.5 文字画像（レベル AA）** — グラフを PNG 等の画像で配信する場合、ラベル文字が画像文字になる
- △ **達成基準 1.4.12 テキストの間隔（レベル AA）** — HTML テキストで注釈を載せる場合のみ
- △ **達成基準 2.3.1 3 回の閃光（レベル A）** — 点滅を伴うリアルタイム更新グラフの場合
- △ **達成基準 2.2.2 一時停止、停止、非表示（レベル A）** — 自動更新・アニメーションするグラフの場合

### キーボード操作仕様

**規範となる仕様は存在しない**（APG にパターンなし）。参考になるのは Highcharts アクセシビリティモジュールの実装（→ 参考記事 #6）:

| キー | 動作（Highcharts の例） |
|------|--------------------------|
| `Tab` | グラフ内のコンポーネント（系列、凡例、メニュー）間を移動 |
| `←` `→` `↑` `↓` | 系列内のデータポイント間を移動（値を読み上げ） |
| `Enter` / `Space` | ポイントの選択・クリック相当 |

- ただしこれは「インタラクティブなグラフ」を選んだ場合の話。**静的グラフ + データテーブルの構成なら、キーボード要件はテーブルのスクロール程度で済む**（`overflow` するテーブルのラッパーに `tabindex="0"` + ラベル）

### ARIA・マークアップ（SVG / canvas / img 別）

規範がないため、描画手段ごとの定石を整理する:

| 手段 | 基本マークアップ | 説明 |
|------|------------------|------|
| SVG（1 枚画像扱い） | `<svg role="img" aria-labelledby="title-id">` + `<title>` | 最も堅実。中の図形は読み上げ対象から外れる |
| SVG（構造を読ませる） | 各要素に `role` / `aria-label` を付与 | スクリーンリーダーの SVG サポートが不安定で難易度が高い。ライブラリなしでは非推奨 |
| `canvas` | `role="img"` + `aria-label`、または `canvas` 内にフォールバックのテーブル | canvas 自体は支援技術に何も伝えない |
| `img`（PNG 等） | `alt`（短い説明）+ 長い説明への導線 | WAI 複雑な画像チュートリアルの構成 |

補足:

- **短い説明 + 長い説明の 2 部構成**が複雑な画像の定石（→ 参考記事 #2）: 短い説明（`alt` や `aria-label`）は「何のグラフか + 結論の要旨 + 詳細の場所」、長い説明（本文・`figcaption`・テーブル）が実データを担う
- `aria-describedby` で長い説明を関連付けると**構造（見出し・テーブル）が失われて連続テキストとして読まれる**点に注意（WAI チュートリアルの指摘）。テーブルを使うなら参照ではなく、ページ内に実体として置く
- 読み上げ不要な装飾 SVG 部分は `aria-hidden="true"`。膨大な `path` が 1 つずつ読まれる事故を防ぐ

### WCAG 外のユーザビリティ要件

- **タイトルに結論を書く**: 「月別売上」ではなく「売上は 3 月をピークに減少」のように、グラフから読み取ってほしい結論をタイトル・キャプションで言語化する。全ユーザーの理解を助け、テキスト代替の核にもなる
- **直接ラベリング**: 凡例と色の対応を目で往復させず、系列の近くに直接ラベルを置く（色覚・認知・ロービジョンすべてに効く）
- **代替テキストの書き方の公式**（Amy Cesal。→ 参考記事 #9）: 「（グラフの種類）: （データの種類）。（結論・読み取ってほしいこと）」+ データの入手先。例:「棒グラフ: 月別の売上高。3 月の 1,200 万円をピークに減少傾向。詳細は下の表を参照」
- **読みやすさ**: タイトル・注釈は平易に（Chartability は「グレード 9 以下の読みやすさ」を推奨）
- **ソニフィケーション（音声化）**: データを音の高低で表現する手段。Highcharts が標準サポート。発展的話題として紹介価値あり
- **強制カラーモード（Windows のハイコントラストモード等）**: `forced-colors` メディア特性で背景・線が置き換えられ、SVG の `fill` が意図せず消えることがある。`forced-color-adjust` や CSS システムカラーでの調整を検討

### チェック項目案（記事の単位に束ね直す）

#### グラフの情報がテキストでも得られるようにする【本章固有】

- 該当基準: 1.1.1 非テキストコンテンツ、1.3.1 情報及び関係性
- 要件: 短い説明（何のグラフで結論は何か）+ 長い説明（データテーブルまたは構造化された本文）。テーブルは `caption` / `th` / `scope` で正しくマークアップ。グラフでしか伝えていない情報を残さない
- 確認方法: グラフを非表示にして（またはスクリーンリーダーだけで）、本文とテーブルから同じ結論に到達できるか

#### 色だけで系列や意味を区別しないようにする【本章固有】

- 該当基準: 1.4.1 色の使用
- 要件: 色に加えて、パターン（斜線・点描）、形状（マーカーの形、線種）、直接ラベルのいずれかを併用する。色覚シミュレーションでの確認
- 確認方法: グレースケール表示で系列を区別できるか。色覚シミュレータ（P 型・D 型）で確認

#### 文字とグラフ要素に十分なコントラストがあるようにする【本章固有】

- 該当基準: 1.4.3 コントラスト（最低限）、1.4.11 非テキストのコントラスト
- 要件: 軸・値ラベルの文字は 4.5:1、棒・線・点は背景と 3:1。隣接する系列間の区別にも配慮。薄いグレーの軸ラベルがデフォルトのライブラリが多く、初期値のままでは不足しがち
- 確認方法: 文字・グラフ要素それぞれのコントラスト比を計測

#### 拡大・狭い画面でもラベルが読めるようにする【他章共通】

- 流用元: アコーディオン章「文字の拡大・行間の変更・画面幅の縮小でも〜」項
- 該当基準: 1.4.4 文字サイズの変更、1.4.10 リフロー（1.4.5 文字画像もここに吸収: SVG や HTML テキストで描き、ラベルをピクセルに焼き込まない）
- 要件（グラフ固有）: 拡大時にラベル同士が重ならない。狭い画面ではグラフの縮小ではなく、レイアウト変更（縦棒→横棒等）やテーブルへの誘導も選択肢
- 確認方法: ズーム 200%・画面幅 320px でラベルが読めるか

#### インタラクティブにするなら、キーボード・タッチでも同じ情報に到達できるようにする【本章固有】

- 該当基準: 2.1.1 キーボード、1.4.13 ホバー又はフォーカスで表示されるコンテンツ、4.1.2
- 要件: ホバーでしか出ない値ツールチップを作らない。キーボードでデータポイントを辿れるようにする（Highcharts 方式）か、同じ値をテーブルで提供する
- 確認方法: マウスなしで、すべてのデータ値に到達できるか
- 補足: 「インタラクションを足すほど要件が増える。静的 + テーブルが最も安上がりでアクセシブル」という判断構造を明示する

#### タイトル・キャプションで結論を言語化する【本章固有】【ユーザビリティ】

- 該当基準: なし（WCAG 外。強いて言えば 1.1.1 の質を高める実践）
- 要件: 「何のグラフか」だけでなく「何が読み取れるか」をタイトルまたはキャプションに書く
- 確認方法: タイトルだけ読んで、グラフの要点が伝わるか

#### 見送り（チェック項目にしない基準）

- **2.3.1 3 回の閃光 ／ 2.2.2 一時停止** — リアルタイム更新グラフ限定の話。カルーセル章（2.2.2）を参照させる程度
- **1.4.12 テキストの間隔** — SVG 内テキストには実質適用しにくい。1.4.4 の項に吸収
- **2.4.7 フォーカスの可視化** — インタラクティブ路線を採る場合のみ。キーボード項の確認方法に吸収

## 3. 具体事例（Evidence）

### 実装事例（ライブラリ・ツール）

| 項目 | Highcharts（+ a11y モジュール） | Chart.js | D3.js | Excel / Tableau 等の BI |
|------|----------------------------------|----------|-------|--------------------------|
| **描画方式** | SVG | canvas | SVG（自前） | 画像 or 独自 |
| **テキスト代替** | 情報リージョン自動生成（グラフ種別・データの説明） | 自前（`canvas` に `role="img"` + `aria-label` を推奨とドキュメントに明記） | すべて自前 | 代替テキスト設定機能あり |
| **キーボード操作** | ✅ データポイント単位で移動・読み上げ | ✖ 自前 | ✖ 自前 | ツール依存 |
| **ソニフィケーション** | ✅ 公式モジュール | ✖ | ✖ | ✖ |
| **位置づけ** | アクセシビリティ対応の業界リーダー | 「デフォルトでは非対応」と公式が明言 | 素材（責任は実装者） | 作成者向け機能の充実度に差 |

- **Highcharts のアクセシビリティモジュールが「フル対応するとどうなるか」の見本**（RNIB との協業で開発。キーボードナビゲーション・スクリーンリーダー向け説明・ソニフィケーションまで揃う）。自前実装の目標水準として引用価値が高い（→ 参考記事 #6, #7）
- Chart.js / D3 を使う場合は「ライブラリは何もしてくれない」前提で、`role="img"` + 代替テーブルの構成を自分で組む（→ 参考記事 #10 の azukiazusa 記事が日本語の好例）

#### 設計判断ポイント（実装が割れている論点）

- **静的 + テーブル vs インタラクティブ** — 本章最大の分岐。インタラクティブにするなら Highcharts 級の対応（キーボード・読み上げ・ツールチップの 1.4.13）が必要になる。記事は「まず静的 + テーブルで成立させ、インタラクションは足し算」の順で解説するのが安全
- **SVG を 1 枚画像として扱うか、構造を読ませるか** — `role="img"` で閉じるのが堅実。SVG 内部の ARIA はスクリーンリーダー間の挙動差が大きく、自前では踏み込まない判断が現実的
- **データテーブルの置き方** — 常時表示か、`details` で折りたたむか、別ページか。折りたたみはアコーディオン章の知見（`details`/`summary`）を流用できる
- **凡例 vs 直接ラベル** — 系列数が少なければ直接ラベルが全面的に優位。凡例を使うなら色 + 形状の冗長コーディング

### 失敗事例（ありがちな NG 例）

<!-- 候補ベース。執筆前にコード例化と裏取りをする -->

- **NG: `canvas` グラフに何の代替もない**
  - 対応する要件: 1.1.1 非テキストコンテンツ
  - 何が起きるか: スクリーンリーダーには完全な空白。ページの主役級の情報が丸ごと欠落する
  - 出典・実例: Chart.js 公式も「デフォルト非対応・実装者が対応せよ」と明言
- **NG: `alt="グラフ"` `alt="売上推移のグラフ"` で終わる**
  - 対応する要件: 1.1.1（「同等の目的」を果たしていない）
  - 何が起きるか: 「グラフがある」ことは分かるが、中身も結論も分からない
- **NG: 凡例が色見本だけ（色覚特性で区別不能）**
  - 対応する要件: 1.4.1 色の使用
  - 何が起きるか: P 型・D 型色覚では赤/緑系の系列が同じ色に見え、どの線がどの系列か分からない
  - 出典・実例: 東京都の COVID-19 サイトで実際に Issue 化され改善された（→ 参考記事 #12）
- **NG: ホバーでしか値が見えない（ツールチップ依存）**
  - 対応する要件: 2.1.1 キーボード、1.4.13、タッチアクセス
  - 何が起きるか: キーボード・タッチ・スクリーンリーダーのユーザーは正確な値に到達できない
- **NG: 薄いグレーの軸ラベル・細い薄色の線（ライブラリのデフォルト）**
  - 対応する要件: 1.4.3、1.4.11
  - 何が起きるか: ロービジョン・屋外の画面では軸も線も見えない。「デフォルトのまま」が違反になる代表例
- **NG: SVG 内部の要素が大量に読み上げられる（aria-hidden 漏れ）**
  - 対応する要件: 1.1.1 / 4.1.2 の運用
  - 何が起きるか: スクリーンリーダーが意味のない「パス、パス、パス…」を延々読む
- **NG: グラフ画像に文字を焼き込んで拡大でぼやける**
  - 対応する要件: 1.4.5 文字画像、1.4.4
  - 何が起きるか: 拡大しても解像度が上がらず読めない。翻訳もされない

### 新しいブラウザ機能

グラフ領域には現時点で直接の新ブラウザ機能はない（この節は本章では薄くてよい）。関連する周辺動向のみ:

- **`forced-colors` メディア特性**（全ブラウザ対応済み）: 強制カラーモードでグラフの `fill` / `stroke` が置き換えられる問題への対応手段。`forced-color-adjust: none` の慎重な利用と、システムカラーでの再配色
- **`ariaNotify()` API**（Chrome 141〜。トースト章参照）: リアルタイム更新グラフの値変化通知に将来使える可能性

### フォールバック・不採用案

#### フォールバック: グラフを正しく実装できないときの選択肢

1. **データテーブル + 本文の結論だけで成立させる**: グラフは「あれば嬉しい視覚的補助」に格下げする。情報保障としてはこれで完結する
2. **静的画像 + 2 部構成のテキスト代替**: インタラクティブ実装を諦め、WAI 複雑な画像チュートリアルの構成（短い alt + 長い説明）に落とす
3. **数値が少なければ文章で書く**: 「前年比 12% 増の 1,200 万円」で足りるならグラフ自体が不要

#### 不採用: SVG 内部をフル ARIA マークアップして「読めるグラフ」を自作する案

**最大の問題: SVG 内の ARIA サポートはスクリーンリーダー・ブラウザ間の差が大きく、検証コストに対して得られる体験が安定しない。** Highcharts 級のライブラリが多大なコストをかけて実現している領域を、記事の実装例で再現するのは現実的でない。

**その他の問題:**

- 「読める」順序の制御（DOM 順）と視覚配置の整合を保ち続けるのが難しい
- データテーブル併記のほうが、実装コスト・確実性・ユーザーの慣れのすべてで勝る
- 採用するなら自作ではなく Highcharts 等の実績あるライブラリに乗る

#### 不採用: CSS だけでグラフを描く（charts.css 等）案

**最大の問題: 見た目はグラフだが、支援技術には `table` や `div` の羅列として伝わり、視覚とセマンティクスが一致しない。**

**その他の問題:**

- ツールチップ・拡大・強制カラーでの挙動が管理しにくい
- 元がテーブルなら「テーブルをそのまま出す + SVG グラフを添える」ほうが素直
