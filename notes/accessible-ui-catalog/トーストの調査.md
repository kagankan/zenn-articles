# トースト UI コンポーネント — 調査結果まとめ

## 1. コンポーネントの概要（What & Why）

### 定義・解決する問題

トーストは、操作の結果（保存完了・送信完了など）を画面の隅に一時的に表示して知らせる通知 UI。スナックバーとも呼ばれる。作業の流れを中断せずに、短いステータスを伝えるために使う。

- Scott O'Hara の定義: 「簡潔なメッセージを、一貫した位置にポップアップ表示するもの」（→ 参考記事 #5）
- 重要な境界線: **複数行のテキストや複数の操作要素を持つものは、もはやトーストではなくダイアログ**（O'Hara）。「トーストに何でも詰め込む」のが混乱の始まり
- Adrian Roselli の警句: 「**トーストをトーストたらしめている特性（勝手に消える・隅に出る・浮いている）を取り除くほど、アクセシビリティは上がる**」（→ 参考記事 #6）。つまりトーストは本質的にアクセシビリティと相性が悪い UI であり、その自覚を持って使う

### そもそも使うべきかの判断

- トーストの弱点は構造的なもの:
  - **見落とされる**: 画面の隅に短時間出るだけ。拡大表示のユーザーは視野の外、作業に集中しているユーザーは気づかない
  - **消える**: 読む速度はユーザーによって大きく違う。読み終わる前に消えれば、伝わらなかったのと同じ
  - **浮いている**: DOM 上の位置と視覚上の位置が乖離しやすく、スクリーンリーダーの探索で見つけにくい
- したがって**「見落とされても実害がない情報」だけをトーストにしてよい**（O'Hara・Roselli 一致）。「保存しました」は OK、「エラーで保存されていません」をトーストだけで流すのは NG
- **操作要素（取り消しボタン等）をトーストに入れない**のが原則（→ 層 2・層 3）。入れる場合は同じ操作を別の恒久的な場所でも提供する
- 代替案（Roselli の 3 案）: ページ内の静的メッセージ（フォームの近くに置く）／通知センター方式（履歴として溜める）／そもそも通知しない（本当に必要かを再考する）

### ネイティブ HTML 要素の有無

- **トーストに相当するネイティブ HTML 要素はない**。`<std-toast>` 要素の標準化提案（2019 年ごろ）があったが頓挫している
- 実装の本筋は **ARIA ライブリージョン（`role="status"` 等）+ JS**。ツールチップやタブと違い「見た目のパターン」ではなく「**支援技術への通知の仕組み**」が主戦場になる、本書では毛色の違う章
- `popover` 属性（`popover="manual"`）はトップレイヤー表示の助けにはなるが、**ライブリージョン機能を持たないため単独ではトーストにならない**（O'Hara の指摘。→ 参考記事 #5）
- 新 API `ariaNotify()` が Chrome 141 で出荷され、ライブリージョンの構造的な弱点を解消する可能性がある（→ 層 3「新しいブラウザ機能」）

### 類似コンポーネントとの使い分け

| 観点 | トースト | インラインメッセージ | 通知センター | アラートダイアログ |
|------|----------|----------------------|--------------|---------------------|
| **表示位置** | 画面の隅に浮く | 操作した場所の近く | 一覧に蓄積 | 画面中央（モーダル） |
| **消え方** | 自動または手動 | ページが変わるまで残る | ユーザーが消すまで残る | ユーザーが閉じるまで残る |
| **作業の中断** | しない | しない | しない | する |
| **向く内容** | 見落とせる成功報告 | フォームエラー・結果 | あとで見返す通知 | 応答必須の重大な警告 |
| **ARIA** | `role="status"` | `role="status"` / エラーは `aria-describedby` 等 | `role="log"` | `role="alertdialog"` |

- **エラーは原則インラインで**（消えない・文脈がある・再確認できる）。トーストはあくまで「成功しました」系
- ユーザーの応答が必要な内容は `alertdialog`（ダイアログ章参照）へ

## 2. アクセシブルであるためには（要件・規範）

### WCAG 2.2 該当基準の洗い出し

<!-- △ = 該当するか微妙だが念のため入れておく。詳細な要件・確認方法はチェック項目案側 -->

- **達成基準 4.1.3 ステータスメッセージ（レベル AA）** ※WCAG 2.1 新規 — トーストの中核基準。フォーカスを移さずに、ロールやプロパティを通じて支援技術がステータスメッセージを判定・通知できること
- **達成基準 2.2.1 タイミング調整可能（レベル A）** — 自動消去は時間制限。原則、消える前提の設計をしない（詳細は後述）
- **達成基準 2.4.3 フォーカス順序（レベル A）** — トースト表示時にフォーカスを奪わない
- **達成基準 2.1.1 キーボード（レベル A）** — 操作要素を入れる場合、キーボードで到達・操作できる（そもそも到達が難しいのがトースト）
- **達成基準 1.4.3 コントラスト（最低限）（レベル AA）** — トーストの文字と背景のコントラスト
- **達成基準 4.1.2 名前・役割・値（レベル A）** — 閉じるボタンの名前等
- △ **達成基準 1.3.2 意味のある順序（レベル A）** — DOM 挿入位置と視覚位置の乖離（Roselli が指摘）
- △ **達成基準 2.4.11 隠されないフォーカス（最低限）（レベル AA）** ※WCAG 2.2 新規 — トーストがフォーカス中の要素に覆いかぶさる場合
- △ **達成基準 1.4.4 文字サイズの変更 ／ 1.4.12 テキストの間隔（レベル AA）** — 拡大時にトーストがあふれない
- △ **達成基準 2.2.4 中断（レベル AAA）** — 通知の延期・抑制をユーザーが選べる
- △ **達成基準 2.3.3 インタラクションによるアニメーション（レベル AAA）** — スライドインのアニメーション

#### 2.2.1（自動消去）の整理（Roselli による。→ 参考記事 #6）

自動消去は原則として 2.2.1 の時間制限に該当する。適合させる方法は:

- 事前に表示時間をユーザーが調整できる、または
- 都度延長できる（ホバー・フォーカスでタイマー停止はこの系譜）、または
- **20 時間以上表示し続ける**（＝実質「自動で消さない」）

実務的な帰結: **「見落とされても構わない情報だけを載せ、同じ情報を別の場所（ページ内の状態表示・履歴）でも確認できるようにしたうえで」自動消去する**のが現実解。操作要素や必須情報を載せた瞬間、自動消去は違反になると考えてよい。

### キーボード操作仕様

**APG にトーストのパターンは存在しない**（Alert パターンがあるのみ）。つまりタブやダイアログのような規範仕様がなく、キーボード操作はライブラリごとの独自拡張になっている。この「規範の不在」自体が記事で伝える価値のある事実。

| キー | 動作 | 出典 |
|------|------|------|
| （なし） | 基本形: トーストはフォーカスを受けず、キーボード操作を持たない | O'Hara 推奨の基本形 |
| `F8`（カスタム可） | トースト表示領域へフォーカスをジャンプ | Radix Toast の独自ホットキー |
| `Esc` | フォーカスがあるトーストを閉じる | Radix Toast |

- 原則: **トーストがフォーカスを奪ってはならない**（`role="alert"` でもフォーカス移動は不適切と Roselli が明言）
- 操作要素を入れる場合のみ、到達手段（ホットキー等）の問題が発生する → 入れないのが最も簡単な解

### ARIA ロールと属性

| ロール | aria-live 相当 | 用途 |
|--------|----------------|------|
| `status` | `polite`（+ `aria-atomic="true"` が暗黙） | トーストの基本形。他の読み上げを妨げず、落ち着いたタイミングで通知 |
| `alert` | `assertive` | 進行中の読み上げに割り込む。時間に敏感な重大情報のみ。乱用しない |
| `log` | `polite` | 順序が意味を持つ蓄積型（チャット、通知履歴）。新規は末尾に追加 |

| 属性 | 付与先 | 値・説明 |
|------|--------|----------|
| `aria-live` | コンテナ | ロールを使わず明示する場合（`polite` / `assertive`）。ロール優先でよい |
| `aria-atomic` | コンテナ | `true` で領域全体を読み上げ（`role="status"` は暗黙で true） |
| `aria-label` | 閉じるボタン | 「通知を閉じる」等 |

**最重要の実装知識（ライブリージョンの罠）:**

- **ライブリージョンのコンテナは、メッセージを入れる前から DOM に存在していなければならない**。トースト表示のタイミングで `role="status"` 付き要素ごと挿入しても、多くのスクリーンリーダーは読み上げない（O'Hara・日本語では 24motz 氏の検証記事が詳しい。→ 参考記事 #11）
- 正しい手順: 空のライブリージョンをページ読み込み時に設置 →（少し遅延させて）**中身のテキストだけを挿入**する
- **ライブリージョン内のセマンティクスは伝わらない**: 中にボタンやリンクを入れても、読み上げでは「ボタンであること」が伝わらない（O'Hara）。操作要素を入れない原則の技術的根拠
- `display: none` や `visibility: hidden` のコンテナからの変更は通知されない

### WCAG 外のユーザビリティ要件

- **ホバー・フォーカス・ウィンドウ非アクティブでタイマーを止める**（Radix はこの 3 つすべてでタイマーを一時停止する）
- **表示位置の一貫性**: 同じアプリ内でトーストの出る場所を固定する（O'Hara）
- **複数トーストのスタック管理**: 新しい通知が古い通知を押し流さない。大量発生時はまとめる
- **`prefers-reduced-motion`** でスライドイン・アニメーションを止める
- **表示時間の目安**: 読む時間には個人差が大きい。「文字数 × 係数」の自動計算でも、最低 5 秒程度 + 一時停止手段の組み合わせが無難（Radix のデフォルトは 5000ms）

### チェック項目案（記事の単位に束ね直す）

#### 表示した内容が、フォーカスを移さずにスクリーンリーダーへ伝わるようにする【本章固有】

- 該当基準: 4.1.3 ステータスメッセージ、2.4.3 フォーカス順序
- 要件: 空の `role="status"` コンテナを**事前に** DOM へ設置し、表示時は中身のテキストだけを差し込む。フォーカスは移動させない
- 確認方法: スクリーンリーダーで、フォーカスを動かさずにトースト内容が読み上げられるか。表示の瞬間にフォーカス位置が変わっていないか
- 補足: コンテナ後入れ・`display: none` からの切り替えで読み上げられない罠を、失敗例とセットで解説する

#### 読み終わる前に消えない（消えても困らない）ようにする【本章固有】

- 該当基準: 2.2.1 タイミング調整可能（2.2.4〔AAA〕もここに吸収）
- 要件: （1）自動消去するのは見落とされても実害がない情報だけ、（2）ホバー・フォーカスでタイマーを停止、（3）同じ情報を別の恒久的な場所でも確認できる、の 3 点セット。エラーや必須情報は自動消去しない（そもそもトーストにしない）
- 確認方法: トーストにポインタを乗せている間、消えずに残るか。トーストを見逃した場合に同じ情報へ到達する手段があるか

#### 操作要素をトーストに入れない（入れるなら代替手段を用意する）ようにする【本章固有】

- 該当基準: 2.1.1 キーボード、2.2.1、4.1.2
- 要件: 原則入れない。どうしても入れる場合は、（1）キーボードで到達する手段（Radix の F8 のようなホットキー等）、（2）同じ操作をトースト外の恒久的な場所でも提供（Radix の `altText` の思想）、（3）タイマー停止、をすべて満たす
- 確認方法: マウスなしで、消える前にトースト内のボタンへ到達・実行できるか。トーストを逃してもその操作を実行する別の手段があるか

#### 通知の重要度に応じて `status` と `alert` を使い分ける【本章固有】

- 該当基準: 4.1.3（の適切な実装方法の選択）
- 要件: 基本は `role="status"`（polite）。読み上げに割り込む `role="alert"`（assertive）は、時間に敏感で重大な内容のみ
- 確認方法: 成功系の通知が、進行中の読み上げに割り込んでいないか

#### 文字と背景に十分なコントラストがあるようにする【他章共通】

- 流用元: ツールチップ章「ツールチップの文字と背景に十分なコントラストがある」項（浮遊 UI の背景色という同型の問題）
- 該当基準: 1.4.3 コントラスト（最低限）
- 確認方法: 文字と背景のコントラスト比 4.5:1 以上。半透明背景なら下のコンテンツ次第で変わる点に注意

#### 文字の拡大・行間の変更でも中身が切れないようにする【他章共通】

- 流用元: アコーディオン章の同名項
- 該当基準: 1.4.4 文字サイズの変更、1.4.12 テキストの間隔
- 要件（トースト固有）: 拡大時にトーストが画面を覆い尽くさない・テキストが見切れない。固定高さを避ける
- 確認方法: ズーム 200%・行間 1.5 で全文が読めるか

#### 見送り（チェック項目にしない基準）

- **1.3.2 意味のある順序** — DOM 挿入位置の問題は「事前設置コンテナ」の実装で自然に解決するため、独立項目にしない
- **2.4.11 隠されないフォーカス** — トーストがフォーカス要素を覆う問題は、表示位置の設計（ユーザビリティ節）で触れる
- **2.3.3 インタラクションによるアニメーション** — ツールチップ章と同じ判断。実装例の CSS（`prefers-reduced-motion`）で触れるに留める
- **2.2.3 タイミング非依存（AAA）** — 2.2.1 の項目に吸収

## 3. 具体事例（Evidence）

### 実装事例（デザインシステム・ライブラリ）

APG に規範がないため、「識者の推奨」と「主要ライブラリ」を並べて比較する構成が向く。

| 項目 | Scott O'Hara 推奨 | Adrian Roselli 推奨 | Radix UI Toast | MUI Snackbar |
|------|--------------------|----------------------|----------------|--------------|
| **ロール** | `role="status"`（履歴型は `log`） | 用途別に `status` / `log` / `alert` を使い分け | `aria-live` 準拠（foreground / background の 2 種別） | `Alert` 併用時は `role="alert"`（要検証） |
| **自動消去** | 批判的（消えても困らない情報のみ） | 2.2.1 違反になり得ると明言 | 5000ms デフォルト + ホバー・フォーカス・ウィンドウ blur で停止 | `autoHideDuration` 指定時のみ自動消去（要検証） |
| **操作要素** | 入れない。恒久的な場所に同じ操作を | 入れない（必要ならダイアログ） | 入れられるが `altText` で代替手段の明示を要求。「無視して安全」な操作のみ | `action` prop あり |
| **キーボード到達** | （操作要素を入れないので不要） | 同左 | `F8` でビューポートへジャンプ、`Esc` で閉じる | — |

- **Radix Toast は「操作要素を入れる派」の中で最も要件を意識した実装**。「Action は無視しても安全なものに限る。確認が必要なら AlertDialog を使え」とドキュメントで明言しており、O'Hara / Roselli の原則と実は同じ側にいる（→ 参考記事 #7）
- MUI Snackbar 行は執筆時にドキュメントで裏取りする（要検証マークの箇所）

#### 設計判断ポイント（実装が割れている論点）

- **操作要素（「元に戻す」等）を入れるか** — 識者は「入れるな」、プロダクト（Gmail の Undo 等）は「入れたい」で恒常的に割れる。折衷解が Radix 方式（ホットキー + `altText` + 恒久的な代替手段）。記事では「入れない」を基本形、「入れるなら 3 点セット」を発展形として提示できる
- **`status` か `alert` か** — 成功通知に `alert`（assertive）を使う実装が世に多いが、割り込みの濫用。使い分け基準を層 2 に記載
- **DOM 設置方式** — 事前設置の単一ライブリージョンに使い回すか、トーストごとに生成するか。読み上げの確実性では事前設置が優位
- **自動消去のデフォルト** — 消えない（ユーザーが閉じる）をデフォルトにするか、5 秒等で消すか。載せる情報の性質で決まる（＝「消えても困らない情報だけ載せる」が守られていれば自動消去でよい）

### 失敗事例（ありがちな NG 例）

<!-- 候補ベース。執筆前にコード例化と裏取りをする -->

- **NG: トースト表示のタイミングでライブリージョンごと DOM に挿入する**
  - 対応する要件: 4.1.3 ステータスメッセージ
  - 何が起きるか: 多くのスクリーンリーダーで何も読み上げられない。見た目は動いているため気づかれにくい、この章最大の罠
  - 出典・実例: O'Hara（→ #5）、24motz 氏の検証（→ #11）
- **NG: エラーメッセージをトーストだけで通知して消す**
  - 対応する要件: 2.2.1 タイミング調整可能（実害としては致命的な情報喪失）
  - 何が起きるか: 見逃したユーザーは操作が失敗したことを知る手段がない
- **NG: トーストにフォーカスを移動させる**
  - 対応する要件: 2.4.3 フォーカス順序、4.1.3（フォーカスを移さず伝えるのが基準の趣旨）
  - 何が起きるか: 入力中のフォームからフォーカスが奪われ、作業が中断・入力が失われる
- **NG: 成功通知を `role="alert"`（assertive）で割り込ませる**
  - 対応する要件: 4.1.3 の適切な実装
  - 何が起きるか: 読み上げ中の内容が中断される。重要でもない「保存しました」が他のすべてに優先される
- **NG: 「元に戻す」ボタンがトーストの中にしかない**
  - 対応する要件: 2.1.1 キーボード、2.2.1
  - 何が起きるか: キーボードユーザー・スクリーンリーダーユーザーは消える前にボタンへ到達できず、取り消し機能が事実上使えない
- **NG: ライブリージョン内のボタンやリンクのセマンティクスを頼りにする**
  - 対応する要件: 4.1.2 名前・役割・値
  - 何が起きるか: 読み上げではテキストしか伝わらず、「操作できること」自体が伝わらない
- **NG: 大量のトーストを連続表示する（読み上げの洪水）**
  - 対応する要件: 4.1.3 の運用、2.2.4
  - 何が起きるか: スクリーンリーダーが通知の読み上げに占拠される。まとめ・間引きが必要

### 新しいブラウザ機能: `ariaNotify()` API（Chrome 141〜）

```js
document.ariaNotify("設定を保存しました");
// 要素起点でも呼べる
button.ariaNotify("カートに追加しました", { priority: "high" });
```

- **何ができるか**: スクリーンリーダーへの読み上げを **DOM 変更なしで直接指示**できる。ライブリージョンの構造的な弱点（事前設置が必要・DOM 挿入タイミングの罠・visibility の罠）をまとめて回避する
- `priority` オプション（`normal` / `high`）で読み上げの優先順位を制御（polite / assertive に相当する概念の整理し直し）
- **対応状況**: Chrome 141（2025 年 10 月）で出荷。それ以前は Edge のオリジントライアル。Firefox・Safari 未対応（2026 年 7 月時点）。W3C ARIA WG で仕様策定中
- **何はまだライブリージョンが必要か**: 非対応ブラウザすべて。当面は「ライブリージョンが本筋、`ariaNotify` は将来の解決策」という位置づけ。機能検出（`"ariaNotify" in document`）でのプログレッシブエンハンスメントは可能
- **チャプターでの扱い方**: トースト実装の難所（＝ライブリージョンの罠）がブラウザ API で解消されつつある文脈で紹介。ツールチップ章の `interestfor` と同じ「Chrome 先行・本筋は従来実装」の温度感

### フォールバック・不採用案

#### フォールバック: トーストを使わずに済ませる選択肢

1. **インラインの静的メッセージ**: 操作した場所の近くに `role="status"` で表示し、消さない。文脈が保たれ、2.2.1 の問題が消える。フォームの結果通知はこれが第一候補
2. **通知センター方式（`role="log"` の履歴）**: 通知を蓄積し、ユーザーが好きなときに見る。見落としが構造的になくなる。Roselli の「トーストウォーマー」案
3. **重大な内容はアラートダイアログへ**: 応答が必要なものはトーストの守備範囲外（ダイアログ章参照）

#### 不採用: `popover` 属性だけでトーストを作る案

**最大の問題: `popover` はトップレイヤー表示を提供するだけで、ライブリージョン機能がない。** 表示してもスクリーンリーダーに通知されない。

**その他の問題:**

- `popover="auto"` は他の popover を閉じてしまい、複数トーストと相性が悪い（使うなら `popover="manual"`）
- ライブリージョンと組み合わせれば有効（表示位置の管理を popover に任せる）なので、「単独では不採用、併用は可」という整理

#### 不採用: 自動消去トーストに必須の操作・情報を載せる設計

**最大の問題: 2.2.1 に違反し、キーボード・スクリーンリーダーのユーザーには機能が存在しないのと同じになる。**

**その他の問題:**

- 「時間内に反応を要求する UI」は認知・運動・視覚のすべての面で排除的
- Gmail の Undo のような有名事例も、実際には設定で取り消し猶予時間を変更できる（＝2.2.1 の「事前調整」への配慮）。真似するならそこまで含めて真似る必要がある
