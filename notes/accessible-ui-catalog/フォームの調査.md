## 1. コンポーネントの概要（What & Why）

### 定義・解決する問題

フォームは、ユーザーからの入力（テキスト・選択・送信）を受け取る UI 群の総称。本章はテキスト入力・セレクト・チェックボックス・ラジオボタンなどの個別要素ではなく、**それらに共通する横断的な関心事**を主題にする:

- ラベルと説明の関連付け
- 選択肢のグループ化
- 必須・エラーの伝達
- 入力支援（type / autocomplete / inputmode）
- 送信前後の誤り防止

フォームは本書の他コンポーネントと違い「使うか迷う」対象ではなく、**アクセシビリティ上の失敗が直接「手続きできない・買えない・問い合わせできない」という実害になる**、最も影響の大きい領域。

### そもそも使うべきかの判断

「フォームを使うか」ではなく「**入力させる量を減らせるか**」が判断軸になる:

- 項目を減らす・任意項目を削る（入力の総量がそのままユーザーの負担）
- 既知の情報を再入力させない（WCAG 2.2 の新基準 3.3.7 がこれを要求。→ 層 2）
- 自動入力に乗る（`autocomplete` を正しく付ければブラウザが肩代わりする）
- **ネイティブのフォームコントロールを使い、カスタム UI を自作しない**。`select` や `input type="date"` の見た目が気に入らないという理由で `div` 製のカスタムコントロールを作ると、キーボード・スクリーンリーダー・モバイル対応のすべてを自前で背負う（→ 層 3「不採用」）

### ネイティブ HTML 要素の有無

- **フォームは HTML のネイティブ機能の本丸**。`form` / `label` / `fieldset` / `legend` / `input`（豊富な `type`）/ `select` / `textarea` / `output` が揃っており、正しく使えば ARIA はほぼ不要
- 本書の原則「ネイティブ要素を土台にする」が最も強く効く章。逆に言えば、**ネイティブから離れるほど（カスタムセレクト等）要件が爆発する**構造を示しやすい
- 長年の不満だった「`select` の見た目をカスタマイズできない」問題には、`appearance: base-select`（Customizable Select）というブラウザ側の回答が出はじめている（→ 層 3「新しいブラウザ機能」）

### 構成要素の整理（類似コンポーネントの代わりに）

| 関心事 | 主な手段 | 主な達成基準 |
|--------|----------|--------------|
| 名前を付ける | `label for` / `id` | 3.3.2、4.1.2、1.3.1 |
| 説明を付ける | 説明文 + `aria-describedby` | 3.3.2、1.3.1 |
| グループ化 | `fieldset` / `legend` | 1.3.1 |
| 入力支援 | `type` / `autocomplete` / `inputmode` | 1.3.5 |
| エラー伝達 | テキスト + `aria-describedby` + `aria-invalid` + ライブリージョン | 3.3.1、3.3.3、4.1.3、1.4.1 |
| 誤り防止 | 確認・修正・取り消しの機会 | 3.3.4（3.3.6） |

## 2. アクセシブルであるためには（要件・規範）

### WCAG 2.2 該当基準の洗い出し

<!-- フォームは 3.3 系（入力支援）がほぼ全部該当する。△ = 該当するか微妙 -->

- **達成基準 3.3.2 ラベル又は説明（レベル A）** — すべての入力欄にラベル・必要な説明がある
- **達成基準 1.3.1 情報及び関係性（レベル A）** — ラベル・説明・グループがプログラム的に関連付いている（`label for` / `aria-describedby` / `fieldset`）
- **達成基準 4.1.2 名前・役割・値（レベル A）** — 入力欄の名前がスクリーンリーダーに伝わる（過去調査の観点）
- **達成基準 3.3.1 エラーの特定（レベル A）** — どの項目で何のエラーかがテキストで特定できる
- **達成基準 3.3.3 エラー修正の提案（レベル AA）** — 修正方法を提示できる場合は提示する（過去調査の観点）
- **達成基準 3.3.4 誤り防止（法的、金融、データ）（レベル AA）** — 送信の取り消し・チェック・確認のいずれかを提供（過去調査の観点。3.3.6〔AAA〕はその全フォーム版）
- **達成基準 4.1.3 ステータスメッセージ（レベル AA）** — エラー発生をフォーカス移動なしでスクリーンリーダーに伝える（過去調査の観点）
- **達成基準 1.4.1 色の使用（レベル A）** — 必須・エラーを色（赤）だけで伝えない（過去調査の観点）
- **達成基準 1.4.3 コントラスト（最低限）（レベル AA）** — プレースホルダーのコントラスト 4.5:1。**無効（disabled）状態のコントロールは適用除外**（過去調査が例外まで明記していた観点）
- **達成基準 1.3.5 入力目的の特定（レベル AA）** ※WCAG 2.1 新規 — 氏名・住所等の定番項目に `autocomplete` 属性
- **達成基準 3.3.7 冗長な入力（レベル A）** ※WCAG 2.2 新規 — 同じプロセス内で一度入力した情報を再入力させない（自動入力・選択式で再提示）
- **達成基準 3.3.8 アクセシブルな認証（最低限）（レベル AA）** ※WCAG 2.2 新規 — ログインで記憶・転記のテスト（パスワードの手打ち強制、CAPTCHA）を課さない。パスワードマネージャー・コピー＆ペーストを妨げない
- **達成基準 2.1.1 キーボード（レベル A）** — ネイティブコントロールなら自動で満たせる
- **達成基準 2.4.7 フォーカスの可視化（レベル AA）** — フォーカスリング（`overflow: hidden` による欠けに注意、は過去調査の指摘）
- **達成基準 2.4.6 見出し及びラベル（レベル AA）** — ラベルが内容を適切に説明している
- **達成基準 3.2.2 入力時（レベル A）** — 入力・選択をきっかけに勝手に送信・遷移しない
- △ **達成基準 2.5.3 ラベルを含む名前（レベル A）** — 視覚ラベルと `aria-label` を併用する場合のみ
- △ **達成基準 2.5.8 ターゲットのサイズ（最低限）（レベル AA）** — チェックボックス・ラジオが小さい
- △ **達成基準 2.4.3 フォーカス順序（レベル A）** — エラーサマリーへのフォーカス移動、DOM 順と視覚順の一致
- △ **達成基準 3.3.5 ヘルプ（レベル AAA）** — 文脈依存のヘルプ提供（過去調査に含まれていた）
- △ **達成基準 1.4.4 ／ 1.4.12 ／ 1.4.10（レベル AA）** — 拡大・行間・狭幅でラベルと入力欄が崩れない（長いラベル・長いエラー文のテストケースを過去サンプルが持っていた）

### キーボード操作仕様

ネイティブコントロールを使う限り、キーボード操作はブラウザが提供する（これ自体が「自作しない」根拠）:

| コントロール | 標準操作 |
|--------------|----------|
| テキスト入力 | 通常のテキスト編集 |
| セレクト | `↑` `↓` で選択、`Enter` / `Space` で開閉、文字キーで頭出し |
| ラジオグループ | `Tab` でグループへ、`↑` `↓` `←` `→` で選択移動（roving tabindex をブラウザが実装している） |
| チェックボックス | `Space` で切り替え |
| 送信 | テキスト欄で `Enter`、ボタンで `Enter` / `Space` |

- ラジオボタンの矢印キー移動は「ブラウザが標準実装している roving tabindex」であり、タブ章の JS 実装と対になる好例として書ける

### マークアップと ARIA

| 手段 | 用途 | 説明 |
|------|------|------|
| `label for` / `id` | 名前 | 基本。クリック領域の拡大という全ユーザー向けの利点もある |
| `fieldset` / `legend` | グループ | ラジオ・チェックボックス群の質問文は `legend` に。読み上げで各選択肢に文脈が付く |
| `aria-describedby` | 説明・エラーの関連付け | 形式の説明（「ハイフンなし」等）とエラーメッセージを入力欄に紐付ける |
| `aria-invalid="true"` | エラー状態 | エラー時に付与、解消したら外す |
| `required` | 必須 | ネイティブ検証も動く。`aria-required` はネイティブが使えない場合のみ |
| `autocomplete` | 入力目的（1.3.5） | `name` / `email` / `tel` / `postal-code` 等の定義済みトークン |
| `inputmode` / `pattern` | モバイルのキーボード切替・形式 | `type` と組み合わせる（過去調査の観点） |
| `output` 要素 | 計算結果・件数等 | 暗黙で `role="status"`（ライブリージョン）になる。過去サンプルはエラーメッセージにも使用していた |

**過去調査からの重要なアップデート — `aria-errormessage` は当面使わない:**

- 過去のサンプルは `aria-errormessage` + `aria-invalid` でエラーを関連付けていたが、**NVDA・VoiceOver が `aria-errormessage` をサポートしておらず、W3C の ARIA WG では `aria-describedby` があれば足りるとして廃止（deprecate）の議論まで出ている**（→ 参考記事 #6, #7）
- 現在の推奨は **`aria-describedby` でエラーメッセージを紐付ける**こと。JAWS / NVDA は `aria-describedby` で関連付けたエラーの出現を（`aria-live` なしでも）読み上げる挙動が確認されている
- 記事では「仕様上はエラー専用の属性があるが、サポートが追いついていない」という、No ARIA is better than Bad ARIA と同系の教訓として書ける

### WCAG 外のユーザビリティ要件

- **プレースホルダーに頼らない**（過去調査が参考記事付きで挙げていた観点）: 入力を始めると消える・コントラスト不足になりがち・翻訳されにくい・ラベル代わりに使うと 3.3.2 違反。使うなら補助的な入力例に限定する
- **必須より「任意」を明記する**戦略もある（大半が必須なら、少数の任意側に印を付けるほうが認知負荷が低い。GOV.UK 方式）。「＊」だけの必須表現は意味が伝わらないので「必須」とテキストで書く
- **送信ボタンを disabled にしない**: 入力不備で送信ボタンを無効化すると、「なぜ押せないのか」が伝わらず、フォーカスもできないため状況の説明も届きにくい。押させてエラーを説明するほうが親切
- **エラーサマリー（GOV.UK パターン）**: 送信時にページ上部へエラー一覧を表示してフォーカスを移し、各項目へのリンクを張る。ページタイトルにも「エラー:」を前置する
- **label の内包 vs 隣接**: 過去実装は「`input` の状態で `label` のスタイルを変える都合」で隣接構造（`input` + `label`）を採っていたが、現在は `label:has(input:checked)` が全ブラウザで使えるため、**内包構造でもスタイル都合の制約はなくなった**。クリック領域の広い内包も選択肢に戻せる

### チェック項目案（記事の単位に束ね直す）

#### すべての入力欄にラベルが関連付いているようにする【本章固有】

- 該当基準: 3.3.2 ラベル又は説明、1.3.1、4.1.2、2.4.6
- 要件: `label for` / `id` で明示的に関連付ける。プレースホルダーをラベル代わりにしない
- 確認方法: ラベルをクリックすると入力欄にフォーカスが移るか。スクリーンリーダーで入力欄の名前が読まれるか

#### 関連する選択肢がグループとして伝わるようにする【本章固有】

- 該当基準: 1.3.1 情報及び関係性
- 要件: ラジオ・チェックボックス群を `fieldset` で囲み、質問文を `legend` に置く
- 確認方法: スクリーンリーダーで選択肢にフォーカスしたとき、質問文（グループ名）も読まれるか

#### 必須・エラーが色以外でも伝わるようにする【本章固有】

- 該当基準: 1.4.1 色の使用、3.3.2
- 要件: 「必須」をテキストで書く（「＊」や赤色だけにしない）。エラーも赤枠だけでなくテキストで示す
- 確認方法: グレースケール表示で必須項目とエラー項目が特定できるか

#### エラーの場所と直し方がわかるようにする【本章固有】

- 該当基準: 3.3.1 エラーの特定、3.3.3 エラー修正の提案
- 要件: エラーメッセージは「どの項目で」「何が問題で」「どう直すか」をテキストで示し、`aria-describedby` で入力欄に関連付け、`aria-invalid` を付ける。項目数が多いフォームではエラーサマリー（上部一覧 + 各項目へのリンク + フォーカス移動）を併用
- 確認方法: スクリーンリーダーでエラー項目にフォーカスしたとき、名前に続けてエラー内容が読まれるか
- 補足: `aria-errormessage` は使わない（サポート不足。層 2 参照）

#### エラーの発生がフォーカスを移動しなくても伝わるようにする【他章共通】

- 流用元: トースト章「表示した内容が、フォーカスを移さずにスクリーンリーダーへ伝わる」項（ライブリージョンの知見を流用）
- 該当基準: 4.1.3 ステータスメッセージ
- 要件: 送信時のエラー通知をライブリージョン（`role="status"` / `output` 要素）で伝えるか、エラーサマリーへフォーカスを移す（この場合は 4.1.3 の対象外になる—フォーカス移動が通知を兼ねる）
- 確認方法: 送信ボタンを押した直後、フォーカスを動かさずにエラーの発生が読み上げられるか（またはエラーサマリーにフォーカスが移るか）

#### 適切な type・autocomplete・inputmode で入力を支援する【本章固有】

- 該当基準: 1.3.5 入力目的の特定（type / inputmode は WCAG 外の実務要件）
- 要件: 定番項目に `autocomplete` トークン。用途に合う `type`（メール = `email`、電話 = `tel`）。数字入力でも電話番号・郵便番号には `type="number"` を使わない（値の丸め・スピナー等の問題。`type="text"` + `inputmode="numeric"`）
- 確認方法: ブラウザの自動入力が正しい欄に入るか。モバイルで適切なキーボードが出るか

#### 送信前に確認・修正・取り消しの機会があるようにする【本章固有】

- 該当基準: 3.3.4 誤り防止（法的、金融、データ）、3.3.6（AAA）
- 要件: 取り消せる・送信前にチェックされる・確認画面等で見直せる、のいずれかを満たす
- 確認方法: 重要な送信（購入・契約・削除）の前に、内容を確認または後から取り消す手段があるか

#### 一度入力した情報を再入力させないようにする【本章固有】

- 該当基準: 3.3.7 冗長な入力（WCAG 2.2 新規）
- 要件: 同一プロセス内で既出の情報（配送先と請求先が同じ、等）は自動入力または選択式で再提示する
- 確認方法: 複数ステップのフォームで、同じ情報を 2 度手入力させられる箇所がないか

#### 文字の拡大・行間の変更・画面幅の縮小でも崩れないようにする【他章共通】

- 流用元: アコーディオン章の同名項
- 該当基準: 1.4.4、1.4.12、1.4.10
- 要件（フォーム固有）: 長いラベル・長いエラーメッセージ・長い選択肢で崩れないか（過去サンプルはこれらの長文テストケースを一式持っていた。実装例に引き継ぐ価値あり）
- 確認方法: 長文ケース + ズーム 200% + 画面幅 320px で、ラベルと入力欄の対応が視覚的に保たれるか

#### 見送り（チェック項目にしない基準）

- **3.3.8 アクセシブルな認証** — ログインフォーム特有の話。汎用チェック項目にせず、コラム（CAPTCHA・パスワードマネージャー阻害の禁止）として扱う候補
- **3.2.2 入力時** — 自動送信・自動遷移の話はリダイレクト章・フィルター章に委譲
- **2.5.8 ターゲットのサイズ** — チェックボックス・ラジオのサイズはスタイリング（実装例）で触れる
- **3.3.5 ヘルプ（AAA）** — 「提供できる場合は提供する」性質で、チェック項目の形にしにくい。説明文の項に一言吸収
- **2.5.3 ラベルを含む名前** — `aria-label` 併用時のみの注意。実装例の補足で触れる

## 3. 具体事例（Evidence）

### 実装事例（デザインシステム・ガイドライン)

| 項目 | WAI Forms チュートリアル | GOV.UK | freee アクセシビリティー・ガイドライン | 過去の社内フレームワーク |
|------|---------------------------|--------|------------------------------------------|---------------------------|
| **ラベル** | `label` 必須、他手段は例外 | `label` + ヒント文 | `label` 必須を明文化 | `label for` / `id` を徹底 |
| **必須の表現** | — | **任意側に「(optional)」を付ける** | テキストで明示 | 「必須」バッジ + `required` |
| **エラー表示** | インライン + 概要の両方を推奨 | エラーサマリー + フォーカス移動 + タイトルに「Error:」 | 特定・修正提案を項目化 | `output` 要素 + `aria-errormessage`（現在は describedby へ更新推奨） |
| **入力支援** | — | `type="number"` を避ける方針を明文化 | `autocomplete` を推奨 | type / autocomplete / inputmode / pattern を明記 |

- **GOV.UK のフォームパターンが実務の最高水準**。エラーサマリー・「任意」表記・`type="number"` 回避など、根拠（ユーザーテスト）付きの判断が揃っている
- **freee アクセシビリティー・ガイドライン**は日本語で読める体系的チェックリストとして参照価値が高い（→ 参考記事 #10）

#### 設計判断ポイント（実装が割れている論点）

- **エラー表示のタイミング** — 送信時にまとめて／フォーカスが外れたとき（blur 時）／入力中リアルタイム、で割れる。入力中の即時エラーは「入力し終わる前に怒られる」問題があり、blur 時も入力途中の離脱で誤爆する。「送信時 + サマリー」が最も事故が少なく、リアルタイムは形式が確定している項目（文字数等）に限定するのが穏当
- **確認画面の是非** — 日本の商習慣では確認画面が定番（3.3.4 の達成手段として明快）。一方、GOV.UK は「1 ページ 1 質問 + 最後に Check answers ページ」方式。どちらも 3.3.4 を満たせるので、「確認の機会がある」ことが本質と整理する
- **必須マーク vs 任意マーク** — 大半が必須のフォームなら任意側に印（GOV.UK）。混在が激しいなら必須側に「必須」テキスト。「＊」単独は避ける
- **ラベルの内包 vs 隣接** — 隣接（`for`/`id`）はスタイルが素直、内包はクリック領域が広い。`:has()` 普及後はスタイル都合の差がなくなったため、好みで選べる時代になった（過去実装の判断根拠が失効した例として書ける）

### 失敗事例（ありがちな NG 例）

- **NG: プレースホルダーをラベル代わりにする**
  - 対応する要件: 3.3.2、1.3.1（関連付けられた名前がない）
  - 何が起きるか: 入力を始めると項目名が消え、確認時に何の欄か分からない。コントラスト不足も常態化する
- **NG: 「＊」や赤色だけで必須を表す**
  - 対応する要件: 1.4.1、3.3.2
  - 何が起きるか: 「＊」の意味が説明されておらず、色覚特性・スクリーンリーダーには必須であることが伝わらない
- **NG: エラーが赤枠だけで、どこで何が起きたか書いていない**
  - 対応する要件: 3.3.1、1.4.1
  - 何が起きるか: エラーの存在も内容も特定できない。スクリーンリーダーには何も起きていないように見える
- **NG: エラーメッセージが DOM に出るだけで、通知もフォーカス移動もない**
  - 対応する要件: 4.1.3
  - 何が起きるか: 送信ボタンを押しても無反応に感じ、フォームが壊れていると判断して離脱する
- **NG: ラジオ・チェックボックス群に `fieldset` / `legend` がない**
  - 対応する要件: 1.3.1
  - 何が起きるか: 「はい」「いいえ」だけが読み上げられ、何への回答か分からない
- **NG: 電話番号・郵便番号に `type="number"`**
  - 対応する要件: 実務要件（値の破壊）
  - 何が起きるか: 先頭の 0 が消える・スピナーで誤操作する・「e」が入力できてしまう。過去サンプルにも `type="number"` があり、用途の線引きを示す教材になる
- **NG: `autocomplete="off"` の乱用・ペースト禁止**
  - 対応する要件: 1.3.5、3.3.8
  - 何が起きるか: パスワードマネージャーや自動入力が使えず、記憶・転記を強制される。認知障害のユーザーに最も深刻
- **NG: 入力不備の間、送信ボタンを disabled にして放置**
  - 対応する要件: 実務要件（4.1.2 の観点でも状態の説明がない）
  - 何が起きるか: なぜ押せないのか誰にも伝わらない。フォーカスもできないため説明も届かない
- **NG: `div` + JS の自作セレクトボックス**
  - 対応する要件: 2.1.1、4.1.2 ほか多数
  - 何が起きるか: キーボードの頭出し・矢印移動・モバイルのネイティブピッカーがすべて失われる。No ARIA is better than Bad ARIA の代表例

### 新しいブラウザ機能

#### Customizable Select（`appearance: base-select`、Chrome 135〜）

- `select` の見た目を CSS で完全にカスタマイズし、`option` 内に画像等のリッチコンテンツを置ける standards-track の機能。**「見た目のためにカスタムセレクトを自作する」動機そのものを消しにきている**
- 対応状況（2026 年 7 月時点）: Chrome / Edge 135（2025 年 4 月）。Firefox・Safari は未対応（ポジションは肯定的）
- 非対応ブラウザでは通常の `select` として動く（プログレッシブエンハンスメントとして安全に使える）

#### `:user-valid` / `:user-invalid`（Baseline 済み）

- ユーザーが操作した後にだけ一致する検証系擬似クラス。`:invalid` の「ページを開いた瞬間から必須項目が全部エラー表示」問題を解消する。CSS だけでエラースタイルのタイミング制御ができる

#### `field-sizing: content`（Chrome 123〜）

- `textarea` を入力量に応じて自動で伸ばす。長文入力時に「小さい窓の中でスクロール」を強いない改善。1.4.10（リフロー）系の体験向上

### フォールバック・不採用案

#### フォールバック: ネイティブコントロールに寄せる

- フォームの「フォールバック」は特殊で、**凝った実装をやめて素の HTML に戻ること自体が最良のフォールバック**。`select` の見た目が要件なら Customizable Select の到来を待つ（または見た目要件を再交渉する）ほうが、自作より安全
- 検証も、まず HTML のネイティブ検証（`required` / `type` / `pattern`）で成立させ、メッセージの質を上げたいときに JS（`novalidate` + 自前表示）へ段階的に移行する

#### 不採用: `div` ベースの自作セレクト・自作チェックボックス

**最大の問題: ネイティブが無償で提供している機能（キーボード操作・スクリーンリーダー対応・モバイルのネイティブ UI・自動入力・フォーム送信との統合）をすべて自前で再実装することになり、完全な再現はほぼ不可能。**

**その他の問題:**

- 見た目の課題は現在ほぼ CSS で解決できる（`accent-color`、擬似要素でのチェックボックス装飾、`appearance: base-select`）
- どうしてもリッチな選択 UI が必要な場合はコンボボックス（APG パターン）になるが、これは本書の別章級の難易度であることを明示する

#### 不採用: `aria-errormessage` への依存

**最大の問題: NVDA・VoiceOver が対応しておらず、関連付けたエラーが読み上げられない。** W3C でも `aria-describedby` で足りるとして廃止議論がある。

**その他の問題:**

- 過去の社内フレームワークでも採用していたが、現在は `aria-describedby` への置き換えが推奨。「仕様に存在する属性でも、支援技術のサポートを確認してから使う」教訓の実例として記事で使える
